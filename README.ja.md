# reyn-knowledge — AI コーディングエージェント運用の検証ノウハウ集

AI コーディングエージェント(Claude Code 等)の fleet(複数エージェントの一群)でソフトウェアを開発・レビューするときに固有に発生する、**検証の失敗パターンとその対処**を体系化したナレッジ集。

## これは何か

母体は [reyn](https://github.com/tya5/reyn)(AI エージェントランタイム)の開発現場である。reyn はほぼ全ての実装・レビュー・マージ判断をコーディングエージェントの fleet が行っており、その過程で数百件の「検証の失敗と対処」がクロスセッション記憶(memory pin)として蓄積された。

その記憶の大半は、一般的なソフトウェア工学の教科書には載っていない種類のものだった — **「エージェントが自分の書いたテスト・ゲート・fixture を過信する形」の実測記録**である。(例中の strip・ゲート等の用語は下の用語集を参照。)例:

- エージェントが「strip して RED を確認した」と報告するが、strip は当たっていなかった
- 8540 本のテストと CI が緑のまま、production では機構が一度も動いていなかった
- 「fixture を録り直した」という申告と「通るように手書きした」を区別する必要が生じた

本リポジトリは、これらの記録から **reyn 固有の文脈を剥がし、AI エージェントを使う開発全般に適用できる形に一般化**したものである。教育資料として、CS 学生や AI エージェント運用の初学者にも読めるよう、各ドキュメントに具体的なコード例を付けている。

## 構成

```
docs/
├── verification/   # Tier 1: AI 生成物の検証パターン(strip 反証・空虚なゲート・census/structure(根拠の2分類)等)
├── git-github/     # Tier 2: エージェント駆動 git/CI 運用の罠(closing keyword・stale local・マージゲート等)
└── orchestration/  # Tier 3: マルチエージェント fleet 運用(予定)
skills/             # 実行可能な checklist(第1弾: closing-keyword-check)
CATALOG.md          # 全ドキュメント索引 + 出典対応表
```

入口は[検証ナレッジの体系マップ](docs/verification/index.ja.md) — 25本のドキュメントが「完了報告をマージするまでに何をどの順で疑うか」のパイプラインとしてどう配置されるか、および横断する4原理をまとめてある。coder / tester / reviewer を別エージェントに分ける標準的な運用に向けては、[役割分離運用の実務](docs/verification/roles.ja.md)が全体系を役割ごとの義務(coder の報告契約・tester の反証メニュー・reviewer の独立検証・マージゲート)に組み直している。個別に読むなら [strip 反証の規律](docs/verification/strip-falsification.ja.md) と [検証環境の構造的盲目](docs/verification/environment-blindness.ja.md) が代表格。git/GitHub 運用側は [Tier 2 の地図](docs/git-github/index.ja.md)から。

## 用語集(最小限)

各ドキュメントは単体で読めるよう、専門用語には本文の初出でも説明を付けている。ここは横断的な最小セット。

| 用語 | 意味 |
|---|---|
| RED / GREEN | テストの失敗 / 成功 |
| assert(表明) | テストコード内の検査式。成立しなければテストは失敗する |
| CI | 継続的インテグレーション。変更を push するたびに自動でテスト一式を回す仕組み |
| PR | プルリクエスト。一まとまりの変更の提案・レビュー単位 |
| ゲート(gate) | 特定の退行を防ぐ目的で置かれるテスト・自動チェック |
| witness | ある性質が壊れたときに RED になるテスト。「witness がある」=「壊すと検知される」 |
| strip 反証(strip-falsify) | 機構を一時的に無効化してテストが RED になることを確認する手順 |
| 空虚(vacuous) | 守るべき欠陥が起きているビルドでも緑になる状態 |
| co-vet | 独立第二検証。実装者の報告を、別のエージェント/人が独立に再検証すること |
| fixture | テスト用に保存した入出力データ(録画済み API 応答など) |
| fleet | 複数のコーディングエージェントの一群 |
| pin | reyn 開発のクロスセッション記憶の1エントリ(本リポジトリのソース) |

## 編集フロー(ソース pin → doc)

1. ソース pin を読み、**不変の教訓**と **reyn 固有の実例**を分離する
2. 固有語彙を一般語彙に置換する(セッション名 → 役割名、内部機構名 → 一般的な機構名)
3. 不変の教訓を主文に、**CS 学生でも追える具体例(トイコード)**を添えて書く
4. reyn 実例は「出典」節に issue 番号ごと残す(出典の透明性のため削除しない)
5. 関連 doc へ相互リンクし、`CATALOG.md` に pin → doc の対応行を足す

reyn 側の pin は増え続けるため、このリポジトリは一度きりの export ではなく**定期同期**を前提とする。同期の単位は CATALOG の対応表である。

## ライセンス / 出典

本文中の `#NNNN` は reyn の PR / issue 番号。事例はすべて実際の開発ログから一般化した。
