# stall-triage — 「止まっているように見える」を5分で切り分ける手順

**使いどき**: 依頼した相手が無音になったとき / 「テスト待ち」の報告のまま動きが見えないとき / 監視(watcher)から idle 候補が上がってきたとき。

前提: エージェントの沈黙は多義である(黙々と作業中 / LLM 応答待ち / 文脈圧縮(会話履歴の自動要約)待ち / 死んだ背景ジョブ待ち / 本当の停止)。以下は**安い検査から順に**並んでいる。

## Step 1 — 自分の直前の送信文を読み返す(最安の検査)

- 相手が plan-first(承認が出るまで実装しない方針)なら: 自分の GO は「決定」の言葉で書いたか? 「推奨します」調なら、**相手は正しく待っている** — stall ではない。断定調で書き直して再送する。
- 相手の質問に答え忘れていないか。依頼文に実行不能な指示(既定タイムアウトで完走不能な foreground 実行など)を書いていないか。

## Step 2 — 機械申告を直接確認する

- セッションの active/idle の**機械申告(bool)**を見る(前提の構成: 各セッションが停止フックで申告を出す — [止まっているエージェントの見つけ方](../../docs/orchestration/stall-detection.ja.md)§4。その bool の欄を見る)。LLM が書いた状態文字列(「CI 待ち」等)は見ない — **同じ文字列の繰り返しは活動の証拠ではなく、staleness(情報が古い)のシグナル**である。
- 申告が active なら、長い正しい計算で静かなだけの可能性を残す。Step 5 へ。idle(または申告機構が無い構成)なら Step 3 の実測へ。

## Step 3 — 3点測定(推測しない)

```bash
gh pr list -R <owner>/<repo> --author <agent>   # 1. open な PR に当該作業が無いか
git -C <worktree> status --porcelain   # 2. 未コミット差分の有無
git -C <worktree> log --oneline -3     #    新しい commit の有無
pgrep -fl <プロセス名のパターン>          # 3. プロセスの生存(ps aux | grep は grep 自身をヒットさせるので使わない)
```

## Step 4 — 結果で原因を帰属する

| 測定結果 | 帰属 | 次の一手 |
|---|---|---|
| PR 無し + 未コミット差分有り + プロセス無し | **死んだ背景ジョブ待ち**(最頻) | nudge(軽い声かけ)して commit を回収させる |
| プロセスが1本でも生存 | 正当に進行中 | 急かさない。Step 5 で所要時間だけ照合 |
| 差分無し・プロセス無し・直前まで活発 | 無出力の作業(読解・思考)中 or 文脈圧縮待ち | nudge を先に打ち、返答の時間を与える。再起動は最後 |
| local に commit があるのに push 無し | 偽 stall(不可視なだけ) | 「区切りごとに push + 一言 status」を次回の依頼文に入れる |

## Step 5 — 「実行中」の自称は既知の所要時間と照合する

- そのタスクの正常値の**数倍〜10倍**を超えて still-running なら、slow ではなく hung として扱う。
- 正常値は時期とともに変わる(スイートは成長する) — **照合は絶対値でなく倍率で**行う。

## Step 6 — 報告は verified fact で書く

- 「実装中のはず」ではなく「**最終活動 HH:MM、PR 未着 = 進捗未確認**」と書く。
- 「running なので順調」をそのまま中継しない(Step 5 を経てから)。

## 背景

各 Step の出典事故(1晩6回の死んだジョブ待ち、44分 hang の「順調」中継、10時間沈黙の誤帰属ほか)は [止まっているエージェントの見つけ方](../../docs/orchestration/stall-detection.ja.md) を参照。
