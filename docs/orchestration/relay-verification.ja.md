# 中継の検証 — 伝聞を運ぶ前に自分で測る

## 前提

fleet(複数エージェントの並行運用)では、主張がメッセージハブ(セッション間のメッセージ中継)越しに流れてくる。ハブ越しの主張は**見た目は事実、実体は伝聞**である。そして中継には増幅作用がある: リード役がオーナーに運んだ時点で、伝聞は**一次報告の顔**になる(受け手はリードの報告を検証済みとして信頼する)。この文書は、[文脈を持たない主張](../verification/cross-context-claims.ja.md)のラベル規律を、中継という動作に特化させた運用編である。

## 1. インフラの状態は、世界で最も安く検証できる主張

実測: 「LLM プロキシが落ちている」という2セッションからの報告を、**自分では一度も確認せずに**複数ターンにわたりオーナーへ中継し、実作業(live 検証・A/B 測定)をその「障害」で止めていた。オーナーの「本当に落ちてるか確証はあるんですか?」を受けて `curl` を1発打ったら — **ずっと生きていた**(全エンドポイント HTTP 200、プロセス生存。相手は一時的な遅延を「down」に過大汎化していた)。

- サービスの生死・ポート・health・プロセスは、**curl / lsof / ps の1発**で確定する(例: `curl -s -o /dev/null -w '%{http_code}' http://localhost:8000/health` — この1行で「down」仮説は決着する)。この安さで検証を省く言い訳は存在しない。
- 相手の「X が down」は**検証すべき仮説**であって、中継すべき事実ではない。
- 未検証のまま運ばざるを得ないときは「**相手の報告では X、当方未検証**」とラベルする — 平叙文に洗浄(launder)しない。
- 生の失敗を取る: connection refused / 遅いだけ / 5xx は**別の故障**であり、「down」という語はそれを潰す。

## 2. claim は literal command + scope で運ぶ — 省略形は伝播事故の源

claim(主張)は、実行した literal command(文字どおりのコマンド)と scope(検査した範囲)ごと運ぶ。「audit clean」「CI green」「トリガー条件成立」のような**省略形の claim** は、3セッション連鎖の伝播事故を実測で起こしている: 発信者は狭い検査(`--check private-state` = 単一規則だけの検査)しか実行していないのに、ハブへの報告は広い検査(`--strict tests/` = 全規則での検査が exit 0)で書かれ、中継者がそれを未検証で転送し、**受信者が literal command を直接実行して初めて 18 errors が発覚**した — 狭/広の差は対象ディレクトリではなく検査の種別そのものだった。

- **発信側**: 実行した**コマンドとスコープをそのまま**書く。「`--check private-state tests/` → 0 errors」は防御可能、「audit clean」は事故源。
- **受信側**: その claim で**次の行動を gate する(進む/止まるの関門にする)なら**、引用された literal command を自分で実行してから動く。
- **誤スコープが発覚したら**: 元の claim を見た**全員に broadcast で訂正**する。こっそり直して先へ進まない(他の受信者が同じ推論を適用中かもしれない)。

## 3. 数値は出力のコピーのみ — 手打ち・記憶・再計算の禁止

状態報告に載せる数値(PR 件数・マージ状態・カウント)は、**その場で実行したコマンド出力のコピーだけ**を使う。手打ち・記憶からの再現・頭の中での再計算は禁止。とくに **alarm 系(CI FAIL 等)は、出力行の引用なしに発してはならない** — 捏造された regression alarm が fleet に伝播した実測が、この規律の起点である。

## 4. 発見の中継前に、交絡の除外

相手の live 検証・実地試験の「発見」をオーナーへエスカレートする前に、**テスト設定の交絡(confound = 結果を歪める併存要因)が除外されているか**を確認する。

実測: 「未知アクションで 12/12 が空停止 = 構造的ブロッカー」という報告をそのまま「深い構造欠陥」としてオーナーへ運んだ。実際にはテスト側が **fake の部品 + 意味を成さないタスク**で構成されており、実在する**部分的な**欠陥(実タスクでの空停止率は約67%)を**全滅(100%)に増幅**していた。逆に、交絡が判明した後に「純粋なアーティファクト(欠陥なし)」へ過剰補正する対称の罠もある — 真値は中間だった。

- エスカレーション前に: (a) 発見は**本物の一貫したタスク**(実スキーマ + 遂行可能な課題)の上か、(b) 「ブロッカー」と「純アーティファクト」の**両仮説を実タスクの一次データが決着するまで保持**しているか、(c) エスカレーション文に**交絡除外の状態を明記**したか。

## チェックリスト

- [ ] インフラ状態の claim: 自分で1発(curl/lsof/ps)測ったか。未検証なら「未検証」ラベルを付けたか
- [ ] claim を発信するとき: literal command + scope を書いたか。省略形にしていないか
- [ ] claim で行動を gate するとき: 引用コマンドを自分で実行したか
- [ ] 誤スコープの発覚時: 全受信者へ broadcast 訂正したか
- [ ] 数値・alarm: コマンド出力のコピー(引用)か。手打ち・記憶・再計算をしていないか
- [ ] 発見の中継前: 交絡は除外済みか。両仮説を保持しているか。除外状態を明記したか

## 出典(reyn 開発での実測)

インフラ: LLM プロキシ「down」中継事件(実際は全 200。オーナーの一言で発覚)。literal command: 2026-05-28 の3セッション連鎖(狭いスコープの実行が広いスコープの claim として伝播、受信側の直接実行で 18 errors)+ 翌日の「backlog から消えた = merged」誤報(実際は closed)と broadcast 訂正。数値コピー: 捏造 regression alarm の伝播(v9 実地試験)。交絡: Stage A 実地試験(「187」は当時の内部アークのラベルで GitHub の issue 番号ではない。fake 部品+無意味タスクが 67% を 100% に増幅、実タスクで中間値に決着)。
