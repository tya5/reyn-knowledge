# 依頼文の規律 — 書いた通りにしか動かず、書いた高さでしか守られない

## 前提

エージェントへの依頼文(dispatch brief = 作業を任せるときの指示文)は、プログラムに近い。受け手は書かれたことを実行し、書かれていないことは実行しない。さらに重要なのは、**書かれた内容の「高さ」(抽象度)が、守られる範囲を決める**ことである。この文書は、依頼文の書き方そのものが事故を作った実測と、その予防の型である。[役割分離運用の実務](../verification/roles.ja.md)が役割ごとの義務の全体像なら、本書はその依頼側の各論にあたる。

## 1. 「X を写せ」は危険 — 不変条件を名指す

まず問題の形を、上限付きキュー(溜められる件数に上限のある待ち行列)の例で見る:

```python
# A: 溢れたら「一番古いもの」を捨てる
if queue.full():
    queue.get_nowait()   # 古い1件を捨てて場所を空ける
queue.put_nowait(item)

# B: 溢れたら「新しいもの」を捨てる
if not queue.full():
    queue.put_nowait(item)   # 満杯なら新規の方を諦める
```

「上限付きキュー」という高さでは A と B は**同一**である。違いはその1段下、「何を捨てるか」にだけ現れる — そして事故はその段で起きる。購読者に最新を届けたい場所(遅れた読者が追いつくための上限)では A が正しい。一方、**次に実行されるべき仕事**を積んでいる場所で A を使うと、次に走るはずだった仕事を黙って捨てる。どちらも「正当な上限付きキュー」なので、**テストは緑のまま**壊れる。

実測: 「`bus.py` の上限付きキューの形を写せ。新しい設計を発明するな」という依頼文が出た。`bus.py` は間違った手本だった(課題チケット自身が正しい手本を名指していたのに、依頼者はチケットを読んだ上で間違ったファイルを指した)。指示どおり写していれば、「動く・緑・もっともらしい」コードが次に実行される処理を静かに捨てていた。受け手の実装エージェントが写すのを拒否して発覚した。

依頼文の安全度は3段ある:

| 依頼文の形 | 安全度 |
|---|---|
| **不変条件(invariant = 常に保たれるべき性質)を名指す**: 「保留分に上限を付けよ。ただし次に実行される1件は決して捨てるな」 | **最良** — 手本のファイル名を間違えても生き残る |
| **手本を名指し + 不変条件の特定を明示的に委譲**: 「先に X を読み、それが何を保存しているかをあなたが名指せ。写すかどうかはその後に決めよ」 | **安全** — 手本が探索を導き、委譲が「写すのを拒否する」ことを期待された動きにする(不服従ではなく) |
| **手本だけ**: 「X を写せ」 | **危険** — 本節の対象 |

実際に事故を防いだのは懐疑心ではなく、依頼文自身に入っていた1つの手順だった: 「まず `bus.py` を読み、**何を**制限しているのか(件数か・並行数か・頻度か)を述べよ」— この質問が「何を捨てるか」を視界に引きずり出した。∴ **「この手本が何を保存しているか述べよ」を、「写せ」より前の手順として必ず置く**。名指しの手順が防御であり、写す手順は防御ではない。

同型の失敗がもう1つ: 「一覧を返す既存の命令があるから、それを呼べばよい」という設計 — 登録済みで呼べる、までは真。だが**出力が1本の文字列**で、受け手の繰り返し処理はリストしか受け取れなかった。「ある・呼べる」の高さで確認を打ち切らず、「**出力の形を下流が食えるか**」まで1段下りる。**到達可能 ≠ 使用可能**。

## 2. 利用者に見える変更には「ドキュメント更新」を必須項目として書く

実測: 約15本の PR(変更提案)を実装中心の依頼文で回した結果、新しい設定キー・フック点・コマンドが、機能一覧や設定リファレンスに**未記載のまま蓄積**した。CI(自動テスト)は通り続けた — ドキュメントは CI の合格条件ではないからである。オーナーの「ドキュメント化漏れを検討して」で初めて発覚した。決定的な対照実験が同時期にある: 依頼文にドキュメント更新を入れていた変更群には、ドキュメントが**あった**。入れれば入る、入れなければ入らない — それだけの話である。

- **依頼文**: 利用者に見える変更(新しい設定キー・フック点・コマンド・イベント種別)には、対応するドキュメントの更新を必須項目として明記する。
- **レビュー側**: PR のファイル一覧に docs/ が無い「利用者に見える変更」は指摘対象にする(実装だけの PR はドキュメント負債のサイン)。
- **大量に並行させるとき**: 各 PR では最小限のドキュメント + 一区切りごとに文書担当へ全数の抜け漏れ点検を依頼する二段構えでもよい([完全性掃討の実務](../verification/completeness-sweeps.ja.md))。

## 3. 検証義務は「具体的な動作」で書く — ラベル確認と中身確認は別物

「〜を確認せよ」という依頼は、受け手が**一番安い確認**で満たしてしまう。実測2件(同じレビューを分担した別々のサブエージェント = 補助作業のために起動した子エージェント):

- (a) 「テストの等級表記に違反がないか確認」→ サブエージェントは docstring(関数に付く説明文)の**ラベルだけ**を見て、assert(テストの検査文)の中身を見ずに「違反なし」と申告 → CI で6件検出。`assert len(result) == 3` のような、出力形式を固定してしまう検査文が残っていた。
- (b) 「この関数がどの領域に属するか確認」→ テストの**ディレクトリ名から推論**(tests/chat/ 配下だから chat 領域)して中身を読まず「別領域への影響なし」と申告 → 実際は別領域のデータに触っており、変更をまるごと取り消すことになった。

どちらも受け手の怠慢と呼ぶのは簡単だが、予防できるのは依頼側である。**検証義務は、表面(ラベル・名前・置き場所)ではなく中身に対する具体的な動作として書く**:

```
## 検証義務(依頼文に貼る型)
1. ラベル(docstring の表記等)の確認だけで終えるな
2. 検査文の中身を grep で直接列挙せよ:
   grep -n "assert len(" tests/
   grep -n 'assert.*==.*"' tests/      # 固定文字列との比較
3. 対象の関数の中身を Read で直接確認し、import と呼び出しの連鎖を追え
4. 「ディレクトリが X 系だから X 領域」という表面からの推論を禁止する
5. 確認に使った一次証拠(grep の出力・読んだ関数名)を申告に含めよ
```

これは[監査は内容を照合する](../verification/audit-content-match.ja.md)(在ることと中身が合っていることは別)の依頼側である。受け手の注意力に期待するのではなく、依頼文が「表面推論の禁止」と「一次証拠の添付」を明文化する。

## 4. GO は「決定」として書く — 推奨は待たれる

plan-first(承認が出るまで実装に入らない方針)で動く相手が、判断を仰ぐ質問を出してきたとする。ここで確定のつもりで「(2) は KEEP **推奨**」と返すと、相手は**正しく待つ** — 「推奨」は傾き(まだ相手が決めていない)であって確定ではないから、規律ある相手ほど着手しない。

実測: この曖昧さが作った沈黙を、依頼側は停止(stall)と誤診し、状況確認の声かけ — そこで初めて断定調で書き直した文 — が実質の着手許可になった。**待った側の規律は正しく、曖昧だったのは依頼側である。**

- 確定を出すときは「**GO — X で確定**(推奨ではなく決定)」と、決定であることを言葉で示す。
- 「推奨/どちらかといえば」は、本当に相手に決めてほしいときだけに取っておく。
- GO を出したつもりの相手が沈黙したら、停止を疑う前に**自分の送信文を読み返す**(soft な書き方でなかったか)。[止まっているエージェントの見つけ方](stall-detection.ja.md)§5 の対。

## チェックリスト

- [ ] 「X を写せ」と書きそうになったら: 保存すべき不変条件を名指したか。最低でも「あなたが名指せ」と委譲したか
- [ ] 「この手本が何を保存しているか述べよ」を、写す手順より前に置いたか
- [ ] 手本の出力・形が下流で使えるか(到達可能≠使用可能)まで確認を下ろしたか
- [ ] 利用者に見える変更の依頼文に、ドキュメント更新を必須項目として入れたか
- [ ] 検証依頼に「ラベルでなく中身」「表面推論の禁止」「一次証拠の添付」を明文化したか
- [ ] plan-first の相手への確定を「決定」の言葉で書いたか。相手の沈黙時、まず自分の文を読み返したか
