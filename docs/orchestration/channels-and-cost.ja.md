# 通信経路と待機コスト — どこで話し、どう待つか

## 前提

複数のエージェントセッションを並行運用すると、通信経路が複数できる: **メッセージハブ**(セッション間の短いメッセージ中継。配達に数十秒の遅れがあり、セッションの再起動で消える)、**issue/PR**(課題チケットと変更提案。永続で、後から監査できる)、**記録ファイル**(教訓の永続化)。経路の選択を誤ると、重要な決定が短命なキューで消えたり、合図の応酬でノイズと往復コストが積み上がる。もう1つの軸が**待機コスト**である: エージェントの「待たせ方」によって、暇なあいだも LLM(言語モデル)を起こし続けて課金される構成と、イベントが来たときだけ起きる構成に分かれる。

## 1. 経路は用途で分ける

| 経路 | 用途 | 永続性 |
|---|---|---|
| ハブ 1対1 | 軽い合図(「PR 出した」「受領」)・短期の調整 | 再起動で消える |
| ハブ全員宛て(broadcast) | 方針の周知・訂正の一斉通知 | 同上 |
| issue + ラベル | 人間の決定待ち・承認依頼 | 永続 + 監査可能 |
| PR コメント | レビューの議論 | 永続 |
| 記録ファイル | 教訓・パターン | 永続(ローカル) |

原則は2つ。**決定を短命な経路で仰がない**(消える上に、後から「誰が何を決めたか」を追えない)。**短期の状況報告を永続経路に書かない**(ノイズになる)。また「受領→ありがとう→どういたしまして」の連鎖は純粋な往復コストなので、能動的な調整(依頼・ブロック・修正要求)以外の合図は沈黙でよい。実測の契機は、リード役(複数のエージェントセッションを束ねる進行役)の受信箱に合図・状況・質問が混在して**480件**溜まったことだった。

## 2. 契約はハブ上で固定しない — issue に書いて参照させる

実測: 2つの実装セッション(書き側と読み側)のあいだのデータ形式の契約(合意すべきインターフェース仕様)を、ハブ越しに確定しようとした。仲裁役が軽微な2点で前言を翻し、複数の「これで最終」を送った。ハブには約30秒の配達遅れがあるため、各相手は「**最後に届いた版**」に応答し、互いに別の版を見て交錯し続け、収束しなかった。ハブは契約を保持できない — 短命で、届いた順がばらけ、正典(canonical = これが正しいと全員が参照する1箇所)を持たないからである。

- 契約は issue/PR コメントに**1箇所**で書き、「ハブ上の契約メッセージは(自分のものも含め)全て無効。差分の議論は issue で」と宣言する。ハブは「push した、レビューどうぞ」程度の短命な合図に戻す。
- **仲裁者は前言を翻さない**: 迷いながらの再決定は、一度の確定よりはるかに発散を増幅する。決めるなら中身で、一度だけ決める。
- **収束は追認する**: 実装者2人が独立に同じ健全な設計に至ったら、自分の(こね回した)版を押し付けず、彼らの到達点を追認する。目的は「正しい合意が1つあること」であって、自分の版が勝つことではない。
- トリガー: 同じ決定の**2度目**の「最終版」をハブに送りそうになったら、手を止めて issue に書く。

## 3. 待機はイベント駆動で — 暇な LLM を起こさない

エージェントに「新着を待たせる」構成は3種類あり、待機中のコストが桁で違う:

| 方式 | 待機中の LLM コスト | 適する場面 |
|---|---|---|
| OS レベルの監視プロセス(新着を検知したときだけエージェントを起こす) | **0**(OS の軽い確認だけ) | 受信箱の監視(常設) |
| 定周期の自己起床(タイマーで定期的にエージェントを起こす) | **起床のたびに発生** | 真に必要なときだけ・疎な周期(60分以上) |
| イベント駆動(相手の投函・報告が起点) | 0 | 相手の報告で構成できる全て |

なお表の1行目と3行目は、どちらも「新着が来たときだけエージェントを起こす」点は同じである — 1行目は、その仕組みを受信箱に対して常設で実現する機構だと考えればよい。定周期を選んでよいのは、① イベント駆動の経路が無く ② 周期確認そのものに運用価値があり ③ 疎な周期で足りる、の3条件が揃ったときだけである。実測の anti-pattern(避けるべき型): 4分間隔の自己起床ループは、イベント駆動の監視プロセス構成に比べて LLM コストが**7〜10倍**に累積した。

さらに強い規律が1つ(オーナー直接指示): **タスクが無い待機中(idle)に、受信箱の監視以外の自己起動ループを新設することを全面禁止**。待機とは「イベントで起こされるまで何もしない」受動形が正解であり、ポーリング(一定間隔で確認しに行く方式)や起床予約で自分を起こし続けない。なお、作業中の「CI(自動テスト)が終わったら自然に止まる監視」は idle ループではない — 禁止対象は、終わりのない自己再起動である。

## 4. 長い作業は背景で走らせる — 会話を塞がない

数秒で終わらない作業(テスト全実行・子エージェントの起動・ビルド)を foreground(前面 = 終わるまで他のことができない同期実行)で起動すると、完了までオーナーのメッセージにもハブにも応答できない。オーナーはこれを「フリーズ」と感じる — 実測では、無反応と感じたオーナーに作業をキャンセルされた。会話やハブに即応すべき役割は、長い作業を background(背景実行)で起動し、完了通知で続きを行う。

ただしこれは、[止まっているエージェントの見つけ方](stall-detection.ja.md)§1(死んだ背景ジョブ待ちが最頻の停止形)と**緊張関係**にある: 背景実行は会話を塞がないが、ジョブが黙って死ぬと停止の温床になる。両立の型は — (a) 走らせる前に commit する(死んでも作業は回収可能)、(b) 完了通知が来ないことを「まだ走っている」と読まず ps で実測する、(c) 全出力を読む必要のある検証の最終ランだけは、タイムアウトを明示した foreground で行う。

## 5. 「投函する」と書いたら、同じターンで投函する

「相手に通知予定」「受領を伝えて完了待ち」とターン末の要約に**書いた**のに、実際の投函をしていない — 述べることと実行することの分離は、自動化を静かに壊す。相手は「来るはずのメッセージ」を待つことすらできない(来ることを知らないので)。単に何も起きず、人間が「通知した?」と聞いて初めて発覚する。

実測は2連発である: 通知漏れをオーナーが発見して手動で回した(1件目)。**その教訓を記録した直後**、別のマージで同型の通知漏れ(2件目)— 記録は履行を担保しない。対策は言い回しの検知である:

- 「相手に X を通知」「受領を伝える」「依頼する」という句を自分の文章に書いた瞬間が、投函の実行を**同じターン内で**行う合図。「予定」の枠で文章にだけ残さない。
- マージは単独の動作ではなく複合動作である: マージの実行 + 作者への確認 + それを待っていた相手への着手通知 + 報告、を同じターンでまとめて行う。
- ターンを閉じる直前の自問: 「投函が必要な言及を書いたのに、投函していないものはないか」。

- [ ] 同じ決定の2度目の「最終版」を送りそうになっていないか。実装者の収束を追認したか
