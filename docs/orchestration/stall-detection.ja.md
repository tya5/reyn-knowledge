# 止まっているエージェントの見つけ方 — 沈黙・自称・機械申告

## 前提

複数のエージェントセッションを並行運用する(fleet)ときの中心的な運用問題は、**「止まっているのに動いて見える」と「動いているのに止まって見える」の両方が日常的に起きる**ことである。エージェントの沈黙は多義で、外形からは区別できない: 黙々と作業中 / LLM 応答待ち / 文脈圧縮(compaction = 長くなった会話履歴の要約処理)待ち / **死んだバックグラウンドジョブを待っている** / 本当に停止。この文書は、実測された停止の形と、それぞれの見分け方の規律である。

## 1. 最頻の停止形 — 死んだバックグラウンドジョブ待ち

**パターン**(1晩で6回発生した実測): 実装エージェントがフルテストスイートを**バックグラウンドで起動**し、**その完了通知を待つ形でターンを終える** → バックグラウンドのジョブが黙って死ぬ(または完了通知が届かない) → エージェントは「待機中」のまま、**未コミット・PR 未作成で無限に停止**する。

**検出は3点を同時に実測する**(推測しない):

1. open な PR に当該作業が**無い**
2. そのエージェントの worktree(専用の作業ツリー)で、未コミット差分が**有り**、新しい commit が**無い**
3. プロセステーブル(`ps`)に、待っているはずのテストプロセスが**無い**

3つ揃えば dead-job stall 確定。**待っているはずのテストプロセスが1本でも生きていれば正当に進行中**なので急かさない(実測で、生存1件のケースを急かさなかったのが正しかった)。

```bash
# 3点測定の例(<agent> は対象エージェント、<worktree> はその作業ツリー)
gh pr list --author <agent>            # 1. open な PR に当該作業が無いか
git -C <worktree> status --porcelain   # 2. 未コミット差分の有無
git -C <worktree> log --oneline -3     #    新しい commit の有無
ps aux | grep pytest                   # 3. 待っているはずのプロセスの生存
```

> **「通知が来ていない」は「まだ走っている」の証拠ではない。** 通知は producer(通知を生み出す側のプロセス)の出来事であり、producer が死ねば通知も来ない([生死は producer で判定する](../verification/liveness-is-producer.ja.md)の運用版)。
> 付記: **CPU 使用率はエージェント自身の生存指標にならない**(大半の時間は LLM 応答待ちで CPU をほぼ使わない)。エージェントは申告・push・メッセージで、**その子プロセスは ps で**見る — 別々の指標である。

**根本原因は「実行不能な指示」だったことが多い。** 「テストは foreground で走らせろ」と依頼文に毎回書いても止まらなかった理由: フルスイートの所要時間が**シェル実行の既定タイムアウトを超えており**、指示どおりに走らせると必ず打ち切られる — エージェントはバックグラウンドに逃げるしかなかった。∴ 予防は3点セットで依頼文に入れる:

1. **タイムアウトを明示**した foreground 実行(既定値では物理的に完走不能であることを伝える)
2. **スイートを走らせる前に作業を commit する**(commit-first) — これで停止しても作業は回収可能になり、stall が「破局」から「ひと声かければ済む事象」に格下げされる
3. **ターンを終えない・全出力を読む**(バックグラウンドで終えると「読む人が誰もいなくなる」— 実測では foreground で読み直したエージェントが本物の失敗を2件発見した。背景のまま終えていれば両方そのまま世に出ていた)

なお、この予防策を**記録した本人が10日後に、うち2点(タイムアウト明示の foreground・スイート前の commit)を依頼文に入れ忘れて同じ停止を3件再生産した**実測がある — 「対策を記録している」と「対策を適用している」は別の動作である([検証ナレッジの体系](../verification/index.ja.md)の横断原理4「注意力ではなく手順」の依頼側)。

## 2. 「実行中」の自称は、既知の所要時間と照合する

エージェントの「いま実行中です」という自己申告は、**そのタスクの既知の所要時間**と照合してから信じる。実測: 通常 3〜4分(当時の既知値)のスイートが**44分**「実行中」— これは「遅い」ではなく **hang**(実際に終了処理の永久待機バグだった)。なお正常値そのものは時期とともに変わる(同じスイートを別時点の記録は約4.5分としている)— 照合は絶対値ではなく**倍率**で行う。中継者は「生きているか(alive)」だけ確認して「**進んでいるか(progressing)**」を確認せず、「実行中なので順調」とオーナーに報告してしまった。

- 既知の所要時間の**数倍〜10倍**を超えた still-running は、slow ではなく hung として扱う([検証ラン自体の生存確認](../verification/verification-run-liveness.ja.md)がラン側の同じ規律)。
- 「running だから fine」と**そのまま中継しない**。

## 3. 沈黙の原因帰属 — 「詰まり」の前に疑うもの

- **文脈圧縮待ち**: モデル階層によっては、セッションが文脈圧縮の境界で停止し自動再開しない系がある。長い自律作業が無音化したら、コードの詰まりを推測する前に**まず圧縮待ちを疑う**(メッセージハブ = セッション間のメッセージ中継の上では active 表示・出力ゼロ・作業規模が大きい、という組み合わせが典型)。実測では 10 時間の無音を「実装で詰まっている」と誤帰属した。予防: **dispatch を圧縮境界を跨がない粒度に刻む**(多軸1PRより軸ごと別PR)。
- **push なしの黙々作業**: 直前まで活発に push していたセッションが沈黙したら、第一仮説は「**push せずに没頭している**」であって「死んだ」ではない — 実測で、25分の沈黙を再起動疑いでエスカレートしかけた相手は、実際にはレースバグを発見して修正中だった。nudge(軽い声かけ)を先に打ち、返答の時間を与える。
- **local-only commit の不可視性**: 相手は20分刻みで実装を続けていたのに、commit がローカルだけで push されず、外形上「42分無音」に見えた実測。予防は検知でなく**依頼時の要請**: 「区切りごとに incremental push + 一言 status」「重い作業は draft PR を早期に open」— これで偽 stall の誤認自体が消える。

## 4. 機械申告と推論を分ける — stall/idle は「セッションの自己申告」が単一の真実源

> **watcher(監視側)が「N 分 post が無い = idle」と推論してはならない。** 外部からは「長い正しい計算で静かなだけ」「本当に停止」「人間待ち」を区別できない — 自分の内部状態を知るのはセッションだけである。∴ idle/active は**セッション自身が停止フック(ターン終了時に自動実行される処理)で機械的に申告**し、watcher はその申告を購読する。

運用の要点(すべて実測由来):

- **両エッジ(開始と停止の両側の合図)が要る**: 停止時の idle 申告だけでは「一度 idle と言ったきり永遠に idle に見える」片道の罠になる。作業開始時の active 申告(ターン開始側のフックで)と対にする。
- **機械軸と意味軸を別フィールドに**: 機械申告(active: bool)と LLM が書く意味的な状態文字列(「CI 待ち」等)を1つのフィールドに相乗りさせると、片方が片方を上書きする。bool は決定論の権威、文字列は任意のヒント。
- **同一の状態文字列の繰り返しは、活動の証拠ではなく staleness(情報が古くなっていること)のシグナル**である(状態文字列は自動更新されない — 切断したセッションも最後の言葉を表示し続ける)。数回同じ文字列を見たら、**active フラグを直接確認する**。実測: 同一文字列を理由に数十件の idle イベントを握り潰し、直接確認したら active=false だった。
- **escalation-for-verification は禁止された推論ではない**: watcher は機械的に idle を検出してリードに上げ、**リードが verify する**(完了か停止かの判定は上げた先の仕事 — §1 の3点測定は、まさにこの verify 段でリードが実行する手順である)。「watcher が stall を断定するな」と「候補をエスカレートするな」を混同しない。
- **「全員 idle のときだけ発火」のゲートは、個別セッションの作業途中 idle を見逃す**(実測: 5段中1段だけ push して切れたセッションを70分見逃した)。停止時の申告に「作業途中(WIP 継続)」とあれば単独でも alert、「依存待ち(X を待って待機)」は正当として抑制 — 申告テキストでこの2つを区別させる。

## 5. dispatch = motion と仮定しない — fan-out と fan-in は対

fan-out(複数の相手へ依頼を配る動き)と fan-in(その結果を回収して確認する動き)は対である — 配ったら、回収するまでが依頼である。「依頼を出した = 動いている」は仮定にすぎない。実測では、依頼への ack(受領応答)後の無言停止を「実装中のはず」と報告し続け、オーナーが同一セッション内で3〜4回 stall 検出係をやらされた。

- dispatch 直後は **pickup(着手シグナル)を確認**する。ack だけで「動いている」としない。
- しばらく無音なら、**PR / リモート branch / 最終活動時刻を自分で実測**してから状態を報告する。報告は「実装中のはず」ではなく「**最終活動 HH:MM、PR 未着 = 進捗未確認**」という verified fact で書く。
- **STOP はタスク単位で**: 1つのタスクを gate するとき、その相手の**他の unblocked なタスクまで止めない**(session 単位の STOP が、独立タスクを持つ相手を丸ごと idle 化させた実測)。完全 idle を許すのは全タスクが blocked/done のときだけ。
- **偽 stall の一種は自分の送信文**: plan-first(承認を待ってから動く方針)の相手に、GO を「推奨します」調で書くと、相手は正しく待つ。stall と断定する前に、自分の直前の送信が soft でなかったかを疑う。
