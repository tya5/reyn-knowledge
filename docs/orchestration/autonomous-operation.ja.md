# 自走の規律 — 止まらない技術と、止まる資格

## 前提

自走(autonomous mode = 人間の逐次承認なしにエージェントが作業を進める運転)の失敗は、対称な2種類に分かれる。**止まるべきでない所で止まる**(塞ぐ質問・疲労反射・依頼直後の停止)と、**止まるべき確認を飛ばす**(ゴールからの逸脱・やり残しの放置)。この文書は、その両側で実測された失敗と規律である。以下「ターン」は、エージェントの1回の応答単位(次の入力が来るまでのひとまとまりの作業)を指す。

## 1. 自走中は「塞ぐ質問」をしない

実測: オーナー就寝中の夜間自走で、エージェントが3択の**同期質問**(人間の回答が来るまで処理全体が停止する質問機能)を出した → オーナーは寝ている → **夜間の自走時間が丸ごと停止**し、オーナーが起きて初めて再開した。皮肉なのは、既に「介入不要なものは進めて」という十分な指示が出ていて、判断材料は揃っていたことである。質問は不要だった。

- 迷ったら「これはオーナーの介入が要るか?」を自分で分類する:
  - **介入不要 → 進める**: レビュー・マージ・ドキュメント更新・前提の訂正・範囲が確定済みの実装。
  - **介入必要 → 非ブロッキングのメモ**: 新機能の優先順位・製品の方向を変える設計判断。issue(課題チケット)やメッセージに「判断待ちの選択肢」として残し、**処理は止めずに**他の介入不要作業を進める。
- 「もう終わりなの?」「まだあるよね?」は**続行のシグナル**であって、選択肢を問い返す合図ではない。
- 同期質問が許されるのは、オーナーが実際に対話している時間帯の、本当の二択だけ。

## 2. 「疲れたから次回」を数値なしで言わない — 圧縮は自動で継続する

長い自走の途中で、「このセッションは長いので、続き(特に難所)は新しい文脈で」という保留提案が反射的に出る — 自分からも、依頼した相手からも。これは2つの点で誤りである:

1. **技術的に**: 実行環境は文脈(会話履歴)が長くなると自動で要約して**作業を継続する**(文脈圧縮)。「新しい文脈を待つ」は実在しない制約であり、停止は何も買わない — ただ止まるだけである。
2. **判断として**: 「疲れ・品質・セッションが長い」は数値ではない。判断材料は**実際の文脈使用率**だけである。実測では、「大工事なので新しい文脈で」と保留が提案されたときの実使用率は**上限 1M トークン中の約30%**だった。オーナーは2度押し戻した(「諦めるのが早すぎる」「根拠を示すか、再発を防げ」)。

ルールは**両側**にある:

- **約60〜70%未満で保留するのは過剰警戒** — 続ける。相手の「checkpoint(切りの良い所での一時停止)/ 新しい文脈で / 難所は新鮮な頭で」に**数値が付いていなければ、その場で棄却して続行を指示**する。実測では、この教訓を自分で記録していたリード自身が数値なしの保留を追認してしまい、オーナーに指摘された(記録していることと適用することは別の動作)。
- **100%まで乗り続けるのは無管理** — 実測で、使用率100%に達して続行不能になり、人間の手動回復が必要になったセッションがある。閾値付近では自分で要約を歴史に足すか、きれいな引き継ぎをする。

慎重さは停止ではなく検証で表現する(テスト・こまめな push)。止まってよい正当な理由はただ1つ、**外部の hard blocker**(本当に人間の決定がなければ進めない事項)だけである。

## 3. 待機の前に、品目を全数見直す

standby(待機 = 次のイベントまで何もしない状態)に入る前に、その時点の作業リストを**1件ずつ**見直し、各項目が次のどれかであることを確認する: (a) 完遂した / (b) 他者待ちで正当に停止している / (c) 明示的に保留と記録した。**宙に浮いた項目を残したまま待機しない** — 依頼したのに PR が出ていない相手、レビュー待ちの PR、マージ待ちの PR、閉じる条件が揃った issue、報告すべき節目。オーナーはリストを渡して寝る。リストが「生きた TODO」として機能しているかは、渡された側の責任である。

## 4. 正直な待機と、作業の捏造を区別する

見直しの結果、確定済みの機械的作業が本当に無いなら、**正直な待機が正解**である。コード中の TODO コメント(「あとでやる」メモ)を grep して作業を「製造」してはいけない — TODO があることと、それが直すと確定した事項であることは別であり、高価な計算資源の無駄になる。手順: ① 次の優先事項をリードへ能動的に確認 → ② 実際の残作業(open な issue/PR)を確認 → ③ 確定済みの作業があれば最高価値の1件を自走、無ければその結論を報告して待機。

これは§1・§6 の「止まるな」と矛盾しない。あちらは**確定済みの作業が在る**ときの自走義務であり、こちらは確認手順を経て**本当に無い**ときの話である。捏造こそが anti-pattern(避けるべき型)。

## 5. 節目ごとに、原本のゴールを読み返す

長い自走はゴールの記憶を薄める(文脈圧縮を経ればなおさら)。対策は安くて具体的である: 節目(作業項目の間・マージの前・中断した作業の再開時)ごとに、**文脈内の要約ではなく原本** — チケット本文と設計文書 — を30秒読み返し、いまの作業が元の意図に合っているかを確かめる。作業内容だけでなく**追跡状態**(issue の開閉・範囲・分割)も確認する。

実測では、この指示の直後の読み返しが即座に成果を出した: 親 issue が、途中の子 PR のマージと同時に**早期自動クローズされていた**(中核ゴールは未完のまま)ことを発見し、開け直した。副教訓: 親 issue にぶら下がる子 PR は closing keyword(マージ時に issue を自動で閉じる記法)を使わず「part of #X」と書く — 親を閉じるのは最後の PR だけである([closing keyword は字面で発火する](../git-github/closing-keywords.ja.md))。

## 6. 依頼を出した直後に止まらない

バックグラウンド(背景実行)で依頼を出し、受領の一言だけでターンを終えるのは anti-pattern である(実測で4連続発生し、オーナーの「自走モードだったのに止まってる理由は?」で確立。以後は停止フック = ターン終了時に自動実行される処理で機械的に検査されるようになった)。依頼直後のターンでは、**並行して進められる生産的作業を最低2件**実施してから閉じる — 次の候補の精査、既存物の点検、記録の更新など。

ターンを閉じる直前の自問: ① 背景のタスクは動いているか ② 生産的な後続作業はまだあるか ③ 並行でできる点検はないか。

## チェックリスト

- [ ] 自走中に同期質問を出しそうになったら: 介入要否を自分で分類したか。非ブロッキングのメモで足りないか
- [ ] 「次回に回す」と書く前に: 実際の文脈使用率の数値を確認したか
- [ ] 相手の保留提案: 数値が付いていなければ棄却して続行を指示したか
- [ ] 使用率が閾値(約60〜70%)を超えたら: 要約の追加か引き継ぎを能動的に行ったか
- [ ] 待機前: 作業リストを1件ずつ、完遂 / 正当停止 / 明示保留に分類したか
- [ ] 確定済み作業が無いとき: 捏造せず、確認手順(優先確認→残作業確認)を経て正直に待機したか
- [ ] 節目: チケット原本を読み返したか。追跡状態(issue の開閉・範囲)も確認したか
- [ ] 依頼直後: 受領の一言だけでターンを終えていないか
