# 緑を読む技術 — 何が走ったか・どのコードか・本当に終わったか

## 中心命題

> **「テストが緑」は「走ったものは全部緑だった」としか言っていない。何が走ったかについては何も言っていない。skip(実行を飛ばされたテスト)は緑に見える。**

∴ `rc=0`(終了コード 0)や「8686 passed」は、**特定の主張が witness された証拠にならない**。読むべきは合格数ではなく **skip の一覧**である。

## 実例 — 「あなたの rc=0 が反証です」と言った側が間違っていた

同じ PR に対して2人の検証者が報告した(検証環境では docker デーモンが落ちていた):

- 検証者A: 「**2 failed**(docker の統合テスト)」— 正直に「裏は取れたが直接の反証はできていない」と付記
- 検証者B: 「**rc=0 / 8686 passed / 19 skipped**。私も独立には反証できなかった」

これを読んだレビュアーが、Bに向かって「**あなた自身の rc=0 が、あなたができなかったと言う反証そのものだ** — 同じコードで失敗ゼロなのだから、コードは変数ではない」と講釈した。Bが `pytest -rs`(skip の理由を表示するオプション)で実測して反論した:

```
SKIPPED test_devcontainer_build_e2e.py:72 : no reachable Docker daemon
SKIPPED test_mount_e2e.py:121/131/150/172/181 : 同上
```

> **「私の rc=0 は『docker ビルドが通った』ではない — 『docker ビルドは一度も走らなかった』である。」**

AとBは、**同じテストの別の分岐**を通っていた(A = 実ビルド分岐、B = skip 分岐)。∴ **Bの緑はAの赤を反証できない**。「コードが同一だからコードは変数ではない」は真だが、「Bの環境でビルドが走った」を含意しない — 変数はデーモンの生死で、Bの環境ではテストが**実行されなかった**のだ。

この誤りの一番鋭い部分: レビュアーは「自分の証拠を読め」と相手に説教している**まさにそのメッセージの中で**、合格数だけを数え、**19 という数字を一度も見なかった**。

## 規律

- スイート結果をある主張の証拠として引用する前に問う: **「その主張を witness するはずのテストは、実際に実行されたか?」** `-rs` で skip 理由を出すか、そのテストを名指しで単独実行する。
- 報告する側・させる側の規律: **「何が skip されたか」を合格数と一緒に報告する**。裸の `rc=0` は反証不能な報告で、「19 skipped: <理由>」は判断を支える報告である。
- **緑の環境が2つあっても、どちらも当該分岐を走らせていなければ、証人は0人である。**

## 健全な skip — 「眠った仕掛け線」

すべての skip が盲点なのではない。健全な skip を見分ける2つの検査:

1. **skip の理由は具体的か(legible)。**「未対応」ではなく、欠けている当のもの(「この OS には機構 X が無い」)を名指ししているか。
2. **到達不能は本物か。** 本当に対象が存在しないのか、それとも対象は在るのにテストハーネスが届いていないだけか(後者の実例: production の入口を迂回していたテストが**41日間**「通って」いた)。

両方を満たす skip は**眠った仕掛け線(dormant tripwire)**である — 対象の機構がその環境に現れた瞬間、skip が実行に変わり、壊れていれば RED を出す。**これは TODO コメントより厳密に良い**。読まれることを祈る記述ではなく、発火が予定された機構だからだ。

## 第2層 — その緑は「どのコード」についての緑か

緑/赤の意味は、**測った対象が走る対象と同一**であることを前提にする。この前提は両方向に壊れる(同じ夜に2人が逆側から落ちた実例がある):

- **false-negative**: 仮想環境が同期されておらず、直したはずのコードの**古い版**を測って「まだ FAIL」と誤認。
- **false-positive**: strip 反証を**親プロセスへの monkeypatch**で実施したが、機構は必ず**新しいサブプロセス**で走る設計だった。パッチは届かず、**何も変更していないコードを測って「strip しても緑 = 修正が効いている」**と読める状態になっていた(気づけたのは「strip したのに緑」が説明できなかったから。実ソースを書き換えて測り直したら5件 RED)。

> **緑/赤を読む前に、「これはどのコードについての緑/赤か」を先に確定する。** サブプロセス境界・仮想環境・PYTHONPATH・import 経路は、全部この穴の入口である。

([strip 計測器自体の健全性](strip-instrument-integrity.ja.md)の壊れ方3はこの規律の venv 版。)

付随して: **grep は「散文の中の墓標」と「生きた呼び出し」を区別しない**。「この API はもう呼ばれていない」の確認は文字列の有無ではなく AST(構文木)で行う — 上の41日事件を作ったのは、まさに「文字列がそこに在る」と「そこでコードが走る」の取り違えだった。

## 第3層 — 「正常に終わった」も検証対象の主張である

終了コード 0 + stderr が空、は「例外なく完走した」を意味しない。**例外が途中で握り潰されている**可能性がある。LLM を呼ぶループでの診断シグネチャが分かりやすい:

> **リクエスト記録数 = レスポンス記録数 + 1、かつ rc=0、かつ stderr が空、かつエージェントは作業の途中で止まっている = ループ経路で例外が飲み込まれた。正常終了ではない。**

なぜこの形になるか: リクエストは API 呼び出しの**前**に記録され、レスポンスは**後**に記録される。その間で raise すればリクエストだけが残る。特定の手順も単純で、(1) 例外を飲むハンドラ(`except Exception`)に一時的に traceback 出力を仕込む、(2) 再実行して実際の例外を取得、(3) 修正後に仕込みを外す。

短い実行・途中終了を「モデルの能力」「タイムアウト」に帰責する前に、**リクエスト対レスポンスの数を数える**。

## チェックリスト

- [ ] スイート結果を引用する前に: 当該の witness テストは実行されたか(`-rs` / 単独実行)
- [ ] 報告に skip の一覧と理由は付いているか。裸の rc=0 を証拠扱いしていないか
- [ ] skip を見たら: 理由は具体的か、到達不能は本物か(眠った仕掛け線か、盲点か)
- [ ] 緑/赤を読む前に: どのコードについての緑/赤か(venv・サブプロセス・import 経路)
- [ ] 「正常終了」を信じる前に: 途中で例外が飲まれた形跡はないか(req/resp カウント)

## 出典(reyn 開発での実測)

skip は緑: #2994(docker デーモン停止下の rc=0 を「反証」と誤読、`-rs` で 19 skips が全部 docker と判明)。健全な skip の判別: #3019。41日間の素通り: #2980。測定対象の同一性: #3031(親プロセス patch の false-positive)と同夜の venv 未同期(false-negative)。飲み込まれた例外: #187/#1413(`response.choices[0]` が空応答で IndexError → ループ全体が無音で死ぬ → retry + 明示エラー化で修正)。
