# strip 反証の規律 — RED 報告を証拠に変える4つの軸

## strip 反証とは

**strip 反証(strip-falsify)**とは、「テストが本当にその機構を守っているか」を確かめる手順である。やることは単純で、**守られているはずの機構を一時的に消して(strip)、テストが落ちる(RED になる)ことを確認する**。テストが緑(GREEN)のままなら、そのテストは機構を守っていない。

まず最小の例から。アップロードされたファイルが 1MB を超えたら拒否する関数があるとする:

```python
MAX_BYTES = 1_000_000

def save_upload(data: bytes) -> str:
    if len(data) > MAX_BYTES:          # ← このガードを守りたい
        raise ValueError("too large")
    return store(data)
```

これに対して、次のテストは一見まともだが**ガードを守っていない**:

```python
def test_save_upload():
    assert save_upload(b"hello") == "stored"   # 小さいファイルが通ることしか見ていない
```

確かめ方が strip 反証である。`if len(data) > MAX_BYTES:` の if 行と raise 行の2行を消してテストを回す。**全部緑のまま通る。** つまり、将来誰かがこのガードを誤って消しても、CI は何も教えてくれない。守るテストはこうなる:

```python
def test_save_upload_rejects_large_file():
    with pytest.raises(ValueError):
        save_upload(b"x" * (MAX_BYTES + 1))    # ガードを消すと、この行で例外が出ず RED になる
```

ここまでは教科書どおりだ。問題は、この手順を実務(特に AI コーディングエージェントが実装とテストの両方を書く環境)で回すと、**「strip して RED を確認しました」という報告自体が壊れている**ケースが繰り返し出ることである。壊れ方は4つの軸に整理できる。

## 軸1 — いくつ strip したか(兄弟サイトの網羅)

同じガードが **N 箇所**に適用されているとき、実装者は代表の1箇所だけ strip して「RED 確認済み」と報告しがちである。

例: 上の 1MB チェックが「Webフォーム経由」「API 経由」「バッチ取り込み経由」の3箇所に入っているとする。テストは Webフォーム経路だけを叩いている。このとき API 側のチェックを strip しても**緑のまま**である(green-on-strip)。将来の編集で API 側のガードが消えても誰も気づかない。

- **ガードの適用サイトを全部列挙する**(ヘルパー関数・フィールド・該当行を grep する)。そのうえで**各サイトの strip が RED になる**ことを確認する。
- 基準は「機構が witness されている」ではなく「**機構に依存する全サイトが witness されている**」。1箇所の RED + 残り N−1 箇所の「コードはある」では不完全。

> **用語**: witness(証人)= その性質が壊れたときに RED になるテストのこと。「witness がある」=「壊すと検知される」。assert(表明)= テストコード内の検査式のことで、成立しなければテストは失敗する。

## 軸2 — 何を壊したか(最小破壊)

「元のコードに戻したら RED になりました」は、**複数の性質を同時に壊している**ので何も切り分けられない。

例: ある PR(プルリクエスト = 一まとまりの変更提案)が (a) ファイル名のエスケープ処理を追加し、(b) 古い「`__` を含むパスを拒否する」バリデーション(入力検査)を削除したとする。実装者が「PR 全体を差し戻し(revert)たら RED になった」と報告してきた。しかしその RED は、差し戻しで復活した (b) のバリデーションが例外を出しただけかもしれない。**PR が本当に守りたかった性質(エスケープによる衝突回避)にテストが反応した証拠にはならない。**

- 基準は「**守るべき単一の性質を、それだけ単独で壊して、RED になるか**」。この例なら「エスケープ処理だけを外し、バリデーション削除はそのまま」という、将来の編集が実際に作りそうな**最も危険な中間状態**を作って RED を見る。
- 依頼するときは破壊対象を名指しする。「fix を strip せよ」ではなく「**エスケープ処理だけを外せ、他は残せ**」。strip が「PR の取り消し」に近いほど証明力は下がる。

## 軸3 — strip は当たったか。緑だったら理由を詰めたか

軸1・軸2は「strip が成立した」ことを暗黙の前提にしている。その前提自体がよく壊れる。実際に1つの検証で3連続した実例がある:

1. sed(文字列置換コマンド)で置換したつもりが**パターンが当たらず置換件数 0**(applied=0) — 何も実験していない。
2. やり直したら**構文エラー**を作って RED — この RED は「機構を壊した」ではなく「**実験装置を壊した**」。
3. 3度目でようやく strip が当たったら、今度は**緑**だった。

そして 3. の緑を「このガードは不要だった」と読むのは早い。**緑には少なくとも3つの意味がある**:

1. ガードが本当に不要。
2. **別のガードに包含されている。** 例: `effective = min(a, b)` という式の下流では、`b <= 0` のチェックは `effective <= 0` のチェックに常に含まれ、単独で RED を出す入力が**原理的に作れない**ことがある。この場合「包含による被覆であり、witness 漏れではない」と**コードに書き残す**。書かないと、次の人が存在しない witness 漏れを直しに来る。
3. **strip が当たっていない / 別の理由で壊れた**(実験不成立、上の 1. 2. と同じ)。

- 依頼には「RED を確認せよ」だけでなく、**「置換が実際に適用されたことを確認せよ(差分か置換件数を出せ)」「緑だったら報告せよ。緑は結論ではなく次の問いだ」**まで書く。「緑でした、効いていないようです」で止めさせない。

## 軸4 — 機構を丸ごと殺したら RED になるか

**軸1〜3をすべて満たしても、機構全体としては何も守られていないことがある。** 個別の strip は「その行が効いている」を示すが、「機構が仕事をしている」ことは示さない。

実例(一般化): 計算結果をチェックポイント(途中保存)に残し、次回は差分だけ再計算する高速化機構。実装者は5箇所を個別に strip し、置換件数まで確認して各 RED を報告した(軸1〜3クリア)。ところがレビュー側が**機構全体を `if False` で殺したら、テストは7本全部緑のまま**だった。

なぜか。テストが assert していたのは「最終的な計算結果が正しい」ことで、それは**チェックポイントが死んで全再計算にフォールバックした世界でも同じ値**になる。判別式はこうなる:

> **witness は「死んだ機構には作れない値」を assert していなければ空虚(vacuous)である。**

フォールバック(fallback = 本来の機構が使えないときの代替動作。全再計算・デフォルト値・復旧パスなど)の結果を assert するテストは、構造的にこの罠に嵌る。フォールバック側を assert する腕(arm = 対で書くテストケースの片側)は、必ず「**機構が生きているときにしか出ない値**」(例: 再計算回数が 0 回であること、キャッシュヒットのカウンタ)を assert する腕と対にする。

- 復旧処理・フォールバック・キャッシュ・高速路のような「**壊れても動く**」設計では、必ず機構丸ごと殺し(no-op〈何もしない処理〉化、`if False`)を実施して RED を確認する。
- 「個別の差し戻し(revert)で RED」は「丸ごと殺しで RED」の代わりにならない。前者が全部成立していても後者が緑だった実例が上のケースである。

## 派生 — 上限・しきい値(bound / cap / threshold)のテストは反転(flip)しなければならない

上限・打ち切り・しきい値を導入する変更は、正常系(happy-path = うまくいくケースだけを通す流れ)のテストを書くと**上限を外した実装でも同じ assert が通ってしまう**ことが多い。

例: 「バージョンファイルは先頭 4KB だけ読む」という読み取り上限を入れたとする。

```python
# ダメなテスト: 「先頭にトークン + 後ろに 8MB のゴミ」
write_file("3.12.7\n" + "x" * 8_000_000)
assert resolve_version() == "3.12.7"   # 無制限 read でも先頭のトークンは取れる → 両実装で緑
```

正しい構成は、**トークンを上限の外側に押し出して、assert が両実装で反転する**形:

```python
# 良いテスト: 空白 5000 文字でトークンを 4KB 境界の外へ
write_file(" " * 5000 + "3.12.7\n")
assert resolve_version() is None       # 上限あり: トークンが見えず代替動作へ → 緑
                                       # 上限なし: "3.12.7" を見つけてしまう → RED
```

push 前に実際に cap を外して(上限の定数を巨大な値に差し替えて事実上無効化して)RED を再現しておく。

## チェックリスト(依頼時・レビュー時)

- [ ] ガードの適用サイトを列挙したか。各サイトの strip が RED か(軸1)
- [ ] 壊したのは守りたい性質「だけ」か。最も危険な中間状態を作ったか(軸2)
- [ ] strip は当たったか(置換件数・差分)。緑なら3分類のどれか特定したか(軸3)
- [ ] 機構丸ごと殺しで RED か。フォールバックを assert する腕に対の腕はあるか(軸4)
- [ ] 上限・しきい値系なら assert は両実装で反転するか
