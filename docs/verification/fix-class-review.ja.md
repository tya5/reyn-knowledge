# fix-class レビュー — 「壊さないか」と「同病はいないか」は別の問い

## 2つのフレーム

パフォーマンス修正(あるいは何らかの「病理」の除去)をレビューするとき、頭の中のフレームには2種類ある:

- **correctness(正しさ)フレーム**(既定の見方): 「この変更は他の呼び出し元を**壊さないか**?」→ 共有関数は1バイトも変わっていない → 影響なし → **通過**。
- **fix-class(同類の欠陥群)フレーム**(病理の除去で本当に要るもの): 「他の呼び出し元は、この修正が取り除いている**のと同じ病理を持っていないか**?」

前者は正しく答えても、後者には何も答えていない。そして**レビューはデフォルトで前者しか問わない**。これが、修正と同型の欠陥(fix-class の兄弟)がレビューを通過して生き残るメカニズムである。

実例(3つの PR を要した): メッセージ処理のたびにログ全体を再走査していた箇所を、「述語(条件判定の関数)を1回構築して使い回す」ヘルパーの導入で修正した。レビュアーは2人とも通過させた。片方は**自分の事前調査で兄弟の呼び出し元を列挙までしていた**のに、「共有関数は変わっていないから呼び出し元は影響を受けない」— correctness の問いへの**正しい答え** — で棄却した。結果、**7つの兄弟サイトが生き残った**。うち1つはコールドスタート(起動直後の初回処理)経路の O(n²)(ログ長の2乗に比例する処理)で、開発環境のログが14行しかないため局所測定では見えなかった。

## 行動につながる兆候 — 新しいヘルパーが1箇所にだけ適用されている

> **修正が共通化プリミティブ(hoist/dedup = 重複した処理を一箇所に括り出す部品)を新設し、それを1箇所にしか適用していないなら、そのプリミティブの存在自体が「病理はクラスである」ことの証拠である。**

誰も、呼び出し元が1つしかない処理のためにヘルパーを抽出しない。抽出した手が「他にも同じ形がある」と知っている。レビューで即座に問う: **「他に誰がこの形を持っているか?」**

そして列挙の権威は **grep** に置く。著者の申告リストではない。実例では、依頼文に書かれていた対象サイトは**全部間違っており**、実装者の grep が依頼文に無い7サイトを見つけた。([列挙の規律](enumeration-discipline.ja.md))

## 根拠の検査 — その「安全」は census ではないか

兄弟サイトを「ここは安全」と除外する根拠は、たいてい census 型である(「このサイトの呼び出し元はループしない」— 今日は真、明日は黙って偽)。もともとの病理自体が、まさにそうやって育った実例がある: ログを引数に取って内部で再走査する API に対して、**後から**ループする呼び出し元が生えたのだ。

- **API の形が病理を強制するなら、呼び出し元側の修正では閉じない。形を変える**(ログではなく述語を渡す)。
- **「鏡像ペア」を片方だけ直さない。** 自称ミラーの片方だけ対称化すると、残った古い対称性 docstring が「この2つは同一のはずだ — ログを引き直そう」と**欠陥の再導入を積極的に主張する**ようになる。

根拠の census/structural 判別そのものは[census と structure](census-vs-structure.ja.md)を参照。

## チェックリスト

- [ ] この修正は何の病理を取り除いているか、一文で言えるか
- [ ] correctness の問い(壊さないか)**とは別に**、fix-class の問い(同病はいないか)を発したか
- [ ] 新設ヘルパーが1箇所適用なら、「他に誰がこの形を持つか」を grep で列挙したか(著者リストを信用しない)
- [ ] 「ここは安全」の根拠は structural か。「今日の呼び出し元がそうしていない」だけではないか
- [ ] API の形自体が病理を強制していないか。鏡像ペアの片割れを残していないか
