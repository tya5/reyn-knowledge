# 正常系の外を踏む — エラー経路・実行時入力・画面全体

## 問題の形

PR(pull request)レビューの既定の注意は「正常系(happy-path)が正しく動くか」と「構造が正しいか(参照切れ・命名・置き忘れがないか)」に向かう。その外側に、2種類の定番の死角がある。**どちらも、単体テストと静的レビューの両方をすり抜け、実際の使用(live / dogfood。dogfood は自分たちの製品を自分たちで日常利用すること)で捕まった**実測がある。

## 死角1 — エラー経路と実行時入力

レビューで明示的に問うべき3つの質問:

1. **この変更の失敗経路はどうなるか?**
2. **実行時に不正な・古い・想定外の入力が来たらどうなるか?** — AI エージェント環境では特に「**弱いモデル(能力の低い LLM)が変な値を書いてきたら**」が現実の入力クラスである
3. **端末・画面を所有する UI なら、エラー時に何が漏れるか?**

実例1(実行時入力): 状態語彙のリネーム(completed → done)で、読む側・比較する側の全数監査は行われた。見落とされたのは**書く側の制約** — モデル(LLM)から直接呼び出せる更新操作の status 引数が**制約なしの文字列**のままだったこと。実行時に(リネームを知らない)弱いモデルが旧語彙 "completed" を書き込み、不正な旧語彙はそのまま保存され、後からそれを読み取る検証が例外を投げる — データ破損として表面化した。

> **語彙・形式の変更で消費者を監査するときは、読む/比較する側だけでなく、入力/書き込み制約の側も含める。**

実例2(エラー経路): 全画面 UI からインライン UI への切り替えで、削除の完全性(参照切れが残っていないか)の監査は行われた。見落とされたのは**インライン UI も端末を所有している**という挙動面 — エラー時にロガーの出力が UI に漏れて画面を壊す。正常系の端から端までのテストは緑で、エラー経路は誰も踏んでいなかった。

## 死角2 — 画面のうち、機能以外の全部

UI の実機確認(スクリーンショット・端末キャプチャ)を検証・レビューするときの注意は、**検証対象の機能に吸い付けられる**。しかしキャプチャには**画面の全状態**が写っている。周辺の退行 — 出るはずの行が出ていない、ずれた行、古い表示 — は、**見えるところに写ったまま、観測されない**。

実例: インライン UI が**ユーザー自身の入力を一度も画面に残していなかった**(エージェントの返答とツール行(ツール実行を表す表示行)だけが描画されていた)。このバグは検証者自身のキャプチャに**写っていた**(会話に `>` のユーザー行が1つも無い)。検証者は検証対象の機能(巻き戻し選択メニュー)を確認し、レビュアーも機能の正しさをレビューし、**2人とも周辺フレームの欠落を見なかった**。捕まえたのは実際に使ったオーナー(実際の利用者でもある管理者)である。

> **キャプチャの検証は2パスで行う: (1) 検証対象の機能は正しいか。(2) フレーム全体を走査して、「画面に在るべきなのに無いものは何か?」を明示的に問う。**

「自分の機能は動いたか?」と「この画面は完全で一貫した状態か?」は別の問いで、前者だけが自然に発火する。会話は完結した筋として読めるか(ユーザー行とエージェント行の両方があるか)、期待される行・マーカー・表示は揃っているか。

## 死角3 — 機構の witness を、見た目の witness と取り違える

実機での UI 変更確認には、もう1段深い罠がある。「機構が画面まで届いた」ことの witness(検査対象の性質が壊れたら失敗になる検査)と、「その結果がどう見えるか」の witness は**別の主張**であり、前者は後者を含意しない。

実例: 検索ヒットとキーボードカーソルの行を、背景色では生き残らない(コンポーネントのスタイル合成に負ける)という理由で反転表示(色を反転させる ANSI 装飾)で目立たせた。実機でのキャプチャ検証は「その ANSI コードが行に乗っているか」を確認し、確かに乗っていた — **だが結果は間違っていた**。明るい背景色を暗いパレットの上で反転させると、ほぼ白一色の帯がダークテーマ全体を貫き、実際に使ったオーナーの評価は「白背景になって気持ち悪い、洗練されていたデザインを壊している」だった。

検証者自身の分析: 「ANSI コードがその行に生き残るか」と「フォーカスが動かないか」は**機能**の witness であって、**見た目**の witness ではない。「実機で確認した(witness 済み)」という報告を受けたとき、レビュー側が確かめるべきは**何を witness したか**である。判別子はこうなる:

> **その witness は「機構が発火した証拠」か、それとも「人が受け取るものの証拠」か。** データが正しい経路を通った・ANSI コードが乗っている・フォーカス位置が変わっていない、は前者。ラベルが実際に描画されているか・帯がどう見えるか・要素が正しく消えるか、は後者。**前者だけを確認した UI 変更は、常に後者を確認し損なう。**

見た目を判定できるのは実際に画面を見た人間(この場合はオーナー)だけであり、機構だけを見られる立場(コードレビュー・自動キャプチャの解析)からは、見た目の良否は原理的に判定できない。とれる態度は「判定を代行しようとせず、見せる」ことである。

- **見た目が変わる変更は、機能が変わる変更と同格の承認ゲート対象にする**: 承認前のチェックリストに、見た目の項目を**未チェックのまま**残し、実際に見る人の判断を待つ。
- **「実機で確認済み」を受け取ったら、何を確認したかを聞く**: ANSI コードの生存・フォーカスの不動は機能の確認であって、見た目の確認ではない。
- **before/after の比較を要求する**: 見た目の変更には、変更前後のスクリーンショットか実機での確認依頼を求める。
- **付随して現れやすい罠 — 「正しく現れる」だけでなく「正しく消える」も見る**: ある装飾を導入した後、その要素の対象から外れた後も画面に残り続ける(視覚的なノイズとして居座る)ことがある。見た目の変更は、1つ直すたびに次の見え方の問題を生むので、**変更後の状態を実際に見せるまで完結しない**。

なお、端末の生出力(display)自体が信頼できないことがある(色コードの混入・行の割り込み・幅崩れ)。そのときは grep や画面表示をそのまま信じず、**ファイルに書き出してから読む**か、**構造化データ(JSON 等)に出してから解析する**ことで実体を確認する — 表示層のノイズを経由しない、地に足の着いた確認である。

## live / dogfood は補完であって冗長ではない

上の実例はすべて「単体テスト + 静的レビュー = 緑、実使用で発覚」だった。実際の使用による検証は、機能単位の検証と**別の軸**を持つ(全体験・エラー経路・実データ)。正常系の端から端まで緑を「検証完了」と読まない。

## 実践方法

- [ ] レビューで3問を発したか: 失敗経路は? 実行時の不正入力は(弱いモデル含む)? エラー時に画面へ何が漏れる?
- [ ] 語彙・形式変更の消費者監査に、書き込み側の制約(入力バリデーション)を含めたか
- [ ] UI キャプチャは2パスで見たか(機能 + フレーム全体の「無いもの探し」)
- [ ] 見た目の変更を「実機で確認済み」で通す前に、何を witness したか(機構か見た目か)を確認したか。見た目の項目を未チェックのまま承認ゲートに残したか
- [ ] 端末出力が信頼できないとき、grep/表示をそのまま信じず、ファイル書き出し+読み込みか構造化データでの確認に切り替えたか
- [ ] 実使用(live / dogfood)の検証を、単体+静的レビューの代替ではなく補完として計画したか
