# 検証環境の構造的盲目 — 「緑」と「赤にできる」は別の主張

## 中心命題

> **ゲートが仮定を witness できるのは、ゲートの実行環境が、その仮定の語っている環境と異なるときだけである。**

(witness〈証人〉= 壊れていれば RED〈失敗〉にできる形で検知すること。)抽象的に聞こえるが、具体例を見れば単純である。

例: 「ユーザーの環境で `python3` と打てば、我々のインタープリタが起動する」という仮定を出荷するとする。これを普通の pytest(Python のテスト実行ツール)のジョブで検証できるだろうか。**できない。** pytest ジョブはこの仮定を**検証しようとしながら、同時に自分でこの仮定を成立させている**(CI ランナーには正しい python3 が PATH に載っている)。仮定とテスト環境が同じ事実なので、原理的に反証が起こりえない。

これを witness できるゲートは、**production(本番)と同じ形の環境をわざわざ構築する**: 実際にビルドした wheel(Python の配布パッケージ)を、使い捨ての venv(仮想環境)に入れ、**その venv を有効化(activate)せず、PATH(コマンド検索パス)にも載せず**に叩く。この環境は「開発環境が production と異なる、まさにその点」で異なっているから、仮定が壊れていれば赤になれる。

覚えるべき一行はこれである:

> **「テストが緑である」と「その環境はテストを赤にする能力がある」は別の主張で、信じる価値があるのは後者だけ。**

## 実例 — 1つの変更に3つの盲点(それぞれ理由が違う)

サンドボックス機構(seccomp / Landlock)の変更で、**同じ changeset に3つの欠陥**があり、それぞれ**別の理由**で検証環境から見えなかった:

| 欠陥 | 環境が構造的に盲目だった理由 |
|---|---|
| システムコール(syscall)許可リストに `stat`/`lstat` が無い | 開発機の CPU アーキテクチャ(aarch64)には**そもそも `stat` syscall が存在しない**(`*at` 系のみ)。この欠陥は古い glibc(標準Cライブラリ)の x86_64(主要な長期サポート版ディストリビューション)でしか発火しない |
| ファイル切り詰め(truncate)の穴 | 検証ホストのカーネルは新しく(ABI 4。ABI = カーネルが提供する機能の世代番号)、穴は **ABI 1–2 のカーネル**(= 世の中の主流のインストールベース)にしか存在しない |
| テストが本物の不可逆フィルタを pytest 自身のプロセスにロード | 開発機(macOS)には該当ライブラリが無く `is_available()` が False なので、**危険が発火できない** |

同じ夜、同じ形が他所でも: 自社利用(dogfood = 自分たちの製品を自分たちで日常使用する)シナリオが CI で走っていない → 削除済み機能への参照が **13日間**誰にも見えず残存。CI がオプション依存をインストールしていない → モジュール全体が skip(実行を飛ばす)されながら CI は緑。配線が死んでいる → その先の自滅バグ(exec 直前に execve を拒否する設定)が「到達不能だから」発火しない。

> **死んだ機構は、それが生き返った瞬間に発火する欠陥を隠している。**

## 修正側にも同じ罠がある

**罠1: 「ガードを忘れられなくする」構造的修正が、唯一の本物の検証を殺す。** 上の3つ目の欠陥への対処として「全テストに自動適用される fixture(テストの共通前処理)で本物のフィルタのロードを禁止する」案が検討され、**棄却された**。その fixture は、これから作る「本物のフィルタをロードすることが目的の CI ジョブ」を黙って無力化するからだ。「ガードを構造化する」前に、**そのガードが殺してはいけない検証がないか**を確認する。

**罠2: レビュアーの「より良い修正」が、修正対象の欠陥クラスを再生産する。** 「syscall を許可リストから消すのではなく、上位機構の管理対象に加える方が良い」という提案は、その管理機能が**新しいカーネルにしか無い**ため、古いカーネルでは穴がそのまま残る — しかも提案者の(新しい)検証ホスト上では閉じて見える。提案もまた「どの環境で成立する主張か」の軸で検査しなければならない。

## 第3の形 — 正確な記述が機構の代わりをしている

環境盲目には、噓が一つもなくても成立する形がある:

> **正確な記述であっても、それを強制する環境が無ければ、ゲートは存在しない。「ドキュメントに書いた」は「どの環境もこれを witness しない」の言い換えである。**

実例: あるレビューで「危険な設定の重なりを**警告するだけ**」の対処案(案C)を「警告は防御ではない」と正しく棄却したレビュアーが、その数時間後、**同じ内容をドキュメント警告の形で含む別 PR を merge しかけた**。文面は正確で、嘘は一つもない。それでも「この仮定を witness できる環境はどれか?」の答えが「無い — 書き残しただけ」である以上、それは棄却したはずの案Cである。

ドキュメントのみのガードが正当なのは、**期日付きのプレースホルダ**(「#N が入るまでの暫定 doc-only」)として明記されるときだけ。

## 正直な「未検証」は仕事をする

上の syscall 欠陥が見つかったのは、実装者が報告に「x86_64 は未検証」と**平文で書いた**からである。レビュアーはその一行を起点に、具体的な欠落(`stat`/`lstat`)まで到達できた。曖昧な自信は穴を隠し、**正直な「Xでは未検証」は荷重を支える**。

## 実践方法

- 緑のスイートを信じる前に問う: **「このテストが落ちる能力を持つには、この環境の何が真でなければならないか?」** 環境がテスト対象の事実を自分で供給しているなら、その緑は無価値。
- 仮定を出荷するときは、**production が開発環境と異なる点を名指しし、その点で異なる環境を構築して**ゲートをそこに置く。
- 実装報告には「どの環境で検証し、どの環境では未検証か」を平文で書かせる。
- ドキュメントだけのガードを見たら「どの環境がこれを witness するか」を問う。答えが無ければ、それは防御ではない。
