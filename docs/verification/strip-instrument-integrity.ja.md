# strip 計測器自体の健全性 — 「測るもの」が壊れる4つの形

[strip 反証](strip-falsification.ja.md)(= 機構を一時的に無効化して、テストが RED〈失敗〉になるか確かめる手順)は「ゲートが本物か」を測る計測器である。**計測器が壊れていれば、対象について何を観測しても結論は出ない。** そして計測器の壊れ方には決まったパターンがあり、その多くは「健全なゲート(退行防止のテスト)を、空虚(vacuous = 実は何も守っていない)だと誤って告発する」方向(偽陽性 = 問題がないのに問題ありと判定する誤り)に出る。この方向の誤りは、空虚なゲートを見逃す偽陰性より発見されにくい。「あなたのテストは効いていない」と言われた側は、普通そのまま直してしまうからだ。

## 壊れ方1 — anchor が一意でない(隣のサイトを潰している)

strip を機械的にやるとき、対象のコード片(anchor)を文字列置換で消すことが多い。このとき anchor が**ファイル内に複数回出現する**と、意図しない方が消える。

```python
# session.py
def on_switch(self):
    self._running.clear()      # 出現1(切り替えハンドラ)

def on_resolve(self):
    self._running.clear()      # 出現2(← 検証したいのはこちら)
```

```python
src = src.replace("self._running.clear()", "pass", 1)   # 最初の出現(出現1)が消える
```

検証対象でない方を潰してテストが緑 →「ゲートは空虚だ」と報告 → 実際にはゲートは健全で、strip が外れていただけ。実例では、この形の誤告発で健全なゲート3本が書き直されるところだった。

- **strip する前に anchor の出現数を数える。** `count == 1` でなければ、行番号か囲む関数名で狙うか、anchor を一意になるまで広げる。
- 「何かが変わったこと」(`assert src != before`)の確認では**不十分**。それは「何かを変えた」証明であって、「検証対象のサイトを変えた」証明ではない。

## 壊れ方2 — 機構が複数箇所に重複宣言されている

anchor がファイル内で一意でも、**同じことを別のファイルも宣言している**ことがある。

例: UI 部品の高さが `chrome.py`(UI の外枠部品)と `app.py` の両方で宣言されており、実際に効いているのは `app.py` 側だけ。`chrome.py` 側だけを strip するとテストは緑のまま →「ゲートが効いていない」と誤読する。`count == 1` は**ファイル内の検査**であって、別ファイルの二番目の宣言は見えない。

> **見分け方: strip の結果が「別の壊れ方」ではなく「まったく何も変わらない」(テスト結果だけでなく、実挙動・出力にも何の差も出ないなら)、潰した対象が間違っている。** 健全なゲートを告発する前に、同じことを宣言している場所が他にないかを探す。

なお、shadow されている(= もう一方に上書きされて効いていない)側は往々にして「説明の docstring(コード内の説明文)が書いてある側」である。将来そこを編集しても何も起きず、ゲートはどちらでも緑なので、この重複はゲートでは捕まらない。

## 壊れ方3 — そもそも別のコードを測っている(実行環境の同一性)

最も根深い形。Python の共有 venv(仮想環境)で editable install(`pip install -e .` = 開発中のソースツリーを直接参照させるインストール方式)を使う環境では、**venv が指すソースツリーが自分の作業ツリーと別物**になっていることがある。

```
$ .venv/bin/python -c "import myapp; print(myapp.__file__)"
/repos/worktrees/agent-B/src/myapp/__init__.py    # ← 自分のツリーではない!
```

この状態でテストを回すと、**自分のコードではなく他人のツリーを測る**。発生機構も特定されている: 複数エージェントが worktree(同一リポジトリの並行チェックアウト)で作業する環境では、worktree 内で `pip install -e .` を打つと、`VIRTUAL_ENV` が親の共有 venv を指したままなので、**親 venv の editable install が自分の worktree へ張り替わる**。つまり事故ではなく、放置すれば必ず再発する仕組みである。要するに「最後に `-e .` を打った worktree が勝つ」ので、自分が被害者にも加害者にもなり得る。

重要な点が3つある:

1. **GREEN 報告の方が危険**(直感と逆)。別ツリーを測ると「変更していないコード」を測るので strip が緑になり、「ゲートは空虚だ」という誤告発を生む。RED は(別ツリーでも RED なら)少なくとも何かを測れている。環境に疑いが出たら、再確認は GREEN 報告から。
2. **中央監査は原理的に成立しない。** 監査役が他セッションのディレクトリで `python -c "import myapp"` を実行しても、使われるのは監査役自身の PATH(コマンド検索パス)の python である。各セッションが実際に呼ぶ python はそのセッションにしか分からない。だから**測る側が、測る瞬間に自己確認する**しかない:

   ```bash
   python -c "import myapp; assert myapp.__file__.startswith('$PWD/src'), myapp.__file__"
   ```

   これを strip の前提チェックの **0 番目**(anchor 一意性より前)に置く。strip の結論は「どのコードを測ったか」に完全に依存するからだ。
3. **宣言でなく解決を読む。** 設定ファイル(`.pth` 等)の中身は「どこを指すと宣言しているか」であり、「実際にどこへ解決されるか」は `myapp.__file__` で測る。宣言と解決のズレこそが、まさにこの壊れ方の本体である。

予防は「worktree では**先に隔離 venv を作り**、共有 venv に向けて `-e .` を打たない」。

## 壊れ方4 — 負荷・並行性(いつ測ったか)

並行エージェント環境では、**遅い実行やタイミング起因の不安定な失敗(timing flake)の原因を「自分の作業記録に最初に見えたもの」で説明してしまう**誤りが出る。実例では、失敗の原因を自分のポーリング(定期監視)ループだと公表した後で `ps`(プロセス一覧コマンド)を打ったら、別セッションがフルテストスイートを回しており、公表した原因は良くて副次的だった。

- 遅い実行・不安定な失敗を説明する前に `ps` と `uptime`(負荷表示コマンド)を打つ。「たぶん干渉」も「たぶん自分のせい」も等しく無証拠。
- **緑も赤も、取得時の負荷を添えて報告する。** 負荷下の緑と静穏時の緑は別の主張である。
- 「自分の作業記録に最初に見えた原因」は**最も安い仮説であって、最も確からしい仮説ではない**。自分が知っている容疑者しか並べていないことに気づけないのが、この誤りの本質。

## 測定が食い違ったら、平均せず決着させる

自分の strip 結果と相手の strip 結果が食い違ったら、「どちらも一理ある」で流さない。strip 報告は検証規律全体の土台であり、ここが揺れると以後のすべての RED 報告の信頼度が落ちる。**「なぜ違ったか」を特定するまで詰める**(上の4つの壊れ方が容疑者リストになる)。また、「あなたの strip は外れている」と指摘された側も、鵜呑みにせず自分で再測定する — 誤告発は再測定によってしか止まらない。

## チェックリスト(strip 実施前)

- [ ] (0) 実行環境の自己確認: `import myapp; assert myapp.__file__.startswith(自分のツリー)`
- [ ] (1) anchor の出現数は 1 か。1 でなければ行番号・関数名で狙ったか
- [ ] (2) strip 後、意図したサイトが本当に変わったか(差分を目視)
- [ ] (3) 「何も変わらない」結果が出たら、同じことを宣言する場所が他にないか探したか
- [ ] (4) 結果(緑/赤)に、実行時の負荷・並行状況を添えたか
