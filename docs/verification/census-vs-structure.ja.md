# census と structure — 「今日そうである」と「そうであるように作られている」

## 問題の形

設計判断やレビューの根拠は、必ず何らかの前提の上に立つ。「このフィールドは信頼できる、なぜなら〜」「この最適化は安全だ、なぜなら〜」。この「なぜなら」には**2種類**あり、混同すると、今日は正しいが明日黙って壊れる根拠の上にシステムを建ててしまう。

- **census(国勢調査)型**: 「**現在の事実の報告**」。呼び出し元を3つ調べたら全部 n < 100 だった。今のプロバイダ(LLM API の提供事業者)はこの形式で返す。今日のコンシューマは全員フィルタをかけて読んでいる。
- **structural(構造)型**: 「**契約の記述**」。このリストはソート済みである、なぜなら `sort()` の出力だから。このログのエントリは削除されうる、なぜなら削除 API がそう定義されているから。

判別式は次の一問である:

> **この前提が壊れたとき、システムは「壊れる(BROKEN)」のか、それとも「違うものになる(DIFFERENT)」だけか。**

structural 型は、壊すためには**誰かが設計・契約を変更する**必要がある。census 型は、**世界がたまたま変わるだけで**壊れる — 新しい呼び出し元、別のプロバイダ、試していなかった入力。前者は壊れたら「システムが壊れた」であり、後者は「状況が変わった」にすぎない。

## なぜ「反証可能性」では判別できないか

最初に提案された定義は「structural = 反証可能な経験的主張を含まない」だった。これは**過剰に当てはまって、structural のカテゴリを空にする**。

例: 「このログのエントリは切り詰め(truncate)されうる」は反証可能である(切り詰め機能を削除すれば偽になる)。それでもこれは structural だ — なぜなら、それを偽にする唯一の方法が**設計変更**だからである。逆に「BPE トークナイザ(テキストを部分語に区切る方式の一つ)の分割は結合規則(merge)を失うだけだから、断片の合計 ≥ 全体、つまり常に安全側(過大見積もりは安全、という向き)に倒れる」は、もっともらしく聞こえるが census である — **誰もトークナイザをそう設計していない**。成立していてほしい事実であって、誰かが署名した契約ではない。

見るべきは**形式**(反証可能か)ではなく**実体**(それは誰の契約か)。

## 同じ前提が、片方の適用条件(regime)では structural、別の適用条件では census になる

例: トークン数の見積もりで「メッセージ配列の合計 = 定数 + 各メッセージの個別カウントの和」という**加法性**を仮定するとする。

- あるプロバイダの公式カウント規約が「3 + Σ(per-message)」と**定義**されているなら、その規約に対して加法性は **structural**(非加法な実装はその規約の実装ではない = 壊れている)。
- しかし中間ライブラリ経由で**複数プロバイダ**に適用するとき、加法性は **census** になる。実測で5プロバイダが同一の数値を返した = ライブラリが1つの規約を全プロバイダに当てはめているだけ。**皆が期待する「ライブラリがプロバイダ別の正確なカウントに改善される」ことこそが、加法性を壊す当のもの**である。

そして**実行時には、自分がどちらの適用条件にいるかを判別できない**。これが次の節の理由になる。

## census 前提の上に建ててよい — ただし「チェック付き・可視故障」のみ

> **census 前提を設計時に仮定してはならない。実行時にチェックし、壊れたら検知できる形で即座に失敗させよ。**

ここで重要な訂正が2つある(いずれも実際の設計レビューの攻防で確定したもの):

1. **チェックは前提を真にしない。故障を可視にするだけである。** チェック付き census 前提は structural に**昇格**するのではない。「隠れた依存」から「宣言され監視された依存」に**降格**するのである(確実さが上がるのではない。census のままであることが公認されるだけである)。得られる価値は運用的(壊れたら分かる)であって、認識的(前提がより確かになる)ではない。
2. **structural 前提からは推論してよい。チェック付き census 前提には、ガード付きで依存することしかできない。** さもないと、次の読者が「チェック済み = 前提条件」と読んで、**自分のガードなしに第二の機能をその上に建てる**。「チェック済み」が守るのは、そのチェックが守っている呼び出し経路だけである。

## チェックは、サンプルした定義域の分しか守らない

チェック自体が census の失敗形を継承する。実例: 「加法性を構築時に一度検証する」チェックが、**プレーンなメッセージ2通**でサンプルしていた。このチェックは、**マルチモーダル添付やツール呼び出しの加法性が壊れている世界でも通る** — その形状に一度も触れないからだ。

(T = 配列全体のトークン数、unit = 単独メッセージのトークン数、k = 定数)

```
構築時チェック(プレーン2通): T([A,B]) == k + unit(A) + unit(B) → True
  ↑ tool_calls も画像も一度も通らない
黙って一般化される形状: tool_calls, マルチモーダル
```

**チェックはサンプルした定義域の分だけしか守らない。** 対処の形: **形状トリガ**(新しい形状クラスの初出時にチェック)+ **定期照合**(N 回ごとに全体を再計算して突き合わせ、ズレ = 再同期 + 監査イベント。黙って補正しない)。これで「ドリフト(想定と実際のズレ)が無いことを祈る」が「ドリフトは N で有界、かつ計測されている」に変わる。

## 実務での見分け方 — 1回の grep で反証できるか

> **「コードを読んで、今日の挙動が違うと示せば、この根拠は崩れるか?」— 崩れるなら census であり、本当の根拠はまだ見つかっていない。**

実例(背景: 分岐と巻き戻しを持つ会話ログで、読み手は「現在の分岐のみ」の絞り込み = ブランチフィルタを選べる): 「使用量の合計をイベントログに載せてはならない。ログはブランチフィルタされるので、巻き戻しで放棄分の使用量が消えるから」という根拠 — もっともらしいが、grep(コード全体の文字列検索)1回で崩れた(フィルタは**コンシューマ〈読み手〉ごとのオプトイン〈明示的に選んだときだけ有効〉**であり、使用量のコンシューマはフィルタしなければよい)。つまり census。本当の(structural な)根拠は別にあった: **ログのエントリは設計上 truncate されうる**ので、生涯単調増加の合計を truncatable なログに置けば処理の連鎖のどこかで切り詰められて失われる — 実際、同型の障害をこのリポジトリは**過去に一度出荷している**。

## 嘘の記述は、不完全な列挙の化石である

census 前提が最悪の形で固定化する経路がこれ:

> **不完全な列挙 → 誤った断定 → 断定が文書化される → 次の読者の前提になる。**

実例: 「この値はコンテキストビルダー群が配線している」というコメント(コンテキストビルダー = プロンプトを組み立てる内部部品)は、列挙が不完全なまま書かれた。**そのコメントが次の実装者の前提になり**、存在しない記録機構の上に機能が建てられ、**8540 本のテストと CI が緑のまま、production は何も記録していなかった**。

1日で出た6欠陥がすべてこの形だった: コメントが配線を仮定 / 関数**名**が実行を仮定(`install_seccomp_filter` は「インストーラを返す」だけで、両呼び出し元が返り値を捨てていた = production で一度もロードされていない)/ コメントが値域を仮定(「スコアは [0.0, 1.0]」はバリデータではない)/ 警告文が、実際には起きないフォールバック(代替動作)を仮定 / PR 本文が到達を仮定(実際は別フィールドが読まれる)/ 過去の嘘がドキュメントに生き残る。

## 実践方法

- 根拠を「structural」と呼ぶ前に、**「この前提が壊れたら、壊れるのか、違うものになるだけか」**を問う。
- 違うものになるだけなら census。**本当の structural な根拠を探すか、実行時チェック(形状被覆・可視故障・次の読者への注記つき)に落とす。**
- チェックを書いたら、**サンプルしている定義域**を明記する。チェックが触れない形状に前提を一般化しない。
- 何かの定義域(呼び出し元・コンシューマ・grep ヒット・和の項)について断定する前に、**列挙する**。列挙の具体的な規律は[列挙の規律](enumeration-discipline.ja.md)へ。
