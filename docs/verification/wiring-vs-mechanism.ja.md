# 配線テストと機構テスト — 「動く部品」と「つながっている部品」は別の主張

## 問題の形

新しい機能を入れるとき、コードは大きく2つの部分からなる。

1. **機構(mechanism)**: 仕事をする関数・クラスそのもの
2. **配線(wiring)**: production コードが実際にその機構を呼ぶ箇所(call-site)

そして**テストは機構だけを検証して、配線を検証し忘れることが非常に多い**。トイ例:

```python
# 機構: エラーハンドラを設定する
def install_error_handler(app):
    app.set_exception_handler(log_and_recover)

# 配線: production の起動パス (main.py)
def start():
    app = App()
    install_error_handler(app)   # ← この1行が「配線」
    app.run()
```

ダメなテストはこう書かれる:

```python
def test_error_handler_installed():
    app = App()
    install_error_handler(app)            # テストが自分で機構を呼んでいる
    assert app.exception_handler is not None
```

このテストは `install_error_handler` が正しく動くこと(機構)を証明する。しかし **`start()` から `install_error_handler(app)` の行を削除しても緑のまま**である。つまり、機能を production に届けている配線は何にも守られていない。将来のリファクタリングでこの1行が消えると、機能は静かに死に、このPRが閉じたはずのバグがそのまま再発する。

確かめ方は [strip 反証](strip-falsification.ja.md)の応用で、**strip する対象を機構ではなく production の call-site にする**。配線の行を消してスイートが緑のままなら、それは機構テストであって配線テストではない。

この形は珍しくない。実測では**一晩にレビューした3つの PR が全部この欠陥**だった。それぞれ (a) テストが自前のドライバで引数をハードコードしていた、(b) テストが内部関数を直接呼んでいた、(c) テストが状態を手組みして本来の入口(セッション層)を迂回していた — 形は違うが、いずれも「production の入口から機構までの経路」をテストが通っていない。

なお、実装者の「fix の前は RED でした」という申告は嘘ではないことが多い。**RED だったのは症状(機構の不在)であって、配線ではない**。「RED before fix」を聞いたら「何を strip したときの RED か」を確認する。

## 「正しい機構がある」と「全経路がそれを通る」は別の主張

この欠陥の一般形は次のとおり:

> **機構を作れと勧める・作ったと報告するときは、「機構の正しさ」と「機構への到達」を必ず2本の別の assert として要求する。**

実例(一般化): 「オブジェクトの外部流出時に deep-copy する責務を、専用ヘルパー1つに集約し、ゲートはヘルパーの出力を `is` 比較で検査する」という設計提案があった。この提案は「正しい契約のヘルパーが存在する」ことしか守っていない。**必要なのは「すべての流出点がそのヘルパーを通る」**という別の主張であり、ヘルパーの単体テストを何本足してもこちらは1ミリも守られない。

この取り違えは、同じレビュアーが**同じ日に2度**やった記録がある。2度出る誤りは個人の注意力の問題ではなく、**手順(依頼テンプレート)の欠落**である — 「機構の correctness と reachability を別々に assert せよ」を依頼の定型に組み込むのが正しい対処。

## 到達には時間軸がある — 明日生える5つ目のサイト

「今日の流出点4つが全部ヘルパーを通る」ことをテストで witness しても、**明日追加される5つ目の流出点には witness がなく、witness がないことは静かである**(shallow copy の混入は壊れるまで無症状、という形で潜伏する)。

対処は「新しいサイトがヘルパーを迂回できない」ことを**構文レベルのゲート(AST チェック等)**で別途要求すること。探すのが「意図」ではなく「式の形」であれば構文ゲートにでき、偽陽性はヘルパー自身の1箇所だけに抑えられる。ただし:

- **ゲートが捕まえない範囲を docstring に明記させる。** 正当なサイトが偽陽性に混ざるゲートはいずれ抑制(無効化)され、**抑制されたゲートは何も守らない**。

## チェックリスト

実装する側:

- [ ] テストは production の実際の入口(実セッション・実ランナー・実ディスパッチ)から機構まで到達しているか。内部関数の直接呼び出しや状態の手組みで代用していないか
- [ ] strip 反証の対象は「production の call-site」か(機構ではなく)
- [ ] 機構の正しさと到達の2本の assert が揃っているか

レビューする側(co-vet = 独立第二検証):

- [ ] 「RED before fix」の申告を額面で受け取らず、**何を strip したのか**を確認したか
- [ ] 自分で production call-site を strip したか。緑のままなら「配線未 guard の機構テスト」→ merge 前に実経路テストを1本要求(通常それだけで済む)
- [ ] 将来のサイト追加に対する構造的ゲート(構文チェック)が必要な形か検討したか

## 出典(reyn 開発での実測)

一晩3連発: #2788(テストが自前ドライバで引数をハードコード)・#2801(内部関数を直接呼び、production 側の呼び出しを strip しても緑)・#2802(状態を手組みしてセッション層を迂回)。いずれも独立第二検証者が production call-site を strip して発見。correctness と reachability の分離: #3383/#3385(deep-copy ヘルパー集約の設計助言で、レビュアーが同じ穴を一日に2度踏み、依頼テンプレートに組み込む対処に至った)。
