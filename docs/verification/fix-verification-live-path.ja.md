# 修正は生きた経路で証明する — 3つの代理の罠

## 問題の形

バグ修正の検証には、本物の代わりに使いたくなる**代理(proxy)**が3つある: (1) 依頼文に書かれた病名、(2) 修正箇所そのものの単独検査、(3) 実装者のテストが緑であること。3つとも、生きた経路(実際に障害が流れる経路)を通した検証の代わりにならない。代理は答えを**間違えるだけでなく、反転させる**ことがある。

## 罠1 — そのバグは、まだ生きているか

確信ありげな根本原因つきでバグ修正を依頼されても、**実装の前に、そのバグが今も有効(ACTIVE)かを確かめる**。過去の同類修正がすでにクラスごと塞いでいることがある。

実例: 「キャッシュされたクライアントが別タスクで閉じられてクラッシュするクラス」という依頼を受けた実装者が、生きた経路を追跡した。結果: 処理は**直列に実行**されており(並行タスクを作る箇所がない)、閉じる処理の呼び出し箇所は1つだけで、そこには**過去の同類修正のコメント**(「開いたのと同じタスクで閉じる」)が既に付いていた。オーナーが実際に踏んだクラッシュは**別の箇所**(既に別修正で対応済み)だった。つまり依頼の前提「有効なバグ」が偽で、**修正を実装していたら、正しいコードをリファクタリングして新しいバグを入れる機会**を作るところだった。

- (1) **生きた障害経路を追跡する**(依頼文の病名ではなく)。(2) 同類の過去修正を grep する(継ぎ目付近の issue 番号つきコメントが目印)。(3) 具体的な再現手順・オーナーの症状を求め、**この箇所**と一致するか照合する。(4) 有効な経路が見つからなければ、そう言って**保留を提案**する — 「有効なバグの修正」と「正しいコードの予防的強化」は別の判断で、後者はオーナーの優先度判断である。

## 罠2 — 単独ゲートの検査は判定を反転させうる

宣言・設定エントリを追加する修正の検証では、**宣言 → それを消費する全ての層**を実際に流す。修正箇所の関数だけを単独で叩く検査は、**逆の結論**を出すことがある。

実例: マニフェストに書いた書き込み許可の宣言が効くかを、実行時ゲート関数を単独で呼んで確認した → 拒否された → 「この修正は不活性(効かない)」と結論しかけた。実際は、このシステムでは**実行時ゲートは設計上、宣言を読まない**。宣言の本当の消費者は**起動時の事前チェック**という別の層で、そこが宣言されたパスを事前承認に回し、承認が永続化された後は書き込みが通る。端から端まで(宣言 → 起動時チェック → 承認 → 書き込み)流せば、修正は**正しく機能していた**。単独ゲートという代理が「動く修正」を「不活性」に反転させ、誤った差し戻しを送るところだった。

- 宣言・設定フィールドの**全消費者を grep で列挙**し(自明なゲートだけでなく)、それぞれを通して本物のフローを流す。
- 検証環境を**本番の形に合わせる**(作業ディレクトリ、相対パスの解決基準など)。形が違う単独プローブは偽の拒否を出す。

## 罠3 — 実装者のテストは兄弟経路しか踏んでいないかもしれない

複数の呼び出し箇所・分岐経路に触れる修正を独立検証(co-vet)するときは、**オーナーが実際に踏んだ経路**を自分で特定して反証する。実装者のテストが緑でも、そのテストが駆動しているのは**別の兄弟経路**かもしれない。

実例: 実装者のテストは対話プロンプト経路(経路A)を駆動して緑だった。オーナーの実際の障害は**既定のフルスクリーン経路(経路B)** — 同じ機構、別の呼び出し箇所 — で起きていた。検証者は経路Bの正確な形を再現し、修正ありで正しい挙動・**修正を反転させると RED** を確認した。これが実装者テストの盲点を埋める、決定的な(load-bearing な)検査だった。

- 修正が変更した呼び出し箇所を列挙し、**オーナーの再現がどれを流れるかをルーティングを追って特定**する(推定しない)。
- その経路の正確な形を再現し、[strip 反証](strip-falsification.ja.md)する(修正ありで良い挙動 + 修正を外すと RED)。実装者の主張を復唱することは検証ではない。
- 実装者のテストが修正後の値を**自分でハードコード**していたら、それは機構テストであり、実際の呼び出し箇所から値が消える将来の退行を捕まえない — 指摘する([配線テストと機構テスト](wiring-vs-mechanism.ja.md))。
- 証拠(永続化されたファイル等)は**正しい場所を見てから**「0件」と結論する。実例では保存先が月別のサブディレクトリ構造で、浅い場所への検索が偽の「0件」を報告した。

## 実践方法

- [ ] 修正の実装前: 生きた障害経路を追跡したか。過去の同類修正を grep したか。オーナーの症状とこの箇所は一致するか
- [ ] 宣言・設定の修正: 全消費者を列挙し、端から端まで本番の形で流したか
- [ ] co-vet: オーナーの実経路を特定し、その経路で strip 反証したか
- [ ] 「0件・不活性・効かない」の結論の前に、見ている場所・層・環境が正しいか確認したか
