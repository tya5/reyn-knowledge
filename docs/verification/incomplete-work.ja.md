# やり残しは欠陥の発見を遅らせる

## 問題の形

部分的に終わった作業・黙って先送りされた作業の何が悪いのか。「いずれ終わらせるのだから同じでは?」— 違う。**やり残しは「動いているように見える」状態を作るので、欠陥が表面化するまでの時間(発見レイテンシ)を引き延ばす。**

実例: ドキュメントが先に理想の挙動(「4段階の確認フロー」)を書き、実装が追いつかないまま放置された。実際の挙動は単純拒否。この乖離は、**誰かが日常使用で偶然踏むまで約1週間**、誰にも気づかれなかった。ドキュメントと実装のどちらも単体では壊れて見えない — 乖離だけが欠陥で、乖離は放置の間ずっと不可視だった。

これは[一括修正 PR のレビュー](sweep-reviews.ja.md)の「未変更は『検査済み』と『見ていない』の区別がつかない」と同族である: **未完了は「まだやっていない」と「終わった」の区別が、外から付かない。**

## 規律

### 1. 監査の範囲は全数である

「優先度の高いサブセットだけ監査して、広域の走査は落とす」を禁止する。順序として優先分を先にやるのは構わないが、**広域も必ず実施する**。全数を見ない監査は、[列挙の規律](enumeration-discipline.ja.md)の切り詰めを工程レベルでやっているのと同じである。

### 2. 発見した穴は、同じセッションの中で起票する

「後で issue を立てる」を禁止する。発見と起票の間に切れ目が入ると、起票は高確率で消える — そして起票されなかった発見は、**次に誰かが偶然踏むまで存在しないのと同じ**になる。先送りにした項目に追跡 issue が無いものも、見つけ次第すべて起票する。

### 3. 終わらなければ、完了分と残余を可視のチェックリストにする

セッション内で全部終わらないのは普通のことで、問題ではない。問題は**黙って落とす(silent drop)**ことだ — どこまで終わっていて、どこが未了かを、後から誰も追えなくなる。完了分 / 残分を列挙したチェックリスト(構造として完全性が見える形)を残す。

### 4. 修正は対称面を全列挙する

ある検査ゲートを1つ直すなら、**同種のゲートを全部 grep して同じ穴を洗う**。「ファイル側だけ直してシェル側は放置」型の部分修正は、直した瞬間から残りの兄弟が「直されたらしい」という誤った印象に守られる。[fix-class レビュー](fix-class-review.ja.md)の実装側の義務にあたる。

### 5. 起票の経路を冗長化する

発見の完全性と、起票経路の可用性は別の問題である。起票ツールの不調(認証切れ等)が「全部追跡する」の単一障害点にならないように、**発見者が起票できなければ他の誰かが代理で起票する**取り決めを先に作っておく。

## 実践方法

- [ ] 監査・掃討の計画に「広域の全数走査」が含まれているか(優先分だけで終わる計画になっていないか)
- [ ] 発見した gap は今このセッションで起票したか
- [ ] 未了で終える場合、完了分/残分のチェックリストを可視の場所に残したか
- [ ] 修正した面の対称面(兄弟ゲート・並行実装)を grep で列挙したか
- [ ] 起票経路が詰まったときの代理経路が決まっているか

## 出典(reyn 開発での実測)

#1505/#1317: ドキュメント先行の理想記述が実装未達のまま放置され、日常使用で偶然踏まれるまで約1週間不可視。オーナー厳命(2026-06-12)「やり残しがないように。以前勝手にやり残したせいで発見が遅れた」。
