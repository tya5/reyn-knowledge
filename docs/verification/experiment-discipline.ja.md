# 実験とベンチマークの規律 — 数値を出す前、信じる前

## 前提

A/B 測定(同じ条件で2案を並べて比べる実験)・ベンチマーク・「修正が効いた」の検証 — どれも最後は**数値**になる。そして数値は、それを生んだ条件の但し書きを失って**独り歩きする**。この文書は、数値を出す側と信じる側の両方の規律である。[測定対象のずれ](measurement-target.ja.md)が「その数字は問いに答えているか」の一般原理なら、本書はそれを実験の場面に特化させた各論にあたる。

## 1. A/B の腕の同一性 — 「どちらの版が走ったか」を検証してから測る

A/B の各腕(arm = 比較する片方の構成)が**本当に指定した版のコードを実行したか**は、仮定でなく検証である。実測: 実験対象のパスを指すつもりの環境変数が、開発用インストール(editable install = 開発中のコードを直接 import させる方式)に**黙って覆い隠され**、誤った版が走ってもエラーは出なかった — 腕が汚染された A/B は差分ごと無効になる。

- 測定の先頭で、**実際に import されたモジュールのファイルパスを印字して確認**してから走らせる。
- **1点の差分は「存在」しか言えない**。「範囲全体でこの差分は当該機構が原因」は別の主張であり、範囲の測定と**直交機構の探索**(比較側の腕に同じ結果を出す別の仕組みがないか)が要る。実測: 単一点から差分を断定した後、比較側の腕でも別機構が同じ結果を出していたと判明した。
- 主張の正直な縮小(「比較側の腕は停止する」と主張していたのを「ほぼ回復する」と記録し直す)は失敗ではなく、正しい動作である。

## 2. 交絡した数値は、注記付きでも出さない

測定条件が壊れていた(検証対象がハンディキャップを負っていた)と分かった数値は、「参考値」「下限」の**注記を付けても発表しない**。数値は注記を落として独り歩きし、後続のセッション・文書が裸の数字だけを引用するからである。実測: 採点系は正しかったが、検証対象側の自己検査が壊れた環境で走っていた — 数字が出る直前に交絡と分類し、**checkpoint して次の枠で忠実に測り直す**判断が取られた。

- 出す前の問い: 「**この数値への入力は、それぞれ忠実か?**」(測定条件は主張どおりの能力を測っているか、壊れた条件のハンディを測っているか)。
- 派生規則: **検証ループが正解情報に触れている**(テストへの反復で答えに漏れがある)測定は、外部に公開するスコアとしては**出せない** — 内部の安定性シグナルとしては価値が残る(その用途と割り切って使い、公式スコアと呼ばない)。

## 3. 自分のログが数える単位と、線の上の単位は違う高度にある

実測(全て localhost、課金ゼロで測定): 埋め込み1回の呼び出しで、HTTP リクエストが **9本**流れていた。ログは「attempt 1/3」と言っている。犯人は疑われた層ではなかった:

```
呼び出し側は「retry 指定なし(None)」のつもり
→ 下位ライブラリの `max_retries or DEFAULT` が None を 2 に変換
→ SDK が1呼び出しで HTTP 3本
× 上位の retry 3回
= 9本(config に「3」と書くと、黙って 9 になる)
```

- **「N 回 retry する」と書く/読む前に、線の上を数える** — retry 層が入れ子なら設定値は掛け算される。
- **`x or DEFAULT` の形を疑う**: 呼び出し側の「指定しない(None)」が、ライブラリの既定値に化ける。「指定しない」と「無効化する」は別である。
- **自分のログが数えている単位を名指す**: attempt / call / request / round-trip は全部違う単位。
- **timeout も同じ高度差を持つ**: SDK の `timeout=` は「retry される1リクエストあたり」の締切で、全体の締切ではない — `timeout: 60` が黙って 180秒になる。リスクは「ライブラリが設定を無視する」ではなく「**読み手が想定した高度とは違う高度で尊重する**」こと。
- おまけの実測: コスト記録が await の**後**にしか走らない実装は、例外時ゼロ記録・成功時すら9本中1本分 — **構造的に下限**の会計になる。オーナーの一言(「え、リトライでずっとコスト増やしてるの?」)が発見の起点で、書いた側は分岐を立てただけで**測っていなかった**。

## 4. 「直った」と言う前の過剰適合セルフチェック

修正を「検証済み」と報告する直前に、次を自問する(全て実測で踏んだ項目):

1. **N=1 か、N≥5 か**: LLM を含む系は確率的で、1回の成功は「直った」とも「今回だけ避けた」とも整合する。
2. **テスト入力が、修正自身の表面と重なっていないか**: 修正で追加した案内文とほぼ同一の文でテストして成功 = **自分の修正への一致を測っただけ**。自問: 「その案内文を消しても、このテストは通るか?」。
3. **構造軸と行動軸を分けたか**: 「到達可能になった」(一覧に載った)と「自然な入力で選ばれる」は別の軸。前者だけで「検証済み」と言わない。
4. **帰属のアブレーション(1要因ずつ戻す切り分け)**: 修正と同時に変えた別の状態(キャッシュ削除など)はないか。「自分の変更だけ戻して、挙動が退行するか?」— 実測では、改善の真因は同時に行った状態クリアで、当の修正は無関係だった。
5. **曖昧な入力を分解したか**: 「間違った選択」に見えた挙動が、曖昧な依頼の別解釈として合理的なら、それは欠陥ではない —「欠陥でなかった」も正当な結論である。
6. **ベンチマーク由来の修正なら**: 一般経路で既に到達可能かを先にテストする。到達可能なのに優先表示・プロンプトの微調整で「直す」のは **soft cheat**(ベンチ特化の調整)であり、一般経路の修正が正解。

## 5. 測定は positive しか証明しない — 棄却の根拠に使わない

オーナーの挑戦(2026-06-19): 「改善案についてメジャーメントで判断するのは間違い。**限られた環境で、他の環境で改善できないことをどうやって証明するんですか**」。

- 測定が証明できるのは **positive**(この環境で効いた)だけ。限定環境の negative を「どこでも効かない」に一般化するのは論理として不当。
- 改善案(指針・プロンプト改善など)の採否は**設計判断**で行う: 健全か・低コストか・害がないか・他環境でもっともらしく有益か。「自分の環境で測れなかった = 棄却」は誤り。
- 例外: **構造的冗長**(その系が構造的に同じことを既にやっている)は環境非依存の事実であり、測定なしの棄却根拠として正当。

## 6. 再現できない環境の性能問題は、確認でなく反証で診断する

自分の環境で再現しない性能劣化・フリーズ(相手のマシンでのみ発生)に、静的プロファイリング由来の修正を出して「直した」と言わない。実測: 静的解析上は本物の改善だった修正が、相手のフリーズには**効果ゼロ**(真因は別経路)だった。以後の誤修正2件を防いだのは反証の連鎖である:

1. **設定レバーの A/B で、仮説サブシステムを丸ごと反証する**: 仮説の層を迂回する設定を相手に切り替えてもらう。症状が残れば仮説全体(過去の修正込み)が1発で棄却される。最安・環境非依存 — 最初に打つ。
2. **イベントログの間隙で挟み撃ち**: 同期時刻付きイベントの2点間の空白が、無計装の同期コードに故障を局所化する。
3. **スタックダンプが決定打**: ハング中のスタックを1回取れば、詰まっている関数が名指しで分かる。
4. **安い行動分岐の質問**: 「毎ターンか、周期的か」「履歴に画像はあるか」— 無料でサブシステムを絞る。

修正の順序も規律: **確実に正しい最小修正**で急性症状を先に解消し、繊細な最適化(再帰・回復との相互作用が未証明のもの)は追跡番号付きの後続に**分離**する。

## チェックリスト

- [ ] A/B: 各腕の実 import パスを印字確認したか。1点の差分を「範囲全体の因果」に格上げしていないか。直交機構を探したか
- [ ] 数値を出す前: 入力は忠実か。交絡があるなら(注記でなく)checkpoint + 測り直しにしたか
- [ ] 検証ループが正解に触れる測定を、公開スコアとして扱っていないか
- [ ] 「N回」と書く前に線の上を数えたか。`x or DEFAULT` は無いか。ログの単位を名指したか
- [ ] 「直った」の前: N≥5 / 入力と修正表面の重なり / 構造軸と行動軸 / アブレーション / 曖昧さの分解 / soft cheat でないか
- [ ] 限定環境の negative で改善案を棄却していないか(設計判断で採否を決めたか)
- [ ] 再現不能な報告: 静的解析で closed にせず、反証の連鎖(設定レバー→間隙→スタック)を回したか
