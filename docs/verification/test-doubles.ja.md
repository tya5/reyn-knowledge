# テストの偽物は本物の形に合わせる — 見せかけの被覆の6つの作り方

## 中心命題

テスト用の偽物(fake・スタブ・fixture・代役の値)は、**テストを書いた人と同じ思い込みを共有する**。だから偽物を使ったテストは、思い込みが間違っていても**偽物とテストが互いに賛成し合って**緑になる。現実をテストに持ち込めるのは「本物の形」だけである — 本物の型、本物の生産者が作る封筒、本物のリゾルバ、本物のバックエンド、既定値でない値、本物の機構。

以下、見せかけの被覆(カバレッジ)が作られる6つの定番と、それぞれの処方。

## 形1 — fake が、production に存在しないフィールドを発明する

最重症の実例から。権限ゲートがこう書かれていた:

```python
resolver = getattr(rs, "permission_resolver", None)   # rs は共有状態オブジェクト
if resolver is not None:
    await resolver.require_file_write(...)             # ← 一度も発火しない
```

実際の `rs` の型(ただの dataclass)には **`permission_resolver` というフィールドが存在しない**。`getattr` の第3引数が黙って None を返し、ゲートは**全経路で死んでいた**。なのに誰も気づかなかった。テストのスタブがこうだったからだ:

```python
class _RS:
    def __init__(self, factory, resolver=None):
        self.permission_resolver = resolver   # ← production に無いフィールドを「発明」
```

> **handler が読むものを供給していた唯一の存在が、テストの fake だった。∴ ゲートは「テスト済み」に見え、production では発火し得なかった。**

3つの教訓:

- この開発には MagicMock 等を名指しで禁止するテストポリシーがあった。**「モック禁止」の字面は手書き fake を止めない。** `MagicMock` を名指しで禁止するポリシーは守られていた。破られたのは根拠(「偽物は本物の契約を黙って腐らせる」)の方である。**禁止の意味は「MagicMock を使うな」ではなく「協力オブジェクトを偽るな」**。
- **偽の callable と偽の data オブジェクトは、壊れ方が違う。** 偽の関数はシグネチャ不一致で**大声で落ちる**。偽の data オブジェクトは、実型に無いフィールドを黙って持ち、`getattr(obj, "x", default)` は**何も raise せず永遠に default を返す**。
- **本物が安く作れるなら fake を書かない。** この事件の実型はただの dataclass で、本物を構築しない理由が最初から無かった。

検出も難しい: **欠けているものは grep できない**(書かれていないので検索対象が無い)。有効なのは構造的な突き合わせ — 「production がそのオブジェクトから読む全属性名(AST で列挙)」×「実型のフィールド集合」の差分。そして**その検査自体を、欠陥が在ると分かっている版のコードに当てて、検出できることを確かめてから**使う(この手順の詳細は[strip 反証](strip-falsification.ja.md)を参照 — 本件はその検査ツール版)。

## 形2 — fixture の封筒(envelope)が、本物の生産者の形と違う

境界を越えるペイロード(ツールの実行結果、プロセス間メッセージ、API 応答)の中の値を検出・解析するコードのテストで、fixture を**頭の中のモデルから手書きする**と、この罠に落ちる。

実例: 「実行結果がエラーか」を判定する述語が、トップレベルの `status` を見ていた。テストも `{"status": "error"}` という手書き fixture で緑。しかし本物のディスパッチャは全結果を `{"status": "ok", "data": <実結果>}` で**包む**ので、実行エラーは `data.status` に**入れ子**になり、トップレベルは常に `ok`。**述語は本物のデータ58件全てに対して no-op** だった。修正は自分のテストと完全に整合したまま、production を1件も検出しない — **閉じたループ(closed loop)**である。

- fixture は手で打たず、**実トレース・イベントログから写す**か、**生産者のコードを読んで**形を確定する。
- レビュー側: envelope を扱う修正では、**fixture が本物の生産者の形と一致するか**を生産者側の grep で確認する。「fix がテストを通る」は fixture が正しい前提でしか意味を持たない。
- 一様なラッパで包む系では、生の status は必ず入れ子になる — トップレベルだけ見る検出はほぼ確実に間違い。

## 形3 — None・permissive な既定値が、検査を素通しにする

強制(enforcement)を守るテストが、**リゾルバに None を渡して**いた。その経路では、リゾルバが無い場合は寛容な既定(fail-open)に落ちて許可される — つまり**宣言(ツールが必要とする権限の宣言)が欠けていても許可される**。テストは宣言の有無と無関係に緑で、守るべき「宣言が無ければ拒否」を検証できない。

- 権限・強制系のテストは**本物の(None でない)リゾルバ**を構築して通す。
- そのうえで反証する: **宣言を消したらテストが落ちる**ことまで確認して初めて、宣言を守るテストである。

## 形4 — fake バックエンドは、本物のバックエンド自身の組み立てを検証できない

録音・記録型の fake バックエンドを注入した単体テストは、**呼び出し側のロジック**を検証する。しかし**本物のバックエンドの組み立て**(コンテナ実行の引数列、`-i` フラグ、標準入力の転送)のバグは、本物を動かす統合テストでしか捕まらない。実例: fake での単体は緑、本物の `docker exec` には `-i` が無く、標準入力が黙って捨てられていた。

- バックエンド統合系の PR では「単体緑 = 統合確認済み」を認めない。**本物のバックエンドを1回動かす e2e** と、**組み立てた引数列そのものの assert** を要求する。

## 形5 — 既定値での往復(round-trip)テストは自明に通る

`設定 → 再読込 → 取得` の往復テストで、**フィールドの既定値と同じ値**を書くと、**書き込みが no-op でも通る**(再読込は書き込みと無関係に既定値を返すから)。実例: 全設定項目を「それぞれの既定値」で往復させて 113/113 合格 — その中に、**ローダーが一度も読まない配線切れのフィールド**が混ざっていた。

- 往復・恒等系のテストは**必ず既定値と異なる値**で行う(整数なら+1、bool なら反転、文字列なら追記)。

## 形6 — テストの主張と中身がずれている(代理検査)

docstring が「ローダー/リゾルバ/ランタイムを検証する」と主張しながら、本体は `yaml.safe_load` + dict の形の assert だけ、というテスト。**本物の機構を一度も呼んでいない**ので、ドキュメントに載っていたスニペットの形が**間違っていても**緑になる — 実例では、間違った形がテストで固定(pin)されたまま merge を通過し、実運用で発火した。モックを使っていなくても起きることに注意。

- 検査手順: 各テストの docstring の**主張**を読む → 本体がその機構を**実際に呼んでいるか**を確認 → ずれていれば、本体を本物の呼び出しに書き換えるか、主張を実態(「スニペットの存在確認」)に格下げする。
- 拡張:「X を忠実に再現する」系の主張は、集約レベルの反証テストだけで受けない(全体を丸ごと壊せば RED になることの確認だけで、各部品の忠実さは確認していない)。**各構成要素を本物の対応物と 1:1 で照合**する(集約の反証は「集約のロジックが動く」ことしか証明しない)。

## チェックリスト

- [ ] fake が供給する属性は、実型に存在するか。本物が安く作れるのに fake を書いていないか(形1)
- [ ] fixture は実トレース由来か、生産者のコードと照合済みか。入れ子を確認したか(形2)
- [ ] 強制系のテストに本物のリゾルバを渡し、宣言を消すと落ちることを確認したか(形3)
- [ ] バックエンド統合は本物で1回動かしたか。組み立てた引数列を assert したか(形4)
- [ ] 往復テストの値は既定値と異なるか(形5)
- [ ] テストの主張と本体の呼び出し先は一致しているか。「再現する」は要素ごとに照合したか(形6)
