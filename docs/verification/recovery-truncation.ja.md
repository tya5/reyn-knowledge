# 復旧の源は破壊を生き残るか — 往復の緑では足りない

## 問題の形

イベントログから状態を再構築する仕組み(イベントソーシング、先行書き込みログ、チェックポイント+差分再生)を持つシステムでは、ログは普通**切り詰め(truncation)・圧縮(compaction)・ローテーション**の対象である — 無限に伸ばせないのだから当然だ。生き残るのはスナップショット(その時点の全状態の写し)だけ、という設計が典型になる。

ここに定番のデータ喪失バグがある:

> **復旧に必要な状態を、切り詰められるログのイベントから再構築している。ログが切り詰められた瞬間、再構築の源が消え、その状態は二度と戻らない。**

そして最悪なことに、このバグは**「書き込み → 再構築」の往復テストが最初から最後まで緑**である。切り詰めが起きるまで、何も壊れて見えない。

実例: 耐久性の再設計レビューで、オーナー(そのシステムの責任者)が**2件の実データ喪失バグ**を掘り当てた。(1) 設定値をログイベントとして永続化していた(レビュー承認済みだった)、(2) 実行主体の識別情報をログから再構築していた(既存バグ。ログを途中まで再生して復元すると、実行主体が別の主体として蘇りうる、セキュリティ性質を持つ穴)。**根は同一** — どちらも「切り詰めを生き残らない源」から復旧状態を作っていた。

## なぜ見落とされたか(2つの根本原因)

1. **正の検証しかしなかった。** 「書き込んで再構築できるか?」(できる)は確認した。「**何がこの再構築の源を破壊するか?**」は誰も問わなかった。
2. **システム既存の不変条件に、新機能を照合しなかった。** このシステムは元々「ログは切り詰められる。生き残るのはスナップショットだけ」という原則で動いていた(既存の主要状態がスナップショットにあるのはそのためだ)。新しい機能を追加するとき、この既存原則に当てなかった — ログを頭の中で「永続の記録」として扱った。

オーナーの捕捉方法は一般化できる: 「**このシステムではログは切り詰められる。それでも X は確実に取れるか?**」— システムが持つ**破壊の性質を、新機能に敵対的に当てる**質問である。

## 規律

1. **再構築の源を特定し、破壊のライフサイクルに通す。** この状態の復元は何を源にするか? その源は切り詰め・圧縮・ローテーション・GC を生き残るか? **ログイベント由来なら、スナップショットに含める**(または切り詰め免除を明示する)。
2. **truncate 反証(truncate-falsify)テストを必須ゲートにする:**
   ```
   X を設定する
   → X の源となったイベントより先までログを切り詰める
   → 再構築する
   → X が生き残っていることを assert する
   ```
   源がログ由来のままなら、このテストは機械的に RED を出す — **このクラス全体を1本の形で捕捉する**。なお、このテストは「X 自身の記録を壊す構成でなければ意味がない」という[strip 反証](strip-falsification.ja.md)(機構を意図的に壊して RED を確かめる手法)側の規律に従う(X の記録が残っているなら復元できて当然)。
3. **習慣**: 復旧用の状態を見たら即座に問う — 「これはログ由来か? → 切り詰めで壊れる → スナップショットへ」。
4. **「再構築できる」を「完了」と報告しない。** 破壊のライフサイクルを通した検証までが完了の定義である([文脈を持たない主張](cross-context-claims.ja.md)の完了報告の規律)。

## 一般化 — 「破壊者」はシステムごとに違うが、質問は同じ

切り詰めはこの実例の破壊者にすぎない。キャッシュの追い出し、TTL(生存期間)切れ、保持期間ポリシー、コンパクション、スキーマ移行 — **あなたのシステムで「消すことが正常動作であるもの」すべて**が同じ質問を要求する:

> **この復旧・監査・課金・識別の源は、システムが正常動作として行う破壊を生き残るか?**

[census と structure](census-vs-structure.ja.md)の言葉で言えば、「ログのエントリは切り詰められうる」は**構造的前提**(それがログというものの契約)であり、「今はまだ切り詰めていない」は census(ある時点の観測の集計 — 詳細は census と structure 参照)にすぎない。

## 実践方法

- [ ] 復旧・耐久性の機能で、再構築の源を1文で言えるか
- [ ] その源を破壊する正常動作(切り詰め・追い出し・保持期限)を列挙したか
- [ ] truncate 反証テスト(X の源を壊してから再構築 → X 生存を assert)を追加したか
- [ ] 新機能を、システム既存の破壊系の不変条件に照合したか

## 出典(reyn 開発での実測)
