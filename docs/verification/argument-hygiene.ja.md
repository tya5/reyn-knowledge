# 論拠の衛生 — 結論の手前で掛ける6つの検査

検証の失敗の多くは、測定より前 — **論拠を組み立てる段階**で仕込まれる。本ドキュメントは、結論を書く直前に掛ける6つの検査である。どれも実測された事故から来ている。

## 検査1 — 「X には Y ができない」は、症状からは言えない

> **「できない」は機構(mechanism)についての主張である。しかしそれは症状(symptom)から作られる。出力は「何が起きたか」を教えるが、「その物に何ができるか」は決して教えない。**

実例: あるライブラリが壊れた PDF に対して文字列 `'None'` を返すのを見て、「このライブラリは成否を区別**できない**、だからラッパでも区別できない」と3回主張し、3回とも間違った。実測すると: 下層のパーサは**例外を投げていた** → ライブラリはそれを捕まえ、専用の例外クラスまで**持っていた** → 最後の変換器の1つの None チェック漏れが `str(None)` を「成功」として返していた。**信号はすべての層に存在し、死んだのは最後の1箇所** — 見ていたのは最後の箱だけだった。

- 「できない」「方法がない」「未対応」と書く前に: **自分が見た層と、その1つ下の層を名指しできるか**。下の層を名指せないなら、それは症状の観測から能力を推論している。
- **同じ入力クラスで挙動が割れたら(片方は例外、片方は `'None'`)、それは「区別できない」の証拠ではなく「2つのコード経路がある」ことの標識**である。
- 変種1(宣言から): 「この経路のゲートが deny」は「**どの経路からも届かない**」を意味しない — ディスパッチ経路が複数ある系では、**全経路を数えるまで到達不能を結論しない**。
- 変種2(字面の不在から): 呼び出し側ファイルに引数名が grep で出ないことは、渡していない証拠にならない — 引数は**import された共有ヘルパーの中で、呼び出し時に**渡されうる。1段開けば割れる。
- **「できない」の散文は self-sealing**(自己封印的)である: 「守っている」という嘘は deny が出ないことで反証できるが、「できない」という嘘は**誰も試さないので嘘のまま残る**。
- オーナーや peer が「実際に使える」と言ったら、それは一次データ。**先に自分の追跡の穴を探す**。ライブラリの API 面(オプション・例外クラス・結果フィールド)を読むのは30秒で、結論を反転させうる。

## 検査2 — コードの「無い」は、忘れたのか決めたのか区別できない

> **コードは「何が起きるか」を語るが、「それが選ばれたことか」は語れない。** grep の上では「忘れられて無い」と「決めて無い」は同一に見える。

実例: あるディレクトリに TTL も上限も掃除処理も無いことを見つけ、「未実装の欠落」として起票が推奨された。しかし docstring を読むと「**ディスク使用量は無制限に増える。運用上の既知の注意点として文書化済み**」「**Phase 2 の予約: 実測の圧力が出たときに(仮説ではなく)**」— つまり**意図的に受容され、再訪の発動条件まで固定された決定**だった。起票していれば、決定済みの非問題にチケットを作り、doc 自身が定めた条件を満たさないまま前倒しするところだった。

- 「機構が無い」を見つけたら、消す・足す・起票する前に、**その不在が決定として散文に記録されていないか読む**(docstring の "Phase N reservation" / "out of scope" / 運用委任の明示、設計記録、issue のスレッド)。
- 決定が見つかったら、**発動条件が満たされているか**まで確認する。条件付き先送りを条件未達で覆すのは、他人の決定の上書きである。

## 検査3 — 外挿はレビューでは死なず、使う工程で死ぬ

実例: 「このパターンを含む 40 ファイル − 対処済み 7 = **残り33が壊れている**」という主張が、実装者・リード・独立検証者の**3人のレビューを全員通過**した。殺したのはレビューではなく**作業**: そのファイル群を移行しようとした人が中身を開かざるを得なくなり、`grep -c 'import 対象'` = **0**(母集団の定義が違った — パターンを含む ≠ 対象に依存する)。2回の grep で終わる検査が、使用の工程まで一度も回らなかった。

> **レビューは主張のもっともらしさを検査する。使用は主張の指示対象(referent)を強制的に開く。もっともらしい外挿はレビューに強く、使用に弱い。**

- 数値の主張(「N のうち M が壊れている」)を伝播する前に、**それを使う最小の一歩**を踏む — 母集団から1件開くだけで割れる。
- **劇化は増幅であって検査ではない**(「あなたはこの発見を小さく見積もっている」と言い添えて転送した — それが増幅だった)。
- 数を主張できないときの正しい形: 「直接検査した6件は該当。残り27は未検査。**だから数を主張しない**」。

## 検査4 — 譲った論拠は、名前を変えて戻ってくる

実例: 「inline コメントは同じ diff に出るから stale が見える」という主張が実測で反証され、受け入れて撤回した。その**2ターン後**、「(別形式は)劣化していくから inline を増やすべき」という**新しい条件**を提出した — 指摘された通り、「劣化する」は inline にも別形式にも真であり、**drift 耐性で負けた論拠を劣化耐性と言い換えて再提出**していた。

- 条件・要件を1つ足すときの自己照合: **「この条件が守ろうとしている性質」を一語で言い、それが今回のスレッドで自分が譲った主張の性質と同じでないか**を見る。
- **「一般に真だが、比較には効かない」性質が典型的な変装**である。両方の選択肢に真な性質は、どちらかを選ぶ根拠にならない。比較の根拠になるのは**片方だけが持つ性質**。
- 答えが既に**検出条件**として存在していないか見る — 劣化を「防ぐ」条件を足す前に、「検出可能にする」要件が既にあった。

## 検査5 — 形は候補を与える。理由だけがクラスを与える

> **修正が構造的である ⟺ 欠陥が「なぜ」存在するかを言えて、取り除いたのがその「理由」である。形だけ取り除いたなら、それは個別(instance)修正である。**

運用形は「**N+1 件目を名指せるか**」— N+1 を名指せるのは、N がなぜ起きたかを知っているときだけだ。そして「理由の顔をした形」が2種類ある:

1. **高度を間違えた理由はまだ形である。**「理由は `name == "X"` が条件に入っていることだ」はコード行の言い換え。本物の理由(「監査の網羅が、出来事ではなく呼び出し側の surface 選択に束ねられていた」)は、**コードを書き直しても生き残る**。特定の識別子や行番号を名指す「理由」は形の変装を疑う。
2. **反証できない理由は何も閉じない。**「誰も考えなかったから」は理由の顔をした無力な文。**使える理由は「このクラスが他のどこに現れるか」を予測する** — 次の事例を予測できない理由は、理由ではない。

- 直す前に「この欠陥はなぜ存在するのか」を1文で書く。書けないなら、まだ個別しか見えていない。「理由を言えない」は正当な報告である(言えないままゲートを作ると対象が開いたまま固定される)。
- 機構を再利用したくなったら、「形が同じか」ではなく「**理由が移るか**」を問う。想起自体は禁じない — 検証なしの採用だけを禁じる。却下するときも「思いついたこと」ではなく「転移しないこと」を却下すると明示する(そうしないと、検証すべき候補自体が出てこなくなる)。

## 検査6 — 「急がない」と「決めていない」は別の軸

> **「急がない」は「いつ」に答え、「決めていない」は「そうするか」に答える。混ぜると、未決のものが「決定済みで後回し」の身分を静かに手に入れる。**

なぜ致命的か: **決まったように見えるものを、誰も再オープンしない**。「決めていない」なら誰かが決めに来るが、「決めたが急がない」は放置が正当に見える。実例では、この混合の結果、あるアークの構造作業が「閉じた issue」と「決定チケット」の隙間に落ち、どこにも起票されていなかった。

- 対処は常に1句で済む: 「**決定済み: X をやる。急がない**」または「**未決: ○○の判断待ちで停止**」。混合だけが不正で、どちらの純粋形も正当。
- 他人の「急がない」を読んだら、どちらの軸か聞く。答えられなければそれは混合である。
- 作業のまとまり(アーク)を閉じる瞬間が、この区別を強制できる最も確実な地点 — 残件は「起票」か「明示的な破棄」のどちらかに決着させ、「次のアークで」を認めない。
