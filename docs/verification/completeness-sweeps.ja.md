# 完全性掃討の実務 — クラスを閉じる列挙の技法

[列挙の規律](enumeration-discipline.ja.md)は完全性の主張が「どう壊れるか」(切り詰め)を扱った。本ドキュメントはその実務側 — **欠陥をひとつ直したとき、同じクラス全体をどう閉じるか**の技法集である。[fix-class レビュー](fix-class-review.ja.md)がレビュアの問いなら、こちらは実行者の道具箱にあたる。

## 1. 資源系の修正は、兄弟サイトの掃討を即座に発動する

無制限入力・資源枯渇・DoS 系のバグを1箇所直したら、**同じ脆弱性クラスの兄弟サイトの掃討を同時に行う**。実例: HTTP 取得の無制限ボディに上限を入れた修正が、同じ「無制限入力」クラスの兄弟(別の HTTP façade、WebSocket の受信フレーム、サブプロセスの標準出力)を取り残し、後日の専用掃討で初めてクラスターとして発見された。

- 修正 PR に**兄弟掃討の結果表**(同パターンの grep → 各サイトを 修正済み / 該当なし / 起票済み に分類)を含める。
- 特に危険な2形: **"safe" を名乗る façade が無制限**(名前が安全を約束している)、**設計済みだが未配線のフラグ**(`truncated` フィールドが存在するのに常に False)。
- 修正は一様な機構+単一ソースの上限値で(リテラルを各所に重複させない)。

## 2. 並行経路 — 判断の重複が、片方だけ遅れる借金を作る

同じ関心事を持つ**N 本の並行経路**の1本でバグを直すと、残りは黙って古いままになる。実例: 「格納するのは生のペイロードであって、包み紙ごとではない」という修正を経路A(辞書ベース)に入れて出荷 → 利用者は経路B(文字列ベース)で同じバグを踏み続けた。2本が乖離した根因は、**判断(「どれが生のペイロードか」)が両経路に重複して存在した**こと。

- **並行経路の掃討**: 経路Aを直したら、同種のハンドラ(オフローダ・ディスパッチャ・直列化器)を grep して各経路を確認する。
- **機構ではなく判断を一本化する**。2経路が同じ判断を下すなら、判断は1つの共有ヘルパーに置く — 重複した判断は乖離の借金である。
- ゲート・ルーティングに分岐を足す修正の正しい形は2つ: (a) **全並行メソッドを列挙して各に追加**(+対称性テスト)、(b) **共有ロジックを単一の継ぎ目(seam)に集約** — サイトごとの確認が不要になるので取りこぼしが構造的に不可能(completeness-by-construction)。可能なら (b) を選ぶ。
- ただし乖離には**本質的なもの**もある(出力の行き先が違う等)。どこまで一本化するかは「出力がどこに着地するか」を追って判定し、**偶発的な乖離だけを共有**する。過剰な統一はモード切替の複雑さという別の借金になる。
- 並行経路の修正の反証は、**取り残されていた側の経路で**行う(直した側はもう緑に決まっている)。

## 3. 網羅は「意味」で組み立てる — 単一機構の呼び出し元 grep ではなく

「X を列挙・表示する全 surface で隠す」という掃討を、`list_names()` の呼び出し元 grep で回した実例: CLI の一覧コマンドだけが**別の機構(ディレクトリの直接走査)**で列挙しており、grep に乗らず取り残された(委譲は「見つからない」と言うのに一覧には出る、という挙動矛盾として実使用で発覚)。

- 網羅は**意味の要件**(「エージェントを列挙する全 surface」)で組み立てる。単一 API の呼び出し元 grep は網羅の証明にならない。
- 最低2手: 正規の継ぎ目の呼び出し元 grep + **別機構の存在を仮定した第二の探索**(または surface の種類一覧を1つずつ確認)。
- 静的な掃討の取りこぼし検出器として、実使用(live/dogfood)が効く — grep に見えない surface も、挙動の矛盾として現れる。

## 4. 「B 以降 X は起きない」の証明は表である

「barrier B の後に X は起きない」型の不変条件(「静止後にログ追記なし」「シャットダウン後にイベントなし」)の証明は、「B は明白な集合を待つ」ではない。**X を生産しうる全ソースを列挙し、各ソースが B に gate されていることを示す表**である。

実例: 静止プリミティブは「明白な実行中集合」を待っていたが、全タスク起動箇所の grep による被覆証明で、**gate されていない追記可能タスクが3つ**見つかった(タイマー・介入ディスパッチ・追跡されない fire-and-forget タスク)。どれも稀にしか発火しない競合なので、レビューだけでは決して捕まらない。

- 手順: (1) 対象範囲の全タスク起動・イベント源を grep、(2) 各について「X を生産しうるか」、(3) 生産しうるものは「B に gate されているか」、(4) `ソース → X生産? → gate?` の**表を成果物にする**(空欄が目に見える形)、(5) X 生産ソースの型ごとにテスト1本。
- **追跡されない fire-and-forget タスクが定番の穴**(join する handle が無い)。修正はたいてい「join 可能な集合で追跡する」。

## 5. registry の軸と seam の軸 — 列挙する前に「どの軸を覆うのか」を決める

レジストリ(登録簿)からの列挙は、**そのレジストリが数える軸**しか覆わない。欠陥はしばしば**値が境界を越える場所(seam)**に棲み、seam はどのレジストリにも載らない。

実例: 「全ツール定義が浅いコピーで外部に流出し、外部ライブラリの in-place 書き換えで正典スキーマが恒久破壊される」欠陥のゲートが、3本の腕すべてを**ライブレジストリから列挙**して「将来登録されるツールも初日から覆う」と主張した。**ツール軸では全数、seam 軸では部分** — 未修正の流出点が別ファイルに残っており、しかもこの問題を起票させた当のツールがそこから壊れていた。

- **seam は値の側から列挙する**: 正典が外に出る**投影の式の形**(`dict(x.parameters)`)を repo 横断で grep する。ツール名を数えても永久に出ない。
- **N 本の腕が同じ1つの呼び出しを通っているなら、それは N 個の seam ではなく、1つの seam の N サンプル**である。
- 同形の式が2サイト以上ある fix-class は、サイトを個別に直さず**投影を1つにする**(責務を持つ唯一のヘルパーを全サイトが呼ぶ)。ただし**ヘルパーの契約の assert は、seam ごとの witness の代わりにならない**([配線テストと機構テスト](wiring-vs-mechanism.ja.md)の「正しさと到達は別の assert」)。
- 第2の形: **「1箇所を導出に変えた」≠「その値がどこにもハードコードされていない」**。導出化したら、**値のリテラル側から** tests/ を横断 grep する(概念名ではなく `"category"` のような具体値で)。実例では、セルを1つ登録した瞬間に、そのセルを「未登録の例」としてハードコードした3つの**別の**テストが RED になった。
- 派生: テストの**否定例は、システムが拡張していく空間の「外」から取る**(「集合にまだ入っていないもの」ではなく「入りえないもの」)。期限付きの否定例を置くなら、期限を明記する。

## 6. grep の及ぶ範囲 — src/tests だけでは clean-break にならない

依存・機能の完全撤去(clean-break)の完全性ゲートは「`src/ tests/` の grep = 0」ではなく、**全 repo grep − 歴史的許可リスト**(存在した事実を正当に記録する ADR・決定文書)である。実例で src/tests 範囲の grep を通()した後に見つかった3つの取り残し: **ロックファイル**(pyproject から extra を消しても re-lock しなければ依存は再インストール可能)、**サンプル設定**(`*.example`)、**`.gitignore` の死んだ規則**。

- 掃討対象に含める: ロックファイル(re-lock + check を同一 PR で)、サンプル設定、ignore 系、CI 設定、パッケージンググロブ、docs。
- **リネームは「旧名の clean-break」である**。掃討には **LLM に見えるテキスト**(他ツールの説明文・プロンプト・メニュー)を含める — 説明文中の旧ツール名は散文ではなく、**モデルに存在しないツールを呼ばせる生きた呼び出しサイト**である。規範ファイル(エージェントが作業前に読む指針)も同様。

## 7. パッケージ移動 — 参照は3クラスある

パッケージの移動(`X/` → `group/X/`)で掃くべき参照は3クラスあり、import の grep は1クラス目しか捕まえない:

1. **ドット付き import**(複数行の括弧ブロックは単一行 grep が取りこぼす)
2. **ドット付き文字列リテラル**(パッケージングのグロブ、AST ゲートのリテラル、動的 import 文字列)
3. **セグメント合成のファイルパス読み**(`_SRC / "web"` のような形。どちらの grep にも不可視)

さらに: 対象は **src + tests + scripts + 補助ディレクトリの全 import 元**。移動パッケージ内の**絶対自己 import**。パッケージ名が**実行時データディレクトリ名と衝突**する場合はランタイム側のリテラルを**書き換えない**(逆の欠陥になる)。入れ子が深くなる移動では **`__file__` からの親ディレクトリ歩き**を grep する — テストがパスを注入していると CI では**隠される**ので、注入なしの既定経路を叩くテストを要求する。恒久形はモジュール自身でなく**パッケージルートを錨にする**パス解決。

シンボルのリネームにも固有の4点: **新名の衝突を事前 grep**(既存シンボルへの上書きは CI で検出できない静かな誤バインド)、**コード文脈パターンだけで置換**(裸の単語置換は散文を壊す)、**兄弟シンボルの件数を前後で記録**(外科的だった証明)、**フルスイートを最後の網**とする(サブプロセス用コード文字列内の裸シンボルはパターンに乗らない)。

## 8. 検索ツール自体が過少報告する

完全性の主張は、検索ツールの健全性に乗っている。実測された2つ:

- **`git grep` は tests/ で黙って過少報告することがある**(9ファイル中2つしか出さなかった実測)。削除・参照ゼロの主張には **plain `grep -rn` を正**とする。食い違ったら plain grep が勝つ。
- **LSP の findReferences には2つの無音故障がある**: (a) コールドスタート直後の1回目は定義しか返さない(2回目から正しい)。(b) **git checkout / 外部ツールの編集などプロセス外のファイル変更後は、索引が古いまま「正しい現在の行」に対して偽のゼロを返す** — しかも安定して0なので再試行でも見抜けない。安全に関わる「残り呼び出し元 = 0」主張は必ず plain grep と突き合わせ、**測定した木の状態(commit)を記録**する。
