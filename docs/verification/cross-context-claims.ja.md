# 文脈を持たない主張 — 助言・委任監査・完了報告のラベル

## 問題の形

複数のエージェント(や人)で開発すると、主張は絶えず**知識の境界**を越えて流れる。設計助言者は実装の詳細を持っていない。委任された監査エージェントは設計判断の経緯を持っていない。実装者はオーナー(プロジェクトの持ち主)の頭の中の最終形を持っていない。

境界を越える主張そのものは正常である。壊れるのは、**主張が「自分の持っていない文脈に依存する部分」を、持っているかのような断定形で運ぶ**ときだ。3つの頻出形がある。

## 形1 — 実装詳細に依存する設計助言は、検証するか、保留を明示する

設計の方向づけ(design steer)が「この状態は誰が持つか」「この値はキャッシュできるか」「この不変条件は何か」「この関数は同期か非同期か」といった**実装詳細に依存する主張**を含むとき、選択肢は2つしかない:

1. その詳細を**一次ソース(実装)で確認してから**断定する
2. 確認できないなら「**この点は X の一次確認待ち。実装側で検証を**」と明示的に保留(hedge)する

実例: 1つの設計ウェーブ(ひとまとまりの設計作業)で、リード役の設計助言が実装側の一次証拠によって **3回**正しく訂正された — (a) 提案した実装分割が既存の「一覧と詳細は単一ソース」不変条件を破る、(b) 同期の事前構築を提案した対象が実際には非同期関数+動的入力で事前計算不可、(c) 「呼び出し側が自分の状態として持てばよい」とした対象が実際には共有シングルトンで、並行実行で衝突する。3件とも高レベルの方向づけ自体は有用だった。**結論を左右する(load-bearing)詳細を未確認のまま断定した**ことだけが問題で、先に保留を付けていれば往復は不要だった。

## 形2 — 委任された監査の「判定」は、事実だけ受け取って判定は自分で再計算する

読み取り専用の監査をサブエージェントに委任すると、返ってくる**判定**(「これは削除のブロッカー」「これは安全」)は**コードだけから**計算されている。サブエージェントはオーナーの設計判断も、契約(コンポーネント間の取り決め)の背景も持っていない。

> **サブエージェントは「何が壊れるか」を正しく見つける。しかし「壊すことが目的かどうか」は原理的に知り得ない。**

実例: 削除 PR(pull request)の影響監査を委任したら「この復元機能が壊れる = 削除ブロッカー、ユーザー可視の退行」と報告された。だがその除去こそ**オーナーが決めた削除の眼目**だった(その復元挙動が引き起こす衝突を直すための削除)。正しい処理は: (1) **事実の地図**(呼び出し箇所、それぞれのフォールバック)は資産として受け取る、(2) **判定は自分がオーナー文脈で再計算**する、(3) 結論を左右する主張1点は自分で直接確認する。付記: サブエージェントの**範囲の要約も過小になりうる**(「唯一の役割は X」と報告された層が実際には Y も担っていた)— 範囲は自分で導出し直す。

## 形3 — 「動く版が載った」と「意図された設計が載った」は別の完了

オーナーの設計提案に由来する作業の完了報告は、**着地(変更が本流に取り込まれ稼働すること)した形がオーナーの意図した最終形か、それとも簡易版か**を明示的に判定してから書く。

実例: 耐久性の設計で、オーナーが提案した最終形(担当ワーカーが採番と書き込みを直列に持ち、ロックを廃する)ではなく、**意識的に段階を分けた簡易版**(呼び出し側がロック下で採番)が着地した。それを「完了・着地」と報告した結果、オーナーが「これは私の期待と違う。次のステップなの? 理解できていないの?」と**2回問うてはじめて**乖離が表面化した。

- 簡易版・段階版なら「**最終形の手前で稼働中。残りは X**」と**先回りして申告**する。「complete / done」と単純化しない。
- 段階分けが**オーナー合意済みか、実装側の一存か**を確認する。
- 「着地した?」と聞かれたら、機能の有無ではなく**設計意図との一致度**を答える。

## 統一形 — 主張に「計算した文脈」のラベルを付ける

[測定対象のずれ](measurement-target.ja.md)の MEASURED / READ / INFERRED(実測した / 出典を読んだ / 推論した、を示す証拠ラベル)が「証拠の種類」のラベルだとすれば、本ドキュメントは「**文脈の範囲**」のラベルである:

> **この主張は、どの文脈まで見て計算されたか — 実装を確認済みか、コードのみか、設計意図と照合済みか。**

ラベルのない断定は、受け手には全文脈確認済みの主張と区別がつかない。そして訂正のコスト(往復・誤ブロック・オーナーの再質問)は、常にラベル1行より高い。

## 実践方法

- [ ] 設計助言を書く前に: 依存する実装詳細を一次確認したか。できないなら保留を明示したか
- [ ] 委任監査の受け取り: 事実と判定を分離したか。判定を文脈込みで再計算したか。結論を左右する主張1点を直接確認したか
- [ ] 完了報告の前に: 着地形は意図された最終形か簡易版か。簡易版なら残りを明示したか。段階分けは合意済みか
- [ ] 断定形で書いた各主張に「どの文脈で計算したか」を添えられるか
