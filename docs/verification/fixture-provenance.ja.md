# fixture の出自を証明する — 「録り直した」を信じずに確かめる

## 背景 — record/replay テスト

LLM を呼ぶアプリケーションのテストでは、**record/replay 方式**がよく使われる: 実際の API 応答を一度録画(record)して fixture(テスト用の保存データ)に残し、CI では録画を再生(replay)する。決定的で、高速で、API 料金もかからない。

このとき、リクエストのペイロード(送信内容)に影響する変更(ツールの説明文、システムプロンプト、スキーマ)を入れると、**fixture の録り直しが必要**になる。そして実装者から「fixture を録り直しました」という申告が届く。

## 問い — 申告を、成果物だけから検証できるか

「実物から録り直された fixture」と「テストが通るように手書きされた fixture」を、成果物だけから区別できるか。fixture の中身を眺めても、照合先は「replay が緑になること」しかないように見える。そして**緑は「正しく録れた」と「たまたま通る値を書いた」を区別しない**。

## 答え — 変更前のコードと組み合わせて RED を見る

replay の照合キーがリクエスト内容のハッシュを含む(これが record/replay 実装の普通の作りである)なら、**fixture のキーは録画時点のコード実体から一意に決まる**。そこで2方向の実験を組む:

| 実験 | 期待 |
|---|---|
| ① 新コード + 新 fixture(PR のまま) | passed |
| ② **旧コード + 新 fixture**(意図的な不整合) | **failed** |

**②の RED が担保である。** もし fixture が新しいコードと無関係な値で通っていたなら、コードを旧に差し替えても passed のままのはずだ。旧コードと組むと壊れる = この fixture は新コードに固有に対応している = 実体から録られた。手書きで「たまたま通る値」を入れた場合、②で RED になる保証はない — 同じ実験が識別に使える。

> **「録り直した」という申告ではなく、「録り直した対象への依存」を測る。**

[strip 反証](strip-falsification.ja.md)が「機構を壊すと RED」で**荷重を支えていること(load-bearing = そのテストが実際に機構を守っていること)**を示すのに対し、これは「**相手側を古くすると RED**」で**対応関係(correspondence)**を示す。同じ道具の別の当て方である。

## 手編集を構造的に不可能にする

録り直しの手順自体も、証明が要らない形にできる:

> **fixture ファイルを削除 → record モードで通常のテスト実行 → 実ペイロードから再生成。手で開いて直さない。**

こうすると手編集が**構造的に不可能**になる。処方の一般形は「**もっともらしいが誤った成果物を構築できる経路自体を消す。誰かが偽物だと気づくことに頼らない**」— 手組みのテストダブル(本物の代わりに使う偽オブジェクト)を、安価に構築できるなら本物のオブジェクトに置き換える処方と同じ形である。

なお最悪の回避は「**fixture が落ちるから、変更した説明文を元に戻す**」。テストを通すために PR の価値そのものを捨てる転倒であり、実例ではこれを採らず、fixture 側を録り直して本文の修正を守った。

## 「既存の失敗です」の申告にも決着プロトコルがある

fixture 問題としばしば同時に来るのが「このテスト失敗は main でも再現する既存の問題で、私の変更とは無関係です」という申告である。これも申告のまま受け取らない。

まず、「既存の失敗」のカテゴリは2つではなく**3つ**ある: (1) PR 由来、(2) 環境固有、(3) **実行順序依存**(テストのランダム順序実行が有効で seed〈乱数の種 = 実行順を決める値〉が固定されていないリポジトリでは、実行ごとに落ちるテストが変わる)。失敗件数が実行のたびに変わるのは (3) の兆候であって「悪化」ではない。

決着の手順:

- **申告に seed を含めさせる。** 同一 seed で **main と PR の双方**を走らせる。
- **報告させるのは差集合 P−M(PR でのみ落ちるもの)だけ。**「両方で落ちる」は本 PR の責任範囲外と確定するので、判断材料として不要。「N 件落ちたが main でも落ちる」は、それ単体では何も決めない — 必要な情報は「**PR でのみ落ちるものが 0 件**」という形。
- **CI(固定環境)を最終審級にする。** ローカルの venv(仮想環境)破損のような環境固有の失敗は CI では出ない。ローカル赤 × CI 緑は「環境固有」の強い証拠。
- 自分が判定する側でも、「単独実行で緑」を根拠にしない。比較は**同じ手順・別ツリー**で行う(main をチェックアウトして同じフルスイートを回す)。

一般化: **緑/赤を読む前に「同じ順序・同じ seed で走ったか」を確認する。測った対象が同じでも、順序が違えば別の実験である。**

### 推論で相乗りしない — 観測だけが失敗を確定する

「既存の失敗」申告に**推論で同意(co-sign)する**のも同じ穴である。実例: 仲間の「4件の失敗は既存」という報告に対し、その テストファイルに古い非推奨パターンが**在る**ことを grep で確認して「既存で合意」と署名した — スイートを**走らせて観測してはいない**。後の清浄環境での実測は「**全部通る・main はずっと緑**」。しかも別の検証者が報告した「4件の失敗」は**中身が違う4件**で、そちらも本人が「自分のローカル環境の汚染(古い editable install の残骸、残置された `.pyc` ディレクトリによる誤った名前解決)だった」と撤回した。

- **CI(清浄な固定環境)の緑が、失敗が実在するかの最終審級。** ローカルのフルスイート実行は実行者の環境汚染を運ぶので、それ単体では確定に使えない。
- **検証者ごとに「失敗の集合」が食い違うのは、環境汚染の強い兆候**であって、退行の証拠ではない。
- もっともらしい原因が「コードに在る」ことの grep は**推論**であって観測ではない([監査は内容を照合する](audit-content-match.ja.md)の失敗版)。
- **清浄環境での再現か CI での確認が取れるまで、追跡 issue を起票しない**(偽の issue は他人の時間を使う)。
