# 監査は内容を照合する — 「在る」は「そう動く」でも「そう言っている」でもない

## 問題の形

機能の棚卸し、ドキュメントと実装のずれの監査、ドキュメント間の転記 — これらの作業に共通する失敗がある。**「該当するものが見つかった」ことを「主張が正しい」ことの証拠にしてしまう**のだ。存在の確認は手軽で、つい頼りたくなるが、監査が本当に確かめるべきなのは存在ではなく**内容**(そう動くか / そこにそう書いてあるか)である。

## 形1 — シンボルの存在は「稼働」の証拠にならない

機能一覧の監査で、「外部チャネル連携(Slack 等)は実装済み」と分類した実例がある。根拠は十分に見えた: 転送用のモジュールが**在る**、ルーティングのクラスが**在る**、設定ブロックまで**在る**。ところがソースの中には平文でこう書いてあった — 「**配線はこの PR(pull request = 一まとまりの変更提案)には意図的に含めない。将来の PR で行う**」。全部、先行して置かれた足場(スキャフォールド = 将来の実装のために先に用意された骨組み)だった。

> **シンボル(クラス・設定・ファイル・CLI 項目)が存在することは、機能が配線され動作していることを意味しない。足場は配線より先に出荷されるのが普通である。**

存在の grep(全文検索)は 1 コマンドで済むが、稼働(STATUS)の確認は実装を読むことを要求する。非対称なコストが、監査を存在チェックに堕落させる。そして「足場を本番機能として一覧に載せる」ことは、**その監査が防ぐはずだった『ドキュメントが実装より先に進むずれ』そのもの**を生産する。

**稼働確認(STATUS パス = 存在確認の後に通す第二の検査)の3点セット:**

1. シンボルの近くでスタブ(stub = 中身のない仮実装)の印を grep する: `future` / `Phase 2` / `NotImplemented` / `TODO` / `NOT included`
2. 中身のある(スタブでない)処理本体があることを確認する
3. **生きた呼び出し箇所・組み込み箇所**があることを確認する([生死は producer で判定する](liveness-is-producer.ja.md)(データを書く側の有無で死活を判定する、の意)と同じ軸)

判定は「実装済み / 未実装」の二値ではなく「本番稼働 / 実験的 / オプション依存 / 構想段階(一覧から除外)」に分類し、境界例は黙って含めたり落としたりせず**レビュー判断として表に出す**。

### 派生 — 数えることは検分することではない

同じ監査で、`ls -d */ | wc -l` の結果 15 を「スキル(エージェントの機能単位)15 個」と報告した実例もある。各ディレクトリを検分したら、3つはキャッシュだけの空ディレクトリで、実体は 12 だった。**件数からの外挿は、1件ずつの検分の代わりにならない**([列挙の規律](enumeration-discipline.ja.md))。

## 形2 — 行番号の一致は「主張」の証拠にならない

`file.py:291 にこの挙動がある` という形の記述(file:line 引用)を監査するとき、**その行に何かがあること**の確認で止まってはいけない。**その行の内容が、主張された意味を実際に体現しているか**まで読む。

実例: 「相対パス解決は `file.py:291`」という主張の監査で、リポジトリ内の `file.py` を grep したが、**grep の結果を先頭2件だけ読んで打ち切ったため**、そのうちの1つの 291 行目に `def glob(...)` が**在った**(glob もパス解決系の構文なので、一見それらしく見えた)ので「一致、正しい」と確認してしまった。実際には別の場所に3つ目・4つ目の `file.py` があり、主張が指していた本物はそちらだった。最初の 291 行目の glob 定義は、**偶然そこにあった同種の構文**にすぎない。

- あいまいなファイル名は**全候補を列挙してから**判定する(`git ls-tree -r --name-only | grep '/file\.py$'` を最後まで読む。`head` で切らない — [列挙の規律](enumeration-discipline.ja.md)層1)。
- 「同じ種類の構文がその行に在る」は棄却理由付きで疑う。**主張された固有の挙動**をその行が実装しているかで判定する。
- 監査結果に相手が一次証拠つきで異議を唱えたら、弁護する前に**現行の正とされる版で取り直す**。

## 形3 — ドキュメントの記述は、転記する前に実装で裏を取る

概念ドキュメントに書かれた実装依存の主張(「X は分離されている」「原子的に行われる」「スコープごとに一意」「一度だけ実行される」)を、別のドキュメントへ**転記(mirror)する前に、一次ソース = 実装**で確認する。概念ドキュメントは過大主張していることがあり、検証せずに写すと**誤りが伝播して増幅する**。

- 分離性・原子性・冪等性(何度実行しても結果が同じ)・スコープ・回数・順序 — この種の性質を含む文の転記は、該当実装の grep を伴う。
- レビューの確認軸は「ドキュメントが(内部で)整合しているか」ではなく「**ドキュメントが実装と一致しているか**」。
- 記述と実装が食い違ったら、**実装を正としてドキュメントを直す**(ドキュメントを信じて実装を曲げない)。

これは[census と structure](census-vs-structure.ja.md)の「嘘の記述は不完全な列挙の化石」(化石 = 過去の不完全な調査結果が記述として残り続けたもの)の**入口を塞ぐ**規律である: 検証されない転記こそが、化石が増える経路にほかならない。

## 実践方法

- [ ] 「見つかった → 実装済みと記載」の各ステップに、稼働確認の3点セット(スタブ印 grep / 本体確認 / 生きた呼び出し箇所)を通したか
- [ ] 件数で報告する前に、1件ずつ検分したか
- [ ] file:line 引用は、行の**内容**が主張の固有の挙動を体現しているか読んだか。同名ファイルの全候補を列挙したか
- [ ] ドキュメント間の転記に実装依存の主張が含まれるなら、転記前に実装を grep したか

## 出典(reyn 開発での実測)

形1: #1522(機能一覧監査。ソース内の「配線は意図的に未包含」をオーナーが着地前に捕捉。同 PR でディレクトリ数 15→実体 12 の外挿も)。形2: file:line 監査で grep の先頭打ち切りにより誤った `file.py` の 291 行目を「一致」と確認、peer が一次証拠で訂正。形3: doc→doc 転記時の実装検証規律(2026-07)。
