# 列挙の規律 — 「全部見た」はどうやって嘘になるか

「全呼び出し元を直した」「参照は残っていない」「両バックエンドに適用済み」— ソフトウェアの変更にはこの種の**完全性の主張**が絶えず必要になる。そして完全性の主張は、調査が雑だから壊れるのではない。**丁寧な調査が、決まったパターンで切り詰められる**から壊れる。パターンは3層ある: 出力の切り詰め、クエリの切り詰め、面(surface)の定義ミス。

## 層1 — 出力の切り詰め: 完全性の grep を head に通すな

実例: ある識別子が生きているか調べるために、**正しい綴りで** grep して **65 件**ヒットした。先頭4件だけ見たらテストとログ収集だった。「孤児(どこからも使われていない)」と結論した。**生きているコンシューマは5件目にいた。**

証拠はバッファの中にあった。それを捨てて、**切り詰めが示唆する結論を書いた**のである。切り詰めは常に「もう見るべきものは無い」方向に嘘をつく。

> **完全性の grep を `head` に通してはならない。**
> 1. まず `wc -l`。
> 2. 件数が「実際に読む量」を超えるなら、**一般化してはならない**。全部読むか、**機械的に分割**する:
>    ```bash
>    grep -rn "the_symbol" | awk -F: '{print $1}' | sort | uniq -c | sort -rn
>    ```
>    全ヒットをファイル別・領域別のバケツに落とし、**バケツ単位で**推論する。

この手法の有効性も同日に実証されている: 約98件ヒットの別の掃討では、領域別に分割したからこそ、たった1件の生きたドキュメント残骸を正しく検出できた。**同じ人が同じ日に**、分割をやった掃討では当て、やらなかった掃討では外した。個人の注意力ではなく、手順の有無が結果を分けた。

## 層2 — クエリの切り詰め: 「どの軸で調べたか」を自問する

出力を全部読んでも、**そもそも投げたクエリが足りない**ことがある。

実例: 「両バックエンドに修正を適用した」と PR 本文で断定したが、実際には書き込み権限を発行する箇所が**3つ**あり、見逃した1つは**その PR の看板機能**の側だった。実装者の自己診断が的確である:

> 私は「修正の形」(`expanduser`)と「コンストラクタの形」(`SandboxPolicy(`)を grep した。**どちらの grep も正しく、どちらも間違った問いだった。** 2つの軸で徹底的に調べたから、掃討は完全だと**感じた**。しかし「**このフィールドを誰が読むか**」という軸を一度も問わなかった。

> **間違った軸に沿った徹底は、完全性の「感覚」を生む。その感覚こそが危険信号である。**

掃討を信じる前に問う: **「私はどの軸でクエリしたか。『誰がこれを消費するか』はその中にあるか。」**

## 層3 — 面の定義ミス: 命名規約・書式は面の定義に使えない

列挙の対象となる「面」を、**命名規約や文字列の書式で定義する**と、規約に従わない実体を静かに取りこぼす。

- 実例1: インデックスの孤立エントリを監査するのに `*_family.md` という**ファイル名パターン**だけを走査した。命名規約に従わない統合ファイルを取りこぼし、孤立件数を 73 と報告(実際は 31)。誤りが「**多い方**」に出た点にも注意 — 過大報告は無害に見えるが、他人に不要な作業を頼む寸前だった。
- 実例2: 「内部区切り文字 `__` が残っていない」ことを `"[a-z_]+__[a-z_]+"` という**引用符付き識別子の書式**で grep して「残存ゼロ」と報告した。しかし別ファイルにある表示用テキスト(モデルが実際に読む面)はこの書式に一致せず素通りした。

ここで重要なのは直し方である:

> **人手の grep が可視面を取りこぼしたとき、直し方は「より良い grep」ではない。その面を produce する機械から列挙することである。**

「何が広告されるか」を知っているのはツール登録機構(レジストリ)であって、ソースコードの書式ではない。全登録エントリの**レンダリング済み出力**を機械に列挙させ、その上で検査する。同じ理由で、完全性を守るゲートは「人がもう一度注意深く grep する」ではなく、**レジストリから導出して全エントリを照合するプログラム**にする — 人間が切り詰める場所を構造的に無くす。

## 和と符号 — 結論が「方向」なら、全部の項を列挙する

数値の議論にも列挙の規律がある。実例: 「メッセージ境界あたり +0.9 トークン」という前提は**真で、実測にも耐えた**。失敗したのは `net = (+0.9 × n) − 2` という**2項の和の符号を、第1項だけから主張した**ことである(−2 は結合側だけに現れる括弧のコスト)。

> **結論が方向・符号で、量が和なら、すべての項を列挙せよ。**

この事件には美しい後日談がある: 2人の測定者が「矛盾する」結果を出したが、実際には**同じ和の別々の項を測っていた**(片方の経路には括弧の項がそもそも無かった)。矛盾に見える測定は、まず「同じ対象を測ったか」を疑う([測定対象のずれ](measurement-target.ja.md))。

## 「私は確認した」は完全性の証拠ではない

正しい綴りの grep + 全件読了でも、軸が欠けていれば外れる。人の宣言に依存しない形 — レジストリ導出・全件照合のゲート — に落とすところまでが列挙の規律である。

## チェックリスト

- [ ] 完全性の grep: `wc -l` を先に。読める量を超えたら全読または機械分割(バケツ化)
- [ ] クエリの軸を列挙したか。「誰が消費するか」軸は入っているか
- [ ] 面の定義は producer(レジストリ・生成機構)由来か。命名規約・書式で代用していないか
- [ ] 方向・符号の主張なら、和の全項を列挙したか
- [ ] 最終的な守りは「もう一度注意する」ではなく「導出+全件照合するプログラム」になっているか
