# 一括修正 PR のレビュー — diff に現れない判断を検証する

## 問題の形

**sweep PR(一括修正 PR)**とは、リポジトリ全体を走査して同種の問題をまとめて直す PR である。例: 119 個のステータス記録ファイルを全数監査し、古くなっていた 26 件を修正する。

このタイプの PR に対する自然なレビューは**抜き取り検証**だ: 修正された項目からいくつか選び、一次証拠(実際の PR の状態、commit の実在)と突き合わせる。実例では 11 件を抜き取り、**全部一致した**。ではこの sweep は信頼できるか?

**半分しか検証できていない。** sweep PR の危険は三方向あり、抜き取りが届くのは最初の側だけである:

| 危険 | diff に現れるか | 抜き取りで検出できるか |
|---|---|---|
| 直した項目が誤っている | 現れる | **できる**(一次証拠と突合) |
| 直すべきでないものを直した | 現れる | できる(ただし正しさの基準を自分で持つ必要) |
| **直すべきものを直さなかった / 正しかったものを倒した** | **現れない** | **できない** |

3行目が本丸である。「119 件中 93 件は触らなかった」という 93 個の判断は、**diff のどこにも書かれていない**。

> **一括修正 PR では、「変更しなかった」も判断であり、判断は検証対象である。diff は「した判断」しか見せない。「しなかった判断」は、こちらから探しに行かないと永久に見えない。**

これは「skip されたテストは緑に見える」の文書版である: 「26 件直した」は「残り 93 件が正しかった」の証拠にならない。**未変更は「検査して正しかった」と「見ていない」の区別がつかない。**

## 穴を埋めたレビューの実例

この sweep で独立第二検証者がやったことが、そのまま手本になる:

1. **「倒れそうで倒れなかった」最有力候補を能動的に選んだ。** 「部分的に完了」のまま残置されたファイル — 機械的に処理したら「完了」に倒されていそうな項目である。
2. **残置の根拠を一次証拠で実測した。** そのファイルの主張(「該当モジュールは依然大きいまま」)を `wc -l` で測り(7488 行 / 3903 行)、残置が正しいことを確認した。
3. **diff に引用された PR 番号を信じず、`gh pr view` で引き直した。**

これで初めて「**倒さなかった判断が正しかった**」が証拠になった。

## How to apply

sweep / 一括修正 PR のレビューでは、抜き取り検証に加えて:

1. **「倒れそうで倒れなかった項目」を自分で 1〜2 件選び、残置の正しさを一次証拠で確かめる。** 選び方 = 「機械的に処理したら間違って変更されていたはずのもの」(部分実装・条件付き・例外扱いの項目)。
2. **母集団の数を自分で数える。** 「N 件中 M 件修正」の N を `git ls-tree | grep -c` などで確認する。依頼文に「全数」と書いても、実際に全数を見た保証にはならない。
3. **判定保留が 0 件なら疑う。** 意味判断を含む sweep で保留ゼロは、「全部わかった」より「**保留する基準を持っていない**」可能性が高い。実例では 2 件が保留されており、それ自体が品質のシグナルだった。
4. **diff 内の引用を信じない。** PR 番号・commit・行数は、diff の記載からではなく一次ソース(`gh pr view` / `wc -l`)から引き直す。

## 出典(reyn 開発での実測)

#3186(119 ファイル全数 sweep・26 件修正。レビュアーが抜き取り 11 件全一致で「信頼できる」と結論しかけ、独立第二検証者が「倒れなかった側」の検証で穴を埋めた)。
