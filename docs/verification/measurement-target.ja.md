# 測定対象のずれ — 数字が出ることと、問いに答えることは違う

## 問題の形

**「測っていない」誤りは自分で気づける。「測ったが対象がずれていた」誤りは気づけない — 数字が出るので、検証した気になるからだ。**

このクラスの誤りを、経験豊富なレビューエージェント(レビューを担当する AI エージェント)が**一日で4回**犯した記録がある。4件とも測定自体は正しく実行され、数字も出た。ずれていたのは「**測定の対象**」と「**決定が必要としているもの**」の間である:

| 何を測ったつもりか | 実際のずれ |
|---|---|
| 機能が実装されない理由 | **測らずに推測**し、それを指示であるかのような断定形で相手に渡した。相手は実測済みだった |
| ドキュメント修正の確認 | **行番号**で見た。別の変更で行がずれていた |
| ブランチの変更内容 | **二点 diff**(`git diff main branch`)で見た。他人が先に main に入れた変更が「このブランチの削除」に見える。正しくは**三点**(`git diff main...branch`) |
| インデックスの孤立エントリ(文書索引のうち、実体ファイルを失った項目)の数 | **ファイル名の規約**(`*_family.md`)だけ走査し、規約に従わない実体を取りこぼした(73件と報告、実際は31件) |

対策の第一歩は単純である:

> **測る前に、「この測定は、決定が必要としているものを覆うか」を一文で書く。** 覆わないなら、測っても決まらない — 時間を使って「検証した気」だけが増える。

## 現状を測るか、目標状態を測るか

対象ずれの一段抽象的な形: 「A案とB案のどちらにすべきか」という決定に対して、「**現在どうなっているか**」を測ってしまう。

実例: ツールの実行エラーは LLM に返され、LLM がそれを読んで次の行動を決める。この前提のもと、「エラーを構造化された辞書(error-dict)で返す現行形式と、平文で返す新形式のどちらが良いか」という設計判断に、「LLM は現在この構造化エラーを**どう読んでいるか**」の測定が提案された。却下理由が本質的である:

> その測定は**現状**を測るが、決定は**目標状態**についてである。「今どう読むか」は「変えたら何を失うか」を教えるが、「どちらの目標が良いか」は教えない。

置き換えは「**害を測る**」: 現行形式のせいでモデルが実際に誤っているか。これなら**どちらに転んでも決定的**で、初めて判断材料として機能する。

## 測定 vs 測定の「衝突」— まず「同じ対象を測ったか」

二人の測定が食い違ったとき、「どちらが正しいか」を裁く前に問うべきことがある:

> **二人は同じ対象を測ったか。**

実例: 実装者が「頂いた判定を私の実測が否定します」と訂正を求めてきた。片方は **main ブランチ上で**そのテストを測り(3回に1回だけ再現する不安定な失敗〈flaky〉)、もう片方は**自分のブランチ上で**測っていた(決定的に失敗)。**どちらも正しい** — そのテストの録画キー(録画済み API 応答をリクエスト内容で照合するキー)はペイロード(リクエストの中身)に依存し、ブランチ側の変更(システムプロンプト変更)でキーが必ず変わるからだ。誤りは、main での観測を「ノイズです、あなたの変更とは無関係」と**断定形で相手の木(ワークツリー = チェックアウトされた作業コピー)についての主張として渡した**ことにある。

> **中継規則: 測定結果を他人に渡すときは「どの木で・どの commit で測ったか」を必ず添える。添えられない測定は、渡してはいけない。**

さらにこの事件では、取り直した再測定**自体も** stale(古いまま)だった(リモートでマージした後、ローカルの同期を怠って4コミット遅れの木で測った)。同じやり取りの中で対象ずれを二重に踏める、ということである。

## 述語が粗いと、集合の全員で発火する

監視・自動化にも同じクラスがある。実例: テストスイート完了を検知する watcher(監視プロセス)が同じ対象について何度も発報した。述語(発火条件)が「**そのツリーの venv〈仮想環境〉を含む任意のプロセス**」だったため、リンター(静的検査ツール)が走るたびに「スイート完了」を撃っていた。測っていたのは「スイートの実行」ではなく「そのツリーの何か」である。修正は発火条件を対象と1:1にする(特定の pid〈プロセス ID〉+ プロセス名で追い、pid の消滅で1回だけ発火 — 消えた pid は集合から落ちるので、重複が構造的に起こり得ない)。

## 識別子で測ったら、内容で1つ照合する

4件中3件は、**識別子を対象の代理に使った**ことが原因だった(行番号・二点/三点 diff・ファイル名パターン)。識別子は対象が動くとずれる。識別子ベースで測ったら、**最低1件は内容で照合する**(その行に本当にその文があるか、そのファイルは本当にその種類か)。

なお、誤りは「少ない方」だけでなく「**多い方**」にも出る(73件 vs 実際31件)。過大報告は無害に感じるが、**他人の時間を使う**。

## 数え方の規則自体が争点のとき、MEASURED ラベルは間違ったものを証明する

対象ずれの、もう一段鋭い形がある: **数える規則(何を1件と数え、何を同一視するか)がまだ決着していないのに、出した数に MEASURED(実測した)ラベルを貼る。**

実例: 同じ問いに3人が3つの数を出した — 16件・4組(9パラメータ)・3組(6パラメータ)。**3つとも、実際に実行して出した数という意味では本物の実測だった。しかしどれも「まだ決まっていない選択(何を同一視の対象に含めるか)の関数」だった。**当事者の自己分析(採用):

> **MEASURED というラベルは「私は推測していない」を証明する。だが数え方の規則が争点のときは、「推測していない」が真であっても「数はまだ意見」である。ラベルは前者しか証明しないのに、読み手は後者まで証明されたと読んでしまう。**

- **数え方の規則が争点のときは、MEASURED を規則ごとに書く**: 「MEASURED(完全一致・アダプタ層のメソッドを含む): 3組」のように、規則を数字に縫い付ける。
- **規則がまだ決まっていないなら、総数を出さない。規則と具体例を出す**: 「A と B は消費者集合が完全一致する」は規則が変わっても生き残るが、「16件」は規則が変われば崩れる。
- **自分の数が後で縮んだら、明示的に撤回する。** 実例では、確定値が出た後も前の数字(16件)を訂正しないまま報告済みで、他者の指摘で初めて撤回した。

**副次的な教訓 — 「狭すぎた」を「広くする」で直すと、不完全さの向きが反転するだけで消えない。** 実例では、ある集計が内部の観点だけで測っていた不備を、外部の観点**だけ**で測り直すことで「直した」つもりになった — 一方の不完全な集合を、別の不完全な集合に取り替えただけだった。正しい高度は「狭い/広い」のどちらかを選ぶことではなく、**両方の観点を別個の対象として数える**ことだった。

**反証は総数の突き合わせでなく、規則が何を誤って併合するかを1つ挙げて行う。** 競合する総数は何往復しても決着しない。決着したのは、片方が相手の緩和を「壊す実例」で示したときだった: 「外部の観点だけで測ると、この2つは同一集合に見える。しかし片方は別の読み手からも読まれており、同じ場所へ運ばれていない」— この一撃で高度の問題が決着した。**反例1つは、数の突き合わせより速く、しかも検査可能である。**

## 帰属も「判断」でなく「手順」に置く

締めくくりに、測定文化の定着に効く一点。ある実装者が機械的改名を拒否して2重の stale を発見したとき、レビュアーは「判断が良い」と評価した。本人の訂正:

> 私も最初は形で見た。「置換すれば済む」と思って検証関数(改名先が有効な操作名かを検査する関数)を叩いたら False が返ってきて、初めて2重に古いと分かった。**測らなければ私も安直な修正を書いていた。判断が良かったのではなく、測る手順が挟まったことが効いた。**

「あの人は判断が良い」と書くと再現しない。「**あの手順が挟まると安直な修正が止まる**」と書くと再現する。レビューで褒めるときも、判断ではなく機構を名指す。

## チェックリスト

- [ ] 測る前に一文: この測定は、決定が必要とするものを覆うか
- [ ] 決定が目標状態についてなら、現状ではなく「害」を測っているか
- [ ] 測定を人に渡すとき、木と commit を添えたか。断定形にする根拠はあるか
- [ ] 自分の主張に MEASURED(実測した)/ READ(出典を読んだ)/ INFERRED(推論した)のラベルを貼ったか(INFERRED を MEASURED の顔で渡していないか)
- [ ] 述語は対象と1:1か。識別子で測ったなら内容で1件照合したか
- [ ] 数え方の規則が争点のとき: MEASURED を規則ごとに書いたか。規則未確定なら総数でなく規則+具体例を出したか
- [ ] 反証は総数の突き合わせでなく、相手の規則が誤って併合/分離する実例を1つ挙げて行ったか
