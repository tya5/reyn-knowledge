# モデルのせいにする前に — 失敗の帰属規律

## 前提

LLM(大規模言語モデル)を部品として使うシステム — エージェント実行系・スキル・パイプライン — で失敗が出たとき、「モデルの能力不足」という分類には特別な危険がある: それは**終端分類**である。そう書いた瞬間に調査は終わり、失敗は「直せないもの」の箱に入る。もし真因が自分の側の構造欠陥(配線・スキーマ・文脈の渡し方)なら、**直せるバグを直せないものとして葬った**ことになる。

実測の重み: 「弱いモデルの認知限界」と判定されかけた 0/5 の全滅が、実際には **7層に積み重なった実行系側の構造欠陥**であり、全層を直したら 4/5 になった。別の作戦では、能力判定の前に**10個の構造欠陥**を順次除去する必要があった。オーナーの原則(2026-05-28): 「PASS していない全シナリオについて、構造問題でないことを確認するまで次を許可したらダメ。せっかく見つけた障害を無視して先に行くのは許さない」。

## 1. 「モデル軸」と言う前の4層検査

失敗をモデルに帰属する前に、4つの層を順に晴らす:

1. **パイプラインの構造**(交絡 = 結果を歪める併存要因): 実行系側の欠陥・設定ミス・環境問題は除外したか。
2. **結果の事実**: 何が起きたか(編集の成否・終了コード・生成物)を事象レベルで検証したか。
3. **文脈の十分性(入力側)**: **モデルが実際に受け取った文脈を読んだか。** 問いはこれだけ — 「**有能なモデルなら、この文脈から正しい行動を出せたか?**」。必要な情報が文脈に無い(引き継ぎで欠落・ファイル内容が渡っていない・指示が曖昧)なら、それは**直せる提示側のバグ**であって、モデルの限界ではない。実測: 「5件全部モデル軸」と結論した後、引き継ぎがファイル内容を運ばず**計画の説明文だけ**を渡していた疑いが浮上 — モデルは不公平な文脈から「幻覚した」だけかもしれない。判定は暫定に格下げされた。この層は3つの中で**最もスキップされやすい**(指示文を字面どおり読み、実際の成果物の形と整合しているか、まで含めて)。
4. **検証ループ(出力側)**: モデルは自分の誤りに気づく**公平な機会**を持っていたか。判別軸は「使ったか」ではなく「**到達可能・発見可能だったか**」:
   - 検証手段が**隠されていた**(一覧に出ない・結果が返らない)→ 構造欠陥(直せる)。
   - 発見可能だったのに**使わなかった**(探索不足・成功を仮定)→ モデル寄りの判定が妥当。ここで補償的な仕組みを足すと**発見を覆い隠す**(成功してもモデル起因か分からなくなる)。

## 2. 免責証拠の出自 — 「一度は正しくやった」の作者を確認する

「同じモデルが一度は正しい出力を出した ∴ 仕組みは健全、失敗はモデルの揺らぎ」— この免責には出自の確認が要る。実測: 免責に使った「正しい出力」は、実は**前処理器が組み立てたもの**で、モデルは一度も正しい形を出していなかった。さらに決定的な事実 — 「その選択肢はそもそもモデルに**提示(advertise)されていたか**」 — は応答側でなく**リクエスト側**にあり、取得して数えたら **0回**だった。構造バグである。

- 免責に使う観測は、**誰が作ったか**(モデル / 前処理器 / fixture = テスト用の作り物)まで遡る。
- 応答ログだけで止まらず、**リクエスト側**(モデルに何が渡り、何が提示されたか)を取る。
- **逆方向も同じ**: イベント種別の集計(「permission_denied ×12」)だけで「構造的」と断定しない。個々の操作を見たら、拒否されたのはモデルが幻覚した実在しないパスだった — 集計は「拒否があった」ことしか言わず、「何が拒否されたか」は言わない。

## 3. 欠陥は積層する — 能力の結論には上限診断の環境が要る

1つの失敗インスタンスは **N 層の欠陥を同時に隠す**。1層直すと次の層が露呈する — だから「1つ直したのに まだ失敗する ∴ モデルが弱い」は誤推論である。

- **全構造交絡を除去した環境でのみ、能力の結論を出せる**: 全ツールが提示され・実行検証が可能で・ファイルシステムが正しく・セッションが新鮮 — 交絡が1つでも残れば「構造でなく能力」の判定は無効。
- 弁別子の例: **成果物は作られたが不正解**(実行系は動いた)と、**成果物が作られない**(実行系が疑わしい)は別の箱。
- 付随義務: **実際に走ったモデルを最初のリクエストで確認する**。ルーティングの既定値が軽量モデルへ格下げしていて、「強いモデルで解けなかった」実験が実は弱いモデルで走っていた可能性が都度確認された。[緑を読む技術](green-reading.ja.md)の「何が走ったか」の LLM 版である。

## 4. 弱いモデルの走行は採掘である — FAIL を数えるのは無駄コスト

弱いモデルでベンチマークや実地試験を回す**目的**は、合格率の測定ではない。弱いモデルは**探針(probe)**である: 経路・スキル・提示が弱い所でつまずいて、有能なモデルなら塗り隠してしまう構造欠陥を露呈させる。

- 「0/5、全部モデル軸」と分類して終える = 走行コストを捨てる anti-pattern。オーナー(2026-06-06): 「FAIL の数を数えるだけであれば無駄なコスト。価値は道の構造不具合を見つけること」。
- **全ての失敗に問う**: 「経路/スキルが何をしていれば、この弱いモデルでも**もっと先まで**行けたか?」— 間違った解での失敗ですら採掘対象(正しい文脈は提示されたか・足場や案内に欠落はないか・失敗は型として再発しているか)。
- 「本物のモデル限界」は**最後の手段**であり、便利な既定値ではない。走行の成果物は合格率でなく、**表面化した構造欠陥のリスト(各々に修正候補付き)**である。

## 5. 「弱くても動く」と「弱いモデルへの特化」は別 — 過剰適合の禁止

オーナー原則(2026-06-03): 「weak model に特化したいわけじゃない、単に weak でも動かしたいだけ」。弱いモデルがある機構でつまずいたときの分岐:

1. まず§1の文脈十分性を検査 → 文脈がどのモデルにも不十分(一般的な正しさのバグ)なら**構造修正**。弱いモデルが動くようになるのは副産物。実測: 「弱いモデルの限界」に見えた失敗が、実はどのモデルにとっても弱い一般的な文脈バグだった。
2. 文脈は十分で、弱いモデルだけが転ぶ → **設計を歪めない**。既存の単純な代替経路(fallback)に振り分ける — 「弱くても動く」はこれで満たされる。
3. 弱いモデルの癖に合わせた重い retry・特例分岐の増設 = **過剰適合、禁止**。
4. 行動を是正したいときの経験則: **足すのは効かない、引くのが効く** — 指示・欄・シグナルの追加(additive)は不発が続き、矛盾の除去(subtractive)とモード宣言だけが行動を変えた。
