# coder / tester / reviewer 分離運用の実務 — 誰が何を検証し、何を報告し、何を待つか

AI コーディングの標準構成は、実装(coder)・テスト(tester)・レビュー(reviewer)を**別エージェント**に分けることに向かっている。本リポジトリの全ドキュメントはこの構成を前提に読める — というより、**出典事件のほぼ全てが「実装エージェントの検証は緑、独立した別エージェントの検証で発覚」という形**であり、この資料自体が役割分離の効果測定になっている。本ドキュメントは、25本の規律を役割ごとの義務に組み直した適用マップである。

## 分離はなぜ効くのか — そして、いつ効かないのか

[テストの偽物は本物の形に合わせる](test-doubles.ja.md)の中心命題を思い出してほしい: **偽物とテストは、書いた人の思い込みを共有するので、互いに賛成し合ったまま現実を外す**。これはテストダブルだけの話ではない。実装者が自分の実装のテストを書くとき、**テストは実装と同じ思い込みから生まれる** — 同じ封筒形状(データを包む外側の形式)の誤解、同じ「ここは呼ばれないはず」、同じ正常系への注目。

独立したエージェントの強みは能力ではなく**文脈の非共有**である。実装者の意図を知らないエージェントには、挙動しか見えない — [意図の記録と挙動の記録](liveness-is-producer.ja.md)の原理を、組織構造で強制するのが役割分離である。

ただし分離は自動では効かない。**効かなくなる形が決まっている**:

1. **検証者が実装者の成果物(fixture・fake・テストハーネス)を再利用する** — 閉じたループが復活する([テストの偽物](test-doubles.ja.md)形2)。
2. **検証者が推論で相乗り署名(自分で観測せず、実装者の結論に賛成の署名だけ加えること)する** — 「もっともらしい原因がコードに在る」の grep は観測ではない([fixture の出自](fixture-provenance.ja.md))。
3. **検証者の推測が「指示」として届き、実装者の実測を押しのける**(後述)。

構成の柔軟性について正直に書いておく: tester と reviewer は小規模では1エージェントで兼ねられる。coder が自分のテストを書く運用も成立する — ただしその場合、**独立エージェントによる反証パス(strip・丸ごと殺し・実形状照合)が必須**になる。守るべき不変条件は組織図ではなく、**「witness(壊れたら RED〈失敗〉になるテスト)を、実装と同じ思い込みで書かない・検証しない」**である。

## coder(実装エージェント)の報告契約

完了報告は「できました、緑です」ではなく、**受け手が検証できる形**で書く。含めるべきもの:

- **strip 反証の明細**: 何を(どの性質だけを)壊したか、置換は当たったか(件数)、何が RED になったか。丸ごと殺しの結果([strip 反証](strip-falsification.ja.md)の4軸)
- **スイート結果は skip 一覧つき**: 裸の rc(終了コード)=0 でなく「N passed / M skipped: <理由>」([緑を読む技術](green-reading.ja.md))
- **測定の座標**: どのツリー(作業コピー)・どの commit・(順序依存があるなら)どの seed・どんな負荷の下か([測定対象のずれ](measurement-target.ja.md)・[fixture の出自](fixture-provenance.ja.md))
- **主張のラベル**: MEASURED(実測)/ READ(出典を読んだ)/ INFERRED(推論)を混ぜない
- **着地形の申告**: 意図された最終形か簡易版か。簡易版なら残余を明示([文脈を持たない主張](cross-context-claims.ja.md))
- **やり残しの可視化**: 完了分/残分のチェックリスト([やり残し](incomplete-work.ja.md))

## tester(独立テスト・反証エージェント)のメニュー

tester を分離する意味は「テストを書く工数の分担」ではない。**実装者の思い込みの外からテストを構成する**ことである。独立 tester の仕事は本質的に反証(falsification)であり、メニューは既にこのリポジトリにある:

- **strip 反証を自分の手で**: 実装者の「RED 確認済み」を再実行する。anchor の一意性・実行環境の同一性から自分で確かめる([strip 計測器](strip-instrument-integrity.ja.md))
- **機構丸ごと殺し**: 個別 strip が全部当たっていても、丸ごと `if False` で緑になる形は残る([strip 反証](strip-falsification.ja.md)軸4)
- **オーナー(報告者)の実経路で反証する**: 実装者のテストが踏んだ兄弟経路ではなく([修正は生きた経路で](fix-verification-live-path.ja.md))
- **fixture を実トレースから自作する**: 実装者の fixture を引き継がない。封筒の形は生産者のコードで確定([テストの偽物](test-doubles.ja.md))
- **欠陥ビルドで RED を実測してからゲートを信じる**([空虚なゲート](vacuous-gates.ja.md))
- **正常系の外を踏む**: エラー経路・実行時の不正入力・画面全体([正常系の外](beyond-happy-path.ja.md))
- **破壊のライフサイクルを当てる**: 切り詰め・追い出し・保持期限([復旧と切り詰め](recovery-truncation.ja.md))

## reviewer(レビューエージェント)の独立検証と、指示の非対称

reviewer の受け取り方の原則は[文脈を持たない主張](cross-context-claims.ja.md)にある: **事実の地図は受け取り、判定は自分の文脈で再計算する**。加えて diff の外を見る([一括修正 PR](sweep-reviews.ja.md)・[fix-class レビュー](fix-class-review.ja.md)・[監査は内容を照合する](audit-content-match.ja.md))。

そして reviewer には、他の役割に無い固有のハザードがある:

> **レビュアの推測は「指示」として届く。∴ 受け手は、自分の実測より先にそれに従う。**

実例: レビュアが「この観測点は外部サービスの内部だから存在し得ない」という**測っていない仮説**を指示として渡した。実装者は 1巡目の報告で**到達不能を自分で実測済みだった**のに、それを副次に格下げし、レビュアの推測を主に据えた。実装者の総括: 「**レビュア側の推測の方が危険です — 指示として届くため、私は自分のデータを再確認する前に従いました**」。coder の推測は自分の中で止まるが、**reviewer の推測は下流の実測を上書きする**。

- **指示を出すときは、推測と実測をラベルで分ける**(「実測: …」「私の仮説(未検証): …」)。同じ文体で書くと受け手には区別できない。
- **相手が実測を報告していたら、自分の仮説より上に置く。**
- **「結論は変えなくてよい、理由だけ直せ」を明示できる** — 誤った理由は正しい結論の下でも害を出す(コードに残った誤った理由を、次の実装者が読む)。
- **受け手側の防御は「気をつける」ではなく既定の手順**: 指示にも「これは実測か」を問い、適用前に自分で測る。同じ夜、この手順を常設の手順(standing practice)にしていたエージェントは一度も押しのけられず、していなかったエージェントは押しのけられた — 差は注意力ではなく手順である([検証ナレッジの体系](index.ja.md)の原理4)。指示の受け手が測って覆すのは**正常系**であり、覆されたら感謝して記録する。

## dispatcher / merger(依頼と受け入れ)の義務

**依頼(brief)に書くこと** — 各 doc の「依頼時」項目の集約:

- strip の破壊対象の名指し(「エスケープ処理だけを外せ」)、置換件数の確認、「緑なら報告せよ。緑は結論ではなく次の問い」
- 機構の正しさと到達の**2本の assert** を別々に要求([配線テスト](wiring-vs-mechanism.ja.md))
- (LLM 応答を録画した fixture を使う開発では)LLM に届くテキストを変えるなら fixture 再録の予告と「旧コード+新 fixture で RED」の要求
- 「既存の失敗」申告の形式(seed + main/PR 双方 + 差集合 P−M(P = PR 側で落ちたテストの集合、M = main 側で落ちた集合))
- user-facing 変更なら doc 更新を必須項目に

**マージゲートの3規則**(いずれも実測された事故から):

1. **verdict(レビュー判定)を読む・マージする、を同じバッチでやらない。** CI 緑を見て反射でマージすると、「修正してからマージせよ」と書かれた verdict を処理する前にバグが本線に載る(実例: 同一ターンで read + merge を束ね、co-vet(独立第二検証)が名指しした実バグがそのまま着地)。verdict を読む → hold/merge を判断する → それからマージ、を別ステップにする。
2. **自分が指摘を出したら、ゲートは「更新後の verdict」になる。** 指摘前の CLEAR でマージすると自分のエスカレーションと競走する(実例: 更新 verdict の 40 秒前にマージ)。
3. **「PASS、ただし1点」には作者の「final」を待つ。** 作者はその1点を今まさに直しているかもしれない(実例: 改善 commit の 47 秒前にマージ)。作者側の義務も対で: note を直し始めたら「HOLD」を先に発信し、終わったら「final」を出す。

## 役割 × パイプラインの対応表

| Stage([体系マップ](index.ja.md)) | coder | tester / reviewer |
|---|---|---|
| 0 対象の同一性 | 測定の座標(木・commit・seed)を報告に添える | 座標のない測定を受け取らない。自分の測定環境も0番チェック |
| 1 主張の中身 | strip 4軸を実施し明細を報告。skip 一覧を添える | strip を独立再実行(オーナー経路で)。丸ごと殺し。fixture は自作 |
| 2 環境の能力 | 「どの環境で未検証か」を平文で申告 | 「この環境はこれを赤にできるか」を問う。正常系の外を踏む |
| 3 静的前提 | 宣言・doc を根拠にした箇所に READ ラベル | producer を grep。監査は内容照合。削除は不在を assert |
| 4 レビューの死角 | やり残しをチェックリスト化 | diff に無い判断・母集団・同病の兄弟を自分で数える |
| 5 申告の出自と文脈 | 着地形(最終形/簡易版)を明示 | 判定を自分の文脈で再計算。指示には実測ラベル |
