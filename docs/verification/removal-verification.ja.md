# 削除の検証 — 「死んでいる」は反証すべき主張である

## なぜ削除は特別に難しいか

追加の欠陥はたいてい「動かない」という形で現れる。削除の欠陥は「**まだ動いていた何かを黙って壊す**」か「**消したはずのものが黙って残る**」という形で現れ、どちらも緑のテストと両立する。削除の検証は「無いことの証明」を最低4回要求する: 死んでいることの証明(前)、消費者がいないことの証明(前)、消えたことの証明(後)、参照が残っていないことの証明(後)。(節1〜2が削除前の2つ、節3〜4が削除後の2つ、節5はその後始末にあたる。)

## 1. 前提「X は死んでいる / 常に空」を反証する — producer の全列挙

「X はもう使われていないので消す」という PR の検証は、その前提を**所与ではなく反証対象の主張**として扱う。

実例: 「この追跡フィールドは前段の変更以降、常に空」という前提の削除 PR を、検証者が「明白な producer(チャット経由の書き込み)は確かに消えている」ことを確認して SAFE(検証報告の判定ラベル)と判定した。しかしフィールドは**クラッシュ復旧の自動再開経路**という非自明な producer からまだ生きて書かれており、削除によって「復旧されたタスクが一覧に表示されない」という実害が生じる状態だった。

- **X の全 producer を grep で列挙する**(書く側・追加する側の全経路)。クラッシュ復旧・自動再開・バックグラウンド復元は、非自明な producer の定番。
- **判定は検証した軸に限定して書く。**「チャット経由の軸はクリーン」であって「この PR は安全」ではない。過大な PASS は、未検証の軸に青信号を出す。

## 2. reader も列挙する — そして自分の監査を自分で再反証する

producer の列挙が済んでも半分である。実例: ログのイベント種別の削除で、最初の監査は「**書く側ゼロ**、復元処理もフォールスルーする」で削除可と結論し、レビューも**承認済み**だった。監査者がなお掃き直したところ、**読む側(replay 機構・ロールバック時のイベント分類表・会話文脈の保持処理)が生きていた** — 実装に入る前に自分で発見して差し戻し、誤削除ゼロで済んだ。

> **レビューの「承認」は免罪ではない。承認後・実装前に見つけた穴は、そのまま差し戻せば無傷である。**

もう1つ、ここで見つかった重要な区別:

> **「死んだ名前を参照する生きたコード」は、死んだ散文(コメント・文書などの実行されないテキスト)ではない。**

削除済みツールの名前がコメントに残っているのは散文(書き換え可)。だが `frozenset({"invoke_skill"})` という重複排除の集合、その名前をキーにしたエラー種別、`name == "invoke_skill"` の比較は、**削除済みの名前を参照する挙動を持つ生きたコード**である。トークンの見た目(コメントっぽい)ではなく、**そのコードが何をするか**で分類する。

## 3. import 緑 ≠ runtime 緑 — 消費者は実行時に壊れる

共有状態オブジェクト(dataclass 等)からフィールドを削除しても、`python -c import` と linter は**緑のまま通る**。壊れるのは、残った消費者がそのフィールドを**読む瞬間**の `AttributeError` — 実行時である。実例では、削除 PR の後、**全チャットターンが例外で死ぬ**状態で「import + lint 緑、テストのサブセット合格」と報告された(482 件の失敗のうち 336 件が、この単一の宙吊り reader の連鎖だった)。

- 削除の仕様書には**削除対象の定義箇所だけでなく、全消費者**を列挙して含める(`.field` / `symbol(` を残す側のファイル全体に grep)。
- 検証ゲートは「import + lint + サブセット」ではなく**実際の消費者経路の実行**(フルスイート、または当該経路のテスト群)。

さらに深い変種: 削除されたシンボルの import が**関数内**(モジュールトップでない)にあるコードは、モジュール読み込みでは踏まれず、どのテストもそのハンドラを呼ばなければ、**import 緑かつフルスイート緑のまま実行時に壊れている**。登録済みツールがこの状態で生き残った実例がある。

- 一括削除の検証では、**登録・ディスパッチ層を grep する**(ツール登録簿、`register(X)`、ディスパッチ表)。登録されたまま死んでいる消費者は pytest から不可視である。
- そうしたツールを消すと、**並行する登録簿すべて**(プロンプトのカテゴリ表、マスターテーブル、ベンチマークの目録)に連鎖する — 全部追う。

## 4. 削除対象の「不在」を明示的に assert する

一括削除の後、「残す側のファイルは揃っている」「宙吊り import ゼロ」「フルスイート緑」でも、**削除対象が消えたことの証明にはならない**。**緑はファイルの不在を要求しない** — 孤児化した死骸(参照が全部古いコメントで、機能的な importer がゼロのファイル)は、import にも pytest にも lint にも触られずに生き残る。実例: 13モジュールの削除で 35KB の中核モジュールが1つ生き残り、上記の全チェックを素通りした。捕まえたのは削除セットに対する明示的な `git ls-tree` である。

- **削除仕様の各項目について、不在を assert する**: ファイルなら存在チェックのループ、クラスなら `grep -c "^class X"` = 0、ツールなら登録簿から消えていること。
- **押した先の実体であるリモートの tip(ブランチ先頭のコミット)に対して**検証する。さらに: 古い remote-tracking 参照(origin/x のローカル控え。fetch しないと古いまま)は偽の「全部消えている」を返すことがある — 対象ブランチを明示して fetch してから見る。

## 5. 削除後の doc 同期 — 概念の生存 ≠ シンボルの生存

削除アーク(一連の作業のまとまり)の締めのドキュメント同期に、専用の罠がある: **概念が生き残ったから、同じ名前を冠したシンボルも生きていると推定してしまう**。実例: `control_ir_results` というフィールドとイベントは生き残ったので、`ControlIRExecutor` クラスとそのファイルも在ると思い込み、doc の参照を残した — 実測(`git cat-file -e` / `git grep -c 'class X'`)では**どちらも削除済み・定義ゼロ**だった。

- doc 同期では、編集した doc が参照する**全ファイルパス・全シンボルの実在を新しい main 上で確認**する(改名対象のトークンだけでなく)。
- **指摘された件数は下限であって全集合ではない。** レビュアーが2件指摘 → 全数掃討で4件。指摘分だけ直すのは「2件直して3件目を見逃す」形。
- 死んだ参照は**削除のみ**。新アーキテクチャへの付け替えは別作業(「再構築」)であり、同期 PR に混ぜない。

## チェックリスト

- [ ] 「死んでいる」前提: producer を全列挙したか(復旧・自動再開・バックグラウンド経路を含む)
- [ ] reader を全列挙したか(replay・巻き戻し・分析系)。「死んだ名前の生きたコード」を散文と区別したか
- [ ] 消費者経路を実行したか(import 緑・lint 緑・サブセット緑で済ませていないか)。登録・ディスパッチ層を grep したか
- [ ] 削除対象それぞれの不在を、明示 fetch した tip に対して assert したか
- [ ] doc の参照シンボル・パスの実在を新 main で確認したか。指摘件数を全集合と誤認していないか
- [ ] 判定を、検証した軸に限定して書いたか
