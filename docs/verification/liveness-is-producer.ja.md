# 生死は producer で判定する — 「意図の記録」と「挙動の記録」

## 問題の形

機能を削除・改名した後のコードベースには、その機能の名前を冠した残骸が大量に残る。ディレクトリを歩くコード、イベント種別(kind)ごとの分岐(`elif kind == "X":`)、デシリアライザ(保存データを読み戻す処理)、設定のキー。これらは生きているのか、死んでいるのか。

直感的な判定はこうなりがちだ: 「**読む側のコードがある**から生きている」。これが間違いである。

実例: 機能削除後の掃討で、約551箇所の残存を「構造的に使われている、残す(KEEP)」と分類した。イベントディレクトリを読むコード、状態ディレクトリを歩くコード、`kind == "skill_done"` を処理する分岐 — どれも呼び出されるコードだった。オーナーの一言「**なぜ生きてると考えてるの? 機能が存在しないのに**」で producer(生産側 = データを書く・イベントを発行する側)を調べ直したら: そのディレクトリパスを**構築して書き込むコードはゼロ**。そのイベント種別を**発行(emit)するコードはゼロ**。全部死んでいた。

> **死活の判定基準は「生きている producer がそのデータを今も書く/発行するか」であって、「reader(読み手)が存在するか」ではない。**

機能が削除されるとき、producer は一緒に消えるが、**reader は生き残ることが多い**(ウォーカー、分岐、デシリアライザ)。二度と生産されないデータを読むコードは**死んだコード**であり、「構造的に残す」対象ではない。残すと (a) 実際の死骸が残り、(b) 削除が消すはずだった古い名前が温存される。

## 確かめ方

- **producer を grep(コード全体の文字列検索)で探す。** 誰がそのファイル/パスを**書く**か、そのイベント種別を**発行**するか、その辞書を**構築**するか。reader ではなく。
- 「reader は生きているエンドポイントから呼ばれる」は不十分 — エンドポイントが、もう生産されないレガシーデータを読んでいるだけかもしれない。
- ディスク上のパス断片: docstring の例ではなく、**実行時にそのディレクトリを構築する箇所**を探す。
- イベント種別: `elif kind == "X"` は、`"X"` を発行する側がいなければ死んでいる。
- デフォルトの疑い方: **機能削除後、その名前を冠した reader/consumer は「生きた producer が示されるまで死んでいる」**。逆ではない。

## 削除(DELETE)か改名(RENAME)か

死活が付いたら、次は処置である。基準は明確に非対称:

- **死んでいる**(どちらかの端が欠けている / 読んでも挙動に影響しない)→ **機構ごと削除**(コード+テスト+名前)。**死んだコードを改名してはならない** — 死骸に新しい名前を付けるのは技術的負債の偽装であり、CI で RED にならないぶん、単に残すより悪質に長生きする。
- **生きている**(生産され、消費され、現在の挙動に影響する)+ 名前だけ古い → **改名**(名前のみ)。
- **不確実なら削除側に倒す。** 生きたコードの誤削除は CI が即座に RED で教えてくれる(回復可能)。死んだコードの誤改名は無期限に隠れる。

## 統一形 — 一族は一つの問いに潰れる

この誤りの一族(reader で判定・宣言で判定・名前で判定)は、すべて次の一問に還元される:

> **「これは『誰かが意図したこと』の記録か、『システムがしたこと』の記録か。」**

スキーマ(データ構造の定義)の宣言、ドキュメントの記述、種別定数のタプル、宣言に添えられた説明文、そして**識別子(名前)そのもの** — すべて前者である。**挙動を記録するのは producer・実行・計測だけ。** 意図の記録なのに、そこから挙動についての主張(「このイベントは記録される」「この機構は動いている」)を導いたら、その成果物がどれほど権威に見えても穴は実在する。橋渡しの検査は機械的だ: **producer はあるか。**

### 宣言はより危険な変装である

「reader がいるから生きている」より強い変装が「**宣言があるから生きている**」で、一晩に3つの基層で同時に出た:

| 基層 | 生きて見えた根拠 | 実測 |
|---|---|---|
| スキーマ | 監査要件の表に必須フィールド付きで載っている | **発行箇所ゼロ** |
| ドキュメント | 公開ドキュメントの種別例に載っている | **改名済みで存在しない** |
| イベントログ | 種別が定数タプルに宣言され、ドキュメントも「ログに記録される」と明記 | **書き込む経路が本体にもテストにもゼロ** |

3つ目が最も重い。ドキュメントは「巻き戻すと購読状態が復元される」と**復旧の挙動を約束**していたが、**巻き戻す対象が一度も書かれない**ので原理的に起こり得ない。これは古い記述ではなく、**偽の保証**である — 信じた運用者は「何も残っていない」状態を正常と読む。

### 名前が一族で最も危険な理由

説明文には吟味すべき「文」が付いている(「これは意図の記述だ」と気づく余地がある)。**名前は文を伴わずに示唆だけを届ける。** 実例: `Cancelled` という名前から標準ライブラリの `CancelledError` との連想で「規約違反がある」と推論しかけた — 実測では独自のドメイン例外で、違反は存在しなかった。

### 説明文は仕様であって報告ではない

宣言に添えられた説明文(「検索結果からツールが**ロードされた**ことを表す」)を読んで「システムがそうしている」と判定した実例がある。実測は逆で、その処理は外部サーバ側で起き、自システムには対応する分岐がゼロだった。決定打として、**その宣言を追加したコミットのメッセージ自身が「本体コードの変更なし」と明言していた** — 発行側を書かないまま、意図的に宣言だけが作られていたのである。

> **宣言の説明文は「その宣言が何のためか」を述べており、「システムが何をしているか」ではない。producer が無ければ、それは未実装物の仕様書である。**

### 抽象レベルの取り違え

「死んでいる」以外の変装もある: イベント種別の例示リストに `read_file` が載っていたが、これは種別ではなく、`tool_executed` イベント内のフィールドの**値**だった。死んでいるのではなく**そもそもその種類のものではない**。例示を更新しても直らない — 一次ソース(実際の producer)から列挙を導出する仕組みにすると、この取り違えは自動的に露出する(「導出リストに `read_file` が現れない」ことの説明を迫られる)。

## ゲートは2方向から満たせる

「宣言 ⊆ 発行」を検査するゲートを緑にする方法は2つある: **発行側を足す**か、**宣言を消す**か。どちらが正しいかは「その機能は生きるべきか」で決まり、**ゲートは答えない**。また、「発行側を足せない」(観測点が外部にある)と「誰も足していない」は別の状態であり、書き分けが要る。

## 実践方法

- 「宣言されている」を根拠にしない。レジストリ(登録簿)・スキーマ・定数タプル・ドキュメントの表 — どれも producer ではない。**書く側を grep する**(emit / append / write / construct)。
- 主張に MEASURED(実測した)/ READ(意図の成果物がそう言っている)/ INFERRED(推論した)のラベルを付ける。READ には「その出典が**何についての**証拠か」を添える — READ を MEASURED に潰すのが再発している誤り。
- 死活分類は項目ごとに行う。「たぶん生きている」という直感で束ねない。
