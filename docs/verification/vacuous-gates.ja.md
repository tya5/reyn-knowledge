# 空虚なゲートの生まれ方 — 壊れたビルドでも緑になるテストの典型形

**ゲート(gate)**とは、特定の退行(regression)を二度と起こさないために置くテストや自動チェックのことである。そして**空虚(vacuous)なゲート**とは、守るべき欠陥が実際に起きているビルドでも緑になってしまうゲートを指す。

空虚なゲートは、ゲートが無いより**悪い**。CI(push のたびに自動でテストを回す仕組み)が緑を返し続ける限り、誰もその面を再検査しないからだ。しかも空虚なゲートは「生まれつき空虚(born-vacuous)」であることが多い — 一度も欠陥を検知できたことがないのに、緑の実績だけを積み上げていく。

以下は、実際の開発記録(形1〜3は同じ作業日に3連続で発生。他の形は別の事件)から抽出した、空虚さが忍び込む典型形である。

## 形1 — 終端状態だけを assert する

(以下、assert〈表明〉= テスト内の検査式のこと。「〜を assert する」=「〜を検査式で確かめる」の意味で使う。)

例: ストリーミング配信で「複数の差分(delta)が届いたら、画面には1つのエントリに全文が表示される」ことを守りたい。前提として、この実装では最後に届く完了フレーム自体も全文を運ぶ。

```python
def test_stream_renders_one_entry():
    send_deltas(["Hel", "lo, ", "world"])
    send_completion_frame()
    assert len(view.entries) == 1
    assert view.entries[0].text == "Hello, world"   # 完了後の終端状態だけを見ている
```

このテストは **delta がゼロ個しか届かなくても通る**。完了フレーム自体が「1エントリ・全文」を作るからだ。つまり「差分が届いて描画される」という肝心の経路が死んでいても緑になる。

**閉じ方: 中間断面を assert する。** 終端の前に「途中の状態」を見る:

```python
    send_deltas(["Hel", "lo, "])
    assert view.entries[0].text == "Hello, "        # ← 途中で部分テキストが見えること
    send_deltas(["world"]); send_completion_frame()
    assert view.entries[0].text == "Hello, world"
```

中間断面を見れば、「何も起きていない」場合に自動で RED〈テスト失敗〉になり、**到達の witness(証人 = 壊れたら RED になる検査)がゲート自体に内包される**。

## 形2 — positive control が別経路を通っている

**positive control(陽性対照)**とは、「信号が出るはずのケースを流して、検知器がちゃんと反応することを確かめる」ためのテスト構成である。ここに罠がある: **positive control が検証対象と別の経路を通っていると、隣の経路の生存しか証明しない。**

例: イベントが `push_event()` 経由で届くことを検証したいのに、positive control では内部キューに `_queue.put()` で直接入れていた。これでは `push_event()` が死んでいても control は成功する。

**閉じ方: positive control は検証対象と同一の配送経路を通す。**(形1の中間断面を入れると、そもそも別建ての positive control が不要になることが多い。)

## 形3 — 存在チェック・弱い RED

「定数が定義されている」「import できる」の assert は、**「その値が実際に出力に載る」という性質を何も witness しない**。ImportError で RED になるだけのテストは、機構の死をほぼ検知できない。

**閉じ方(共通): 欠陥のあるビルドを実際に作って RED になることを実測してから ship する。** これが「生まれつき空虚ではない」ことの唯一の証明である。strip(検証対象の機構を意図的に無効化すること)による反証 — [strip 反証](strip-falsification.ja.md)の適用形。

## 形4 — 散文(docstring・コメント・PR 本文などの説明文)が2つの性質を主張し、テストが片方しか覆っていない

docstring(コード内の説明文)・PR 本文・コメントは、しばしばテストより広いことを主張する。

実例1(一般化): 「このキーは**借用**であって奪取ではない」と docstring に書きながら、テストは「借りる」側だけで「返す」側は0本。

実例2: 予約キーのテーブル `RESERVED_KEYS` に「新しいキーバインドが予約キーを黙って奪うことはできない」と書きながら、ゲートが検査していたのは「この機能の2キーが、既に使われているキーの集合と衝突していないこと」だけ。予約キーを後から奪う変更を入れても**27本全部緑**だった。

> **性質を記述することは witness することではない。書き下すのは「見つけられる」ようにする行為であって、「真にする」行為ではない。**

検出法として実際に機能した問いがこれ:

> **この名前付きテーブルは、テストの中で assert の「主語」か、それとも別の集合を組み立てる「材料」か。**

`RESERVED_KEYS` はテスト内で**読まれていた**ので配線済みに見えた。しかし、それ**について**は何も assert されていなかった。付随して2つ:

- **覆われていない方が「より一般的な性質」になりやすい。**「任意のバインド vs 任意の予約キー」は「この2キー vs 全部」より広い。広い方を散文に書き、狭い方を assert してしまう。
- **テーブル自体の非空虚も要る。** 空の `RESERVED_KEYS` は `not (reserved & live)` を自明に真にする。`assert reserved` を1行添える。

## 形5 — 幾何の収まり検査(containment)は軸と階層を持つ

「画面外にはみ出していない」のような幾何の主張は、1つの不等式では表せない。同じ穴が3つの事件で、形を変えて4回すり抜けた記録がある:

| ゲートが見ていたもの | すり抜けた経路 |
|---|---|
| `height > 0` かつ `display == True` | 両方 True のまま**画面外へ押し出された**(y = −8)。「存在する」は「見える」ではない |
| 収まりの**上限のみ**(`y + h <= H`) | **負の y** が素通り。両端が要る(`y >= 0` かつ `y + h <= H`)+ 潰され下限(高さが最小値以上であること) |
| 外側の領域の幅 | 消費は**内部**で起きていて、外側の幅は変わらない。**測る面が違う** |
| 親だけ・水平軸だけ | 親は収まるが**子要素**が画面外。x は正しいのに**縦方向**でクリップされ不可視 |

規則:

> **containment は「両軸 × 両端 × 実際に見せたい子要素」まで下ろす。** 親が収まっていることは子が見えることを意味せず、片軸が収まっていることはもう一軸で不可視でないことを意味しない。

- assert する面を選ぶ前に、**スペースの消費が起きる場所**(外側の領域か、内部レイアウトか)を特定する。
- **最低2つの画面サイズでパラメータ化(parametrize = 複数条件で同じテストを回す)**し、壊れを実測した寸法を必ず含める。1サイズの収まり検査は「その幅では収まる」以上を主張しない。
- **strip が緑になったら、まず gate を疑う。** 実装が正しかった可能性より、測る面・軸・深さを間違えた可能性の方が高い。
- 例外として「導出値」の gate は strip の期待が**逆**になることがある(ラベル幅を最長から導出したら、ラベルを短くしても崩れないのが正しい = その strip は緑が期待値)。**緑が期待値の strip を「非空虚の証拠」として数えない**こと。

## 弱い検出器に頼らない — 兄弟との食い違いは偶然

実務での発見エピソード: strip 5本中1本だけ緑になったのを実装者が「異常だ」と疑って追跡し、本物の穴を見つけた。だがこの検出は**兄弟が食い違うときにしか働かない**。一族まるごと未到達なら、全部緑で黙って失敗する。一般化するべきは異常検知ではなく**到達性の assert**(「この経路は本当に実行されたか」をゲート自身に持たせる)である。

## ゲートを書く・レビューする前の3問

1. 終端状態だけを見ていないか。**中間断面**はあるか
2. positive control は**同一経路**か
3. **欠陥版で RED を実測**したか

「X が起きない」系の assert は特に危険で、X の生産経路が死んでいるだけで緑になる([生死は producer で判定する](liveness-is-producer.ja.md)と同根)。
