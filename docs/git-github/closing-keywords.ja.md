# closing keyword は字面で発火する — 6つの踏み方と防ぎ方

## 前提 — closing keyword とは

GitHub では、PR(pull request)の本文や commit メッセージに `Closes #123` / `Fixes #123` / `Resolves #123` と書くと、**PR のマージと同時に issue #123 が自動でクローズされる**。便利な仕組みだが、この**パーサ(解析器)は文の意味を読まない**。2つの字面規則だけで動く:

1. **コードスパン(バッククォート `` ` `` で囲んだ部分)の中は読まない。**
2. **囲まれていなければ、文脈に関係なくリテラル一致で発火する。**

この2規則が、人間の意図と正反対の結果を量産する。エージェント開発では PR の生成量が多く、issue の自動クローズが**タスク管理の実体**になるため、この誤発火は「タスクが黙って消える/黙って残る」という運用事故に直結する。

## 中心命題

> **「`Closes #N` と書いた」は何かが閉じることの証拠にならず、「書いていない」は閉じないことの証拠にならない。答えるのは parser の出力 — `gh`(GitHub CLI)の `gh pr view <PR> --json closingIssuesReferences` — だけである。**

これは[緑を読む技術](../verification/green-reading.ja.md)の「rc(終了コード)=0 は何が走ったかを言わない」と同型である: **書いた文字と起きることは、どちらの方向にも一致しない**。そして確かめるコストは1コマンドで、**マージ前の open な PR に対しても実行できる**。

## 6つの踏み方(すべて実測)

| # | 形 | 実例 |
|---|---|---|
| 1 | **バッククォート内 → 閉じない**(false negative) | `` `Closes #2972` `` と書いた PR がマージされ、issue は開いたまま。マージ自体は完全に正常に見えるので誰も気づかない |
| 2 | **否定・説明文の生キーワード → 閉じる**(false positive) | 見出し「**this does NOT close #2940**」が **#2940 を閉じた**。閉じないためにこそ書かれた文が閉じ、オーナー報告のバグが**2日間**、3つの監視役(リード・レビュー担当・棚卸し担当の各セッション)の誰にも気づかれずクローズ済みだった |
| 3 | **キーワードについて語る文も宣言として読まれる** | ルールを説明する英文 "`Closes` here would **auto-close #2827**" の中の生の `close #2827` という隣接が、#2827 を実際に閉じた(和訳: 「ここに Closes を書くと #2827 が自動クローズされてしまう」) |
| 4 | **commit メッセージ経路** | squash マージ(複数 commit を1つに畳むマージ)の既定本文は**各 commit メッセージの連結**。途中の commit に残っていた `Closes #1909` が main の commit メッセージに入り、**マージ前の `closingIssuesReferences` が 0 件でも**閉じた |
| 5 | **指示文が罠を運ぶ** | 「本文に『closed by #3410』と明記して」という**レビュアーの指示どおりに書いた**PR が、#3410 を閉じかけた。PR を書く人だけでなく、**文言を渡す人**が発生源になる |
| 6 | **語順の偶然** | `Applies the real fix #3457's temporary carve-out...` — 誰もクローズの話をしていないのに、**英語の語順が偶然 `fix #N` を作った**(所有格の `'s` はパーサに見えない) |

なぜ形1が起きやすいか: 多くのリポジトリには「識別子はバッククォートで囲む」というハウススタイルがあり、`Closes #N` が周囲のリテラルと**同じ見た目に揃えられてしまう** — 不注意ではなく、スタイルの副作用として発生する。さらに、依頼文(brief)の中で壊れた形を例示すると、**実装エージェントはそれを忠実にコピーする**(罠の発見の10分前に書かれた依頼文が、4時間後に同じ事故を再生産した実測がある — 途中で学んだ罠は、**既に送付済みの依頼文を遡って修正しきる**まで閉じない)。

## 規律

**書き方:**

- 閉じたいとき: `Closes #N` を**バッククォートなしの平文**で書く。
- 閉じたくないとき: **キーワードを使わずに書く**。❌「does not close #N」「closed by #N」 → ✅「**#N はこの PR の後も open のまま**」「**#N 側の PR で完了する**」。
- `fix` / `close` / `resolve` が `#N` の**直前**に来ていないか、**語順として**全文を見る(形6)。commit メッセージも対象(形4)。
- 他人に PR 文言を指示するときは、**その文言自体をパーサ目線で読む**(形5)。

**検証(両方向):**

- PR を開いたら: `gh pr view <PR> --json closingIssuesReferences` — 閉じるべきものが**入っているか**と、閉じてはいけないものが**入っていないか**の両方を見る。
- マージしたら: 対象 issue の実際の `state` を見る。**マージ前の確認は必要だが十分ではない**(形4の commit メッセージ経路は本文検査をすり抜ける)。
- クローズイベントの `commit_id` / `actor` フィールドに意味を読まない — 実測では、**PR 本文の**キーワード起因でも手動クローズでも `commit_id=null`・actor は同一で、**null は何も区別しない**。ただし**非 null の commit_id は commit メッセージ経路の印**になる(確認は `gh api repos/<owner>/<repo>/issues/<N>/timeline`)。

## 「閉じるか」と「閉じるべきか」は別の問い

parser の検証は「この PR は #N を閉じる**か**」に答えるが、「閉じる**べきか**」には答えない。実測の事故: 依頼文が「`Closes #3043`」と「30秒タイムアウトには触るな」を同時に要求した — **#3043 のタイトルはそのタイムアウトのバグ**だった。PR は「スコープ外」と本文に書きながらその issue を閉じ、3回再現済みのバグの追跡が消えかけた。実装者の総括:

> 私は `closingIssuesReferences` を2回走らせた。2回とも「キーワードは parse されたか?」に答えていた — 本当の問いは「この PR はこの issue を閉じる**べき**か?」だった。**自分を「検証済み」と感じさせる check を走らせていた。**

- **閉じる前に issue の「タイトル」を読み、それがこの PR の直したものかを確かめる**(これは意味の判断なので機械化できない — できないと知っておくことが規律である)。
- 間違って閉じた場合の復旧: タイトルが実態と乖離しているなら、reopen よりも「**タイトルを、実際に修正された内容に合わせて訂正し、残りを新 issue へ**」が正しいことがある(クローズ済み issue を後から走査する人はタイトルしか読まない)。

## 閉じる前の列挙 — 「たぶん最後の PR」で閉じない

複数 PR で1つの issue(アンブレラ)を進める運用では、`Closes #N` を書く前に**その issue を参照する open な PR を列挙**する:

```bash
gh pr list --state all --search "<N> in:body"   # 全状態で引いて、その中の open を数える
```

open がゼロのときだけ `Closes #N`、そうでなければ `part of #N`。実測: 列挙せずに閉じた結果、**まだ open の兄弟 PR が残ったまま40分間、アーク(複数 PR からなる一連の作業)の完了前に issue がクローズ済み**になっていた。

> **「たぶんこれが最後」で閉じてはいけない理由: 閉じた事実そのものが残件の存在を隠す。** クローズ済み issue はレビュー対象からも open 一覧の棚卸しからも消えるので、残件は「誰も見ない場所」へ移動する。

サブ PR の書き方: アンブレラへの言及は `part of #N` / `toward #N`。**「後続の PR-3 が closes #N する」という未来の説明文でも生のキーワードを書かない**(形2・3で発火する)。

## 機械化の記録 — ゲートを作るときの教訓ごと

この罠は最終的に CI ゲート(「**著者が宣言した意図**と**パーサの出力**の矛盾」を検査する自動チェック)で塞がれた。その構築過程自体が教訓を含む:

- **検査は3方向**: 閉じたい宣言があるのに parser が閉じない(形1)/ 閉じない宣言があるのに parser が閉じる(形2・3)/ **何も宣言していないのに閉じる**(宣言前提の検査2つだけでは穴になる)。
- **抜け道(escape hatch)の設計**: 「この PR は #N について議論しているだけ」という本文全体スイッチ案は、**レビュー側がゲート導入 PR 自身を反例に却下した**(その PR は本物の宣言と議論の両方を含み、全体スイッチは本物の宣言の検査まで消す)。採用されたのは **issue 番号ごとの**マーカー。抜け道の語彙は、issue 番号単位のように狭く保つ。
- **最初の実ケースでバイパスが要る機構は、(ゲートが本物であることの)証明に失敗している**: 初版はゲートを通すために PR 本文へ**目に見えないゼロ幅スペースを11個**入れていた — 発見不能なバイパスは、そのゲートが殺すはずだった欠陥クラスそのものである。マージブロッカーとして扱われた。
- **ゲートは本文しか見ない** → 形4(commit メッセージ)は残る。ゲートが緑でも「close は防げた」と読まない — **ゲートが塞いだ経路と発火した経路は別でありうる**。

## チェックリスト

- [ ] 閉じたい: 平文の `Closes #N`。閉じたくない: キーワード不使用の言い換え
- [ ] `fix`/`close`/`resolve` + `#N` の隣接を、本文と commit メッセージの**語順**として点検したか
- [ ] PR を開いた後: `closingIssuesReferences` を両方向で確認したか
- [ ] `Closes #N` の前に: `part of #N` の open PR を列挙したか(閉じた事実は残件を隠す)
- [ ] issue の**タイトル**は、この PR が直したものを記述しているか(閉じるべきかは別の問い)
- [ ] マージ後: 対象 issue の実際の state を見たか
- [ ] 罠を途中で学んだら: 既に送付済みの依頼文を遡って修正しきったか
